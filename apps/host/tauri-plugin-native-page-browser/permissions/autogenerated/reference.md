## Default Permission

Default grant for the native-page-browser plugin: open an `http(s)` URL in the
system's in-app browser (`open`), and close a view it opened (`close`).
References the hand-authored, richly-described `open.toml` and `close.toml`
rather than the boilerplate autogenerated `allow-open` and `allow-close` grants.

#### This default permission set includes the following:

- `open`
- `close`

<tr>
<td>

`native-page-browser:close`

</td>
<td>

Allow closing a view `open` opened, by the `view` name it was opened under. On iOS
it dismisses that `SFSafariViewController` and any view presented over it, each
sending its `closed` event; a view already gone closes nothing. A Custom Tab
(Android) and a default-browser tab (desktop) can't be closed by the app, so
there it is rejected.


</td>
</tr>

<tr>
<td>

`native-page-browser:open`

</td>
<td>

Allow opening an external `http(s)` URL in the system's in-app browser, presented
as a native page: `SFSafariViewController` (iOS), a Custom Tab (Android), or the
default browser (desktop). A `Channel<BrowserEvent>` carries exactly one `closed`
event back per successful `open` once the view is gone (iOS and Android only;
desktop never sends one), and on Android a `keptAlive` before it when the view's
browser keeps the app alive under the view. The caller names the view (`view`),
for `close`, and says how it shows beside the views showing (`mode`): on iOS a
`replace` open replaces them and reports each one's close, and a `stack` open
presents over them; on Android a `replace` open arriving while a view is still
opening joins it, a `stack` open launches its own, and one arriving while the
app is in the background is rejected. The caller cannot script or navigate the
open page. Non-`http(s)` URLs are rejected.


</td>
</tr>
</table>
