# Server Runs — Explanation

How the Tauri host runs the install's servers, what it notifies about them,
how the base sees and changes them and opens their consents, and how the
host keeps running them in the background.

## What it is

Every server in `servers.json` is one **unit** on the app's unit runner
(`tauri-unit-runner-rust`, over the Tauri-free `unit-runner-rust`). Its
words (unit, run, run policy, detail, stop reason, present, background
session, ended by platform) and its rules are in unit-runner-rust's
[Design Explanation](../../unit-runner/unit-runner-rust/docs/Design%20Explanation.md),
and the Tauri side in tauri-unit-runner-rust's
[Design Explanation](../../unit-runner/tauri-unit-runner-rust/docs/Design%20Explanation.md).
This page covers what the servers group and the host build on them.

**The app pushes, `UnitRunner` starts and stops runs per policy.** The host
never decides when a server runs. It stores each server's run policy in
`servers.json` and pushes it to `TauriUnitRunner`; `UnitRunner` starts and
stops runs to match, restarts a run that ends on its own, and keeps the app
alive in the background while any server should run. It never reads
`servers.json`.

**On Android, servers run while the app is open, and for the grace period
after.** The background session there is a `shortService`, which Android times
out after 3 minutes, so the host builds `TauriUnitRunner` with
`BackgroundSessionLength::GracePeriod` (see unit-runner-rust's Design
Explanation). While the app is open, servers run in-process with no foreground
service. When it moves to the background, the session starts and every server
whose policy wants it running (`always` and `until` included) keeps serving for
the 2-minute grace period, then stops (`PolicyInactive`), and the session ends
as no longer needed. When the app comes back, the servers run again.

**On iOS, every server shares one background window, and they all stop when
it ends.** iOS ends its background time itself, so the host builds
`TauriUnitRunner` with `BackgroundSessionLength::AsLongAsNeeded`: the one
background session, for every server at once, runs while any server's policy
wants it running, the app in the foreground included. When the app moves to the
background, iOS gives that session its background time, typically about 30
seconds, and the plugin stops the session with `PlatformExpiration` just
before it runs out (see Plugin fork below). Every server still running stops
then, together (`SessionEndedByPlatform`), and each posts its own "Wildflower
server paused". That window is usually shorter than the 2-minute grace
period, so a `whileOpen` server stops with the rest; only an `until` whose
deadline passes inside the window stops before it (`PolicyInactive`). When the
app reopens, it is present again, and each server runs again if its own policy
wants it running: `always` and `whileOpen` do, `until` only while its deadline
is ahead, and `off` stays stopped. A `BGTask` iOS launches later starts the
session again: the servers whose policy wants them running serve inside it,
until it expires the same way.

**On a desktop, the session lasts while any server should run.** The host uses
`AsLongAsNeeded` there too, and no platform time limit ends the session.

**The base's run-policy field says how long is left, and what a phone
allows.** A live `until` reads as the time left, rounded up (minutes under an
hour, never "0 min", then whole hours), and its deadline: "On for 2 h — until
5:42 pm". Its clock ticks each minute, on the deadline's minutes, and reads
the time again as the page is shown, since a suspended app's timers run late,
so the field reads "Ended at 5:42 pm" once the deadline passes, with no change
of policy. On iOS and Android, while the policy is `always` or a live `until`,
a note above the field, which describes its picker, says what that phone
allows, as the Android and iOS paragraphs above describe: on Android, the
2-minute grace period; on iOS, about 25 seconds (the background time, less the
5 the plugin keeps to stop cleanly), then only the short spells of the
`BGTask`s iOS launches. The host app maps the platform once from the
`TAURI_ENV_PLATFORM` the Tauri CLI builds it with, and passes it to the base's
router context.

## The flow

```text
[Tauri host run()]
  runner = TauriUnitRunner::<ServerDetail>::new(BackgroundServiceStartConfig { label, type })   // from tauri-shared-config.json
  .plugin(tauri_plugin_notification::init())
  .plugin(runner.background_service_plugin())   // the background session
  .plugin(runner.lifecycle_plugin())            // present/absent, iOS return to the foreground, session start/end
  setup():
    host_ports = consent dialog   // shared by every run of every server
    wildflowerhealthio_servers_tauri::host_servers(app, data_root, &runner, host_ports, server_config)
      read servers.json ── unreadable ─▶ logged; no server runs
      for each record: ServerUnits::push(record)
        runner.set_unit(domain, record.run_policy, || ServerUnit::new(server_config(&record)?, host_ports))
      spawn: emit_server_statuses(runner.subscribe(), registry)   // the server-status event
      spawn: notify_consent_requests(runner)  // consent notifications, opened on the desktop and at arrivals in the foreground, and the app icon's badge
      spawn: post_stop_notifications(runner.subscribe_stops())
      manage ServersState { registry, data_root, server_units, registry_writes }

[command] server_add / server_set_credentials
  lock registry_writes ─▶ write servers.json ─▶ ServerUnits::push(record) ─▶ unlock
[command] server_set_run_policy(domain, choice)
  lock ─▶ write the policy (for ─▶ until) ─▶ runner.set_unit_policy(domain, policy) ─▶ unlock
          └─ the runner doesn't hold it ─▶ ServerUnits::push(the record as stored)
[command] server_update(domain, launcherUrl, authorizationUrl, certificateAuthority)
  lock ─▶ write the record ─▶ a run input changed, or the runner doesn't hold it? ServerUnits::push(record) ─▶ unlock
[command] server_remove(domain)
  lock ─▶ runner.remove_unit(domain), awaited ─▶ store policy Off, delete the folder, then the record ─▶ unlock
          └─ the deletion fails ─▶ ServerUnits::push(the record as stored, Off)
[command] servers_list
  read servers.json ─▶ join each record with runner.statuses() ─▶ read the cached certificate state of each server whose run reported none, concurrently ─▶ ListedServer[]
[command] server_open_pending_consent(domain) / server_open_notified_consent(notificationId ─▶ domain)
  ensure_launchable ─▶ ServerDetail::pending_consent ── none ─▶ nothingPending
  └─ consent_sign_in_url(code, consent) ─▶ the in-app browser, a launch view over the views showing
       └─ iOS: spawn: ServerConsentWatcher::until_settled(consent) ─▶ close the view ── the view closes first ─▶ stop

[UnitRunner] the policy wants it running ─▶ a run, on its own thread and runtime:
  factory: server_config(&record) ─▶ ServerUnit
  ServerUnit::run(ctx)
    wildflowerhealthio_wildflower_server::set_up(config, host_ports, observers with the run's own senders)   // binds no port
    spawn: each health, tunnel state, certificate state or pending consent ─▶ ctx.set_detail(ServerDetail { health, tunnel, certificate, pending_consent, launch_minter, sign_in_code_minter, consent_watcher })
    ctx.announce_running()                                         // Starting ─▶ Running
    WildflowerServer::serve(ctx.shutdown_token())
  asked to stop ─▶ detail cleared at once, what the run sets after dropped   // nothing launches into a stopping run
  the run ends ─▶ runtime shut down (every slice task with it) ─▶ Stopped { reason, error }

[servers-tauri] runner.subscribe() ─▶ ServerStatusTracker ─▶ server-status, to the main webview
                     runner.subscribe() + runner.subscribe_foreground_arrivals() + runner.units_to_run() ─▶ ConsentNotificationCoalescer ─▶ consent notifications and opens, and the app icon's badge
                     runner.subscribe_stops() ─▶ StopNotificationCoalescer ─▶ stop notifications

[base, once its consent is answered] plugin:background-service|configure_recovery
  { enabled: true, config: the same label and type }
```

| Consents                | The newest consent waiting on a run is its `ServerDetail::pending_consent`, cleared with the detail once the run is asked to stop, and the server's status carries it as `pendingConsent`, named for the client that asks (its registered name, or its `client_id` while it has none). A task on `runner.subscribe()` feeds `ConsentNotificationCoalescer`, which posts "‹client› wants access to ‹domain›" under the server's id (`consent-request:<domain>`) once for each request that is newest on a server and not yet notified for: requests stack, so a new one takes over and deciding it brings back the one before, which, like a request still waiting when the run restarts, doesn't notify again. A request made by a browser signed in as the Owner, as one a launch opened, neither notifies nor opens: `/oauth/authorize` sends that browser to the consent card and records it on the request (`decidable_in_requesting_browser`), so the Owner already looks at it. It still counts as the server's newest, and the server's page still shows it as the pending request. A server forgets the requests it notified for once its run reports nothing pending, keeping at most 32 meanwhile. On a phone the host withdraws a server's notification once the request it announced is no longer the server's newest (decided or expired, or another it notified for is newest again), or the server is removed; a desktop's plugin can't withdraw one. A tap opens it on a phone. On a phone each arrival of the app in the foreground, its first window and each return alike (`runner.subscribe_foreground_arrivals()`, counted once the runs it starts and stops are asked for; not leaving the background on Android, but coming back to a Custom Tab the Owner left up over the base when going home), opens at most one request. Of the newest requests of the servers the runner runs now (`runner.units_to_run()`), as their runs last reported them, kept while a run isn't reporting, each one the server notified for or opened is a candidate, and the one seen latest opens, so seeing the notification and coming back to the app goes straight to the decision, a consent closed undecided opens again, and a request notified while the app started in the background opens once it comes to the foreground. A request first seen at the arrival opens instead of notifying. Failing a candidate, each server on its way up at the arrival, one of those whose run isn't reporting, as at a start in the foreground, has its first report's request open instead of notifying, even one it notified for before; the first such report with a request opens it, and none after. A server that isn't on its way up, as one whose policy is off or the Owner turns on later, notifies as usual, and so does one whose run the arrival started stops before reporting, and every server once the app leaves the foreground or a notification is tapped. One the Owner's own browser made opens neither way. A tap on a notification wins over the arrival it brings, so only the tapped consent opens: on Android the host app's `MainActivity` marks the resume the tap brings, and that arrival opens nothing; on either phone the tap ends every open still waiting for its server, and so does the app leaving the foreground, where nothing can open. The first window opens before `host_servers` sets the servers on the runner, so the consent task counts an arrival from before it started as one as it starts. A request that arrives while its server is stopped or suspended waits until it expires (5 minutes), and the requester's wait page keeps waiting; one still pending when the base comes back opens as above. A desktop can't click a notification, so there the host also opens each request it notifies for at once in the default browser, as the server's page's Open does. ## Verification limits

`servers-tauri` and the app crate link `webkit2gtk`, so they build only
where GTK/webkit is installed (CI, and a container that has it). That is why
the logic lives in `servers-rust` and `wildflower-server-rust`.
`servers-rust`'s `tests/server_unit.rs` runs the real server through
`UnitRunner`: it comes up `Running`, answers `/health`, reports its health
and its tunnel's state as its detail, stops with the detail cleared when its policy turns off, and
sets up over the same folder and runs again when it turns back on. The manifest and plist tests
check what the files declare, not what the Android manifest merger or iOS make
of them, and the mobile background session can only be verified on a device.

On macOS, `tauri-plugin-notification` posts a dev build's notifications as
Terminal (`com.apple.Terminal`, by `tauri::is_dev()`), so they show only while
Terminal's notifications are allowed in System Settings → Notifications.

### Device test plan

Android (13 or later, with a server added):

1. First launch, with the server's policy set to always: the server runs with
   no foreground service. The merged manifest
   (`app/build/intermediates/merged_manifest/`) has none of the removed
   permissions, no `BackgroundCallConnectionService` and no `BootReceiver`.
2. Move the app to the background: the "Wildflower server is running"
   notification posts with its Stop action, and
   `adb shell dumpsys activity services app.tauri.backgroundservice` shows the
   service running as `shortService`. Starting it must not throw
   `ForegroundServiceStartNotAllowedException`.
3. Within 2 minutes, call the server through the tunnel from another device:
   it answers. After 2 minutes,
   the server stops, the persistent notification goes, and a call gets no
   answer.
4. Bring the app back to the foreground: the server runs again and answers.
5. Background the app again and tap Stop on the persistent notification: the
   server stops, and the "Wildflower server stopped" notification names it and
   the reason.

iOS:

1. First launch: the notification prompt appears once.
2. Background the app, then launch each task from the debugger
   (`e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"<bundle id>.bg-processing"]`,
   then `.bg-refresh`): the server answers through the tunnel inside the
   window.
3. End each window (`_simulateExpirationForTaskWithIdentifier:`): every expiry
   posts "Wildflower server paused", replacing the last one rather than
   stacking.
4. Background the app with no task simulated: shortly before iOS suspends the
   app, "Wildflower server paused" posts, and the server stops.
5. Bring the app back to the foreground: the server runs again, with no stop
   notification for that, and answers.

## Risks

- **Plugin maturity.** First published in April 2026 by one author, about 19k
  lines. It is pinned exactly (`=1.0.1`), patched to our fork's commit. If it
  becomes a liability, the surface `TauriUnitRunner` uses (start, stop, events,
  the Android FGS and the iOS `BGTask`) is small enough to replace.
- **Store review.** Play asks no declaration for a `shortService`. App Store
  needs justification for `processing`/`fetch` background modes.
- **Helios globals.** No slice holds process-global state. Helios's `OnceLock`s
  are immutable caches or per-instance, and it spawns on the current runtime, so
  a second run in the same process is safe. The `ServerUnit` test runs a
  server twice end to end.

## Deliberately not here

- A cap on running servers.
- iOS Live Activity, a desktop tray icon, or updating the FGS notification text
  (the plugin has no API for it).
- OS-service (daemon) mode on desktop.
- Remote push (APNs/FCM). Every notification is local.
- A native error dialog for a failed run: `UnitRunner` retries it every few
  seconds, and its stop notification says why.
