# Wildflower Server — Composition Explanation

## What this package is

`wildflower-server` exports a single, platform-neutral `Layer`:
[`WildflowerServerLive`](../src/index.ts). It composes every slice's
`HttpApi` group (gatekeeper, FHIR resources / public, collector, apps,
tunnel admin, vendor-apps), the SPA static-file fallback, Swagger
docs, and the CORS + cookie-stripping middleware into one runnable
server Layer.

The package owns the API shape and the security posture. It does **not**
own the platform binding (HTTP transport, file system, store handles,
telemetry, tunnel control). Those services are required _peers_ — a
host app ([`wildflower-node`](../../wildflower-node/src/index.ts),
[`wildflower-expo`](../../wildflower-expo/src/daemons/http-server.ts))
supplies them.

## The host's job

A host is a thin Layer composer. Its single responsibility is to
satisfy `WildflowerServerLive`'s peer requirements with implementations
that fit its runtime, then launch the result. The two existing hosts
share their composition shape because the contract is identical; only
the Lives and the launch mechanic differ.

### Transport + filesystem

- `HttpServer.HttpServer` — the TCP/HTTP binding the API runs on. Node: `NodeHttpServer.layer`. Expo: `ExpoHttpServer.layer({ port })` (from `expo-effect-platform`, bound to `127.0.0.1`).
- `FileSystem.FileSystem` + `Path.Path` — read static SPA assets, join paths. Node: `NodeFileSystem.layer` + `NodePath.layer`. Expo: both bundled in `ExpoContext.layer`.
- `WebAssetsDir` — absolute path to the SPA bundle directory. Node: `webAssetsDir` from `wildflower-react/web-assets`. Expo: a runtime-staged cache directory holding the inlined SPA HTML.
- `Origin` — the server's local origin (alphanumeric-terminated). Node: from the `ORIGIN` env var. Expo: hardcoded `http://127.0.0.1:<PORT>` — the public origin is owned separately by `TunnelStore`, not bound to this Tag.

### Cross-cutting platform services

- `CryptoRandom` — token + nonce entropy. Both hosts use `cryptoRandomLayerFromWebCrypto(globalThis.crypto)`.
- `Telemetry` — OTEL + Sentry wiring. Node: `nodeTelemetryLayerFromEnv`. Expo: `reactNativeTelemetryLayerFromEnv`.

### Slice stores (all projections of one LiveStore handle)

The six slice-store layers must all close over the **same** `Store`.
Building them from a fresh store per slice would split the database
into six.

- `GatekeeperStore` — `GatekeeperStore.layerFrom(store)`.
- `AppsStore` — `AppsStore.layerFrom(store)`.
- `CollectorStore` — `CollectorStore.layerFrom(store)`.
- `EmrStore` — `EmrStore.layerFrom(store)`.
- `LocalHttpServerStore` — `LocalHttpServerStore.layerFrom(store)`.
- `TunnelStore` — `TunnelStore.layerFrom(store)`.

The `*Store.layerFrom(store)` factory is generated by each slice's
`defineSliceLivestore` call ([`shared-structures-core/livestore`](../../../slices/shared-structures/shared-structures-core/src/livestore));
the returned Layer satisfies the slice's `Context.Tag` so HTTP handlers
can request `yield* TunnelStore` (etc.) and get a typed Store back.

Adapter differs by host: `@livestore/adapter-node` (filesystem) for
the node host, `@livestore/adapter-expo` (expo-sqlite) for the Expo
host.

### Tunnel

The tunnel is **not** a `WildflowerServerLive` peer — it's a separate,
forked daemon that shares the same `TunnelStore`.

The `TunnelDaemon` Layer (exported from
[`tunnel-node`](../../../slices/tunnel/tunnel-node/src/startTunnel.ts)
and [`tunnel-expo`](../../../slices/tunnel/tunnel-expo/src/startTunnel.ts))
is `Layer.scopedDiscard(Effect.forkScoped(runTunnelDaemon(startTunnel)))`.
The daemon watches `TunnelConfig.requestedRunning` and forks the
adapter-specific `startTunnel` Stream into a sub-scope; it writes
`TunnelState.{running, currentSubdomain, currentRootDomain, error}` as
the relay responds.

apps-core's `LaunchApp` HTTP handler reads `TunnelStore` directly to
decide tunnel vs local-origin redirects — there's no `TunnelControl`
Tag, no `PublicOrigin` Tag, no synchronous `setTunnelActive` call. The
HTTP layer commits intent (`TunnelConfig.requestedRunning`); the
daemon honours it asynchronously.

## Layer graph

`WildflowerServerLive` from `wildflower-server` resolves to:

```text
WildflowerServerLive
├── HttpApiBuilder.serve(middleware)         ← CORS + cookie-strip
├── HttpApiSwagger.layer()
├── WildflowerHttpApiLive                    ← 8 HttpApi groups
│   ├── GatekeeperApiHandlersFor             (needs: GatekeeperStore, CryptoRandom, Origin)
│   ├── FhirResourcesApiHandlersFor          (needs: EmrStore + RequireAuth)
│   ├── FhirPublicApiHandlersFor             (needs: EmrStore)
│   ├── CollectorApiHandlersFor              (needs: CollectorStore + RequireAuth)
│   ├── AppsApiHandlersFor                   (needs: AppsStore, TunnelStore, LocalHttpServerStore)
│   ├── AppsAdminApiHandlersFor              (needs: AppsStore + RequireAuth)
│   ├── TunnelAdminApiHandlersFor            (needs: TunnelStore + RequireAuth)
│   ├── VendorAppsApiHandlersFor             (static, base64-encoded assets)
│   ├── RequireAuthMiddlewareLive            (needs: GatekeeperStore)
│   └── SmartConfigurationLive               (needs: Origin)
└── StaticSpaLive                            (needs: WebAssetsDir, FileSystem, Path)
```

Hosts compose `WildflowerServerLive` against the platform peers and
fork `TunnelDaemon` alongside. Node does both in one `Layer.launch`:

```text
FullServerLive = Layer.mergeAll(WildflowerServerLive, NodeTunnelDaemon)
                   |> Layer.provide(Layer.mergeAll(...platform peers + six slice stores))

run = Effect.gen(function* () { yield* Layer.launch(FullServerLive) })
```

## Boot sequence

The Layer graph is declarative — Effect resolves it bottom-up — but
the host's `Effect.gen` _before_ the Layer launch has a real ordering:

1. **Open the LiveStore** (`createStore` / `useStore`). Single shared
   handle.
2. **Build the gatekeeper store layer.** Needed by the seeds below.
3. **Seed signing key.** Idempotent. Without it gatekeeper can't sign
   anything.
4. **Seed the first-party `wildflower-host` client.** Idempotent. The
   identity tokens for this host are minted against it.
5. **Mint a bootstrap host-owner token.**
   - Node (dev only): log the token at startup so a developer can
     paste it into the SPA without going through the device flow.
     Production node hosts use the device flow.
   - Expo: the device IS the owner — always mint, log a partial token
     for the local dev console.
6. **Compose `FullServerLive`** by providing every peer above to
   `WildflowerServerLive` (and, for node, merging `TunnelDaemon` in).
7. **Launch.** Node: `Layer.launch(FullServerLive)`. Expo:
   `Layer.launch(Layer.mergeAll(HttpServerDaemonLive, TunnelDaemon))`
   inside a React `useEffect`. The HTTP-server slot is itself a
   `runHttpServerDaemon`-wrapped Layer that forks the build into a
   sub-scope each time `LocalHttpServerState.requestedRunning` flips
   on. Steps 1–5 (telemetry inject, seeds, mint, asset staging) run
   once inside `HttpServerDaemonLive`'s scope opener, before the
   watcher fiber is forked — so the daemon's internal respawn loop
   doesn't re-seed or re-mint.

## Notes for the Expo mirror

The Expo host's composition mirrors the node host section-for-section,
with two structural differences imposed by the Expo runtime.

**The HTTP server can stop and start mid-session.** The Expo host
delegates server lifecycle to
[`runHttpServerDaemon`](../../../slices/local-http-server/local-http-server-core/src/daemon/index.ts)
from `local-http-server-core`. The daemon watches
`LocalHttpServerState.requestedRunning` and forks a `startServer`
Stream into a sub-scope; the first stream emit is the "ready" signal,
after which the stream parks until the sub-scope closes. The host
provides the `startServer` callback that builds `FullServerLive` under
`Effect.scoped(Layer.build(...))`.

**The tunnel daemon runs alongside the HTTP server, under one
`Layer.launch`.** The Expo host mirrors node's
`Layer.mergeAll(WildflowerServerLive, NodeTunnelDaemon)` shape: it
composes `Layer.mergeAll(HttpServerDaemonLive, TunnelDaemon)` and
launches that once. The user-toggle-driven start/stop machinery is
inside `runHttpServerDaemon`, not in the outer Scope — so merging at
the outer layer doesn't couple the HTTP server's per-bind lifetime to
the tunnel daemon's. The only Expo-specific divergence is **where the
launch is triggered**: a `useEffect` in
[`app-livestore-provider.tsx`](../../wildflower-expo/src/components/app-livestore-provider.tsx)
forks `Layer.launch(...)` once the store handle is available, with
`Fiber.interrupt` cleanup so React's mount semantics drive scope
lifetime cleanly (and StrictMode is handled by the standard cleanup
contract).

Other Expo-side substitutions:

- **`FileSystem` + `Path`** come bundled in `ExpoContext.layer`, not
  as two separate layers. Provide that one instead.
- **LiveStore adapter** is `@livestore/adapter-expo` (SQLite via
  `expo-sqlite`).
- **`Origin`** is the loopback URL (`http://127.0.0.1:<PORT>`). The
  public origin lives in `TunnelStore` only — read it via
  `TunnelState.queries.current$` (`currentSubdomain` +
  `currentRootDomain`) and compose `https://{sub}.{root}` at the call
  site, or fall back to the local origin when the tunnel is down.
- **Bootstrap token**: the Expo host mints one on every launch and
  commits it into `gatekeeper-core`'s `BootstrapToken` clientDocument;
  `HomeScreen` `useQuery`s the row and passes the token to
  `<AppShellWebView>`, closing the auth loop on first load without a
  device-code round trip. The row is session-scoped, so a fresh boot
  always mints fresh — token persistence via `expo-secure-store`
  remains a planned follow-up.

## When this doc is wrong

- A slice gains or loses an `HttpApiGroup`, or changes which
  middleware it requires.
- A new top-level peer requirement appears on `WildflowerServerLive`
  (look for added `Layer.provide` calls in a host that aren't covered
  here).
- A `*Store.layerFrom(store)` factory's signature changes shape (it
  no longer takes the shared `Store`, or returns a different Tag).
- The `TunnelDaemon` Layer or `runTunnelDaemon` contract changes shape.

Update the requirements table and the layer graph; the boot-sequence
section is more stable but worth re-reading if seeds shift.
