# Spike: axum → OpenAPI → Effect schemas (gatekeeper OAuth)

**Status:** throwaway prototype (lives outside the pnpm workspace; not built/tested by `vp`).
**Question it answers:** *Can we generate an OpenAPI spec from the axum servers and use it to generate TypeScript Effect clients?*
**Verdict in one line:** the **schema** half works well today with [`openapi-to-effect`](https://github.com/fortanix/openapi-to-effect); the **endpoint + client** half is still hand-written — and doing this for real immediately surfaces genuine Rust↔TS drift.

This spike targets the **gatekeeper** slice's OAuth surface because it is the richest one (discriminated unions, optional fields, form-urlencoded bodies, multiple error statuses).

---

## The pipeline

```text
slices/gatekeeper/gatekeeper-rust/src/http/handlers/oauth/*.rs   (source of truth: serde structs/enums)
        │
        │  utoipa + utoipa-axum  (#[utoipa::path] + #[derive(ToSchema)])      ← NOT done here; see note
        ▼
gatekeeper-oauth.openapi.json   (OpenAPI 3.1)                                 ← hand-authored stand-in
        │
        │  openapi-to-effect gen                                              ← the real tool, run for real
        ▼
generated/*.ts                  (Effect `Schema.*` definitions, 16 files)    ← machine-generated, verbatim
        │
        │  hand-written wiring                                                ← remaining-wiring/oauth-api.ts
        ▼
HttpApiGroup / HttpApiEndpoint  →  HttpApiClient.make(...)                    ← same as today
```

Per the decision when this spike was scoped, the **axum → OpenAPI** step is *hand-authored* rather than wired with `utoipa` for real (that would mean adding Rust deps and annotating every handler — real scope). `gatekeeper-oauth.openapi.json` is written to match what `utoipa`/`utoipa-axum` would emit from the Rust types, with each schema's `description` pointing at its Rust origin. The **OpenAPI → Effect schemas** step uses the real tool.

## Reproduce

```bash
# openapi-to-effect's formatter pass needs these two (it shells out to prettier
# + the jsdoc plugin); install them somewhere throwaway, NOT in this repo.
cd /tmp && mkdir -p o2e && cd o2e && npm install --no-save prettier prettier-plugin-jsdoc

# generate (paths are absolute so the repo's package files stay untouched)
npx --yes openapi-to-effect@latest gen \
  <repo>/spikes/openapi-to-effect-gatekeeper/gatekeeper-oauth.openapi.json \
  <repo>/spikes/openapi-to-effect-gatekeeper/generated
```

Versions used: `openapi-to-effect@0.9.3` (Nov 2025), Node 22. The repo targets
`effect@3.21.2` / `@effect/platform@0.96.0`; the generated code imports from the
unified `effect` package, so it is on the right major.

## What was generated vs. what stayed manual

| Concern | Generated by `openapi-to-effect`? | Where |
| --- | --- | --- |
| Response body shapes (`TokenResponse`, `DeviceAuthorizationResponse`, `Jwks`, …) | ✅ | `generated/` |
| Discriminated unions (`AuthorizationStatus`, `TokenRequest`) | ✅ as `Schema.Union` of literal-tagged members | `generated/` |
| Error body shapes (`OAuthError`, `AuthorizationRequestNotFound`) | ✅ | `generated/` |
| String constraints (`minLength`/`maxLength` on `code_verifier`) | ✅ `pipe(S.String, S.minLength(43), S.maxLength(128))` | `generated/AuthorizationCodeTokenRequest.ts` |
| HTTP method + path + operationId per endpoint | ❌ | `remaining-wiring/oauth-api.ts` |
| **Query / path parameters** (the `/authorize` query, `/authorize/:id` path) | ❌ — only `components/schemas` are walked | `remaining-wiring/oauth-api.ts` |
| **Form-urlencoded encoding** on the token payloads | ❌ — generated structs are plain JSON shapes | `remaining-wiring/oauth-api.ts` |
| Per-status error mapping (`.addError(schema, { status })`) | ❌ | `remaining-wiring/oauth-api.ts` |
| `text/html` success on `/authorize` | ❌ | `remaining-wiring/oauth-api.ts` |
| `HttpApiClient` | ❌ (derived from the assembled `HttpApi`, unchanged from today) | n/a |

So `openapi-to-effect` covers the **schema** layer cleanly, which is most of the
tedious, drift-prone typing — but **not** the `HttpApi` endpoint/transport layer.
That endpoint layer is exactly what `@effect/openapi-generator` (the official
v4-beta tool) aims to generate; it is not usable on this Effect-3 codebase yet.

## The payoff: drift this surfaces immediately

Authoring the spec from the **Rust source of truth** and diffing the generated
schemas against the current hand-written
`slices/gatekeeper/gatekeeper-core/src/http-api-definition/oauth.ts` exposed four
real divergences — two of them functional gaps in the TS client:

1. **`refresh_token` is missing from the TS token response.**
   Rust `internal.rs::TokenResponse` serializes `refresh_token` whenever the
   grant carries `offline_access` (`token_exchange.rs` sets it on the
   authorization-code and refresh-token paths). The generated
   `TokenResponse.ts` has `refresh_token: S.optional(S.String)`. The current
   `TokenResponseSchema` in `oauth.ts` **has no such field** — a client decoding
   with it silently drops the rotated refresh token.

2. **The `refresh_token` grant is missing from the TS request union.**
   Rust `token_exchange.rs::TokenPayload` is a 3-variant enum:
   `authorization_code`, `device_code`, **and `refresh_token`**. The generated
   `TokenRequest.ts` is a `Schema.Union` of all three. The current
   `TokenExchangePayloadSchema` is a union of only the first two — so the TS
   client cannot perform a refresh-token exchange the server supports.

3. **`AuthorizationStatus.denied` carries an optional `redirect` in Rust**
   (`#[serde(skip_serializing_if)]`), generated as
   `redirect: S.optional(S.String)`; the TS `denied` member has no `redirect`.

4. **Precision *regression* on `OAuthError` (the honest caveat).**
   The Rust `OAuthError.error` field is typed `String` (its values come from the
   closed `OAuthErrorCode` enum in `error_codes.rs`, but that enum is not on the
   serialized type). So a faithful utoipa spec → generated schema gives
   `error: S.String`. The hand-written TS deliberately narrowed this to literal
   unions (`Schema.Literal('invalid_request', …)`). **Codegen from the Rust
   types as they stand today would *lose* that precision** unless the Rust side
   exposes `OAuthErrorCode` via `#[derive(ToSchema)]` and types the field with
   it. This is the clearest example of why "just generate it" isn't free.

Findings 1–3 are precisely the bugs a **generate-and-diff contract test** would
have caught the moment the Rust contract changed.

## Rough edges of the generated output (for honesty)

- **House style differs.** Generated files use `import { Schema as S } from 'effect'`
  and `S.Struct`; the repo convention is `import { Schema } from 'effect'` and
  `Schema.Struct`. They also emit `import { pipe, Option, Schema as S }` even
  when `Option`/`pipe` are unused — `oxlint` would flag the unused imports. A
  real adoption needs a post-generation lint/format pass (or accepting generated
  style inside a quarantined, lint-ignored directory).
- **No barrel/index** is produced; each schema is its own file. (`openapi-to-effect`
  can bundle into one file via a spec config if preferred.)
- **`nullable` vs `optional`.** The repo's `patient` uses
  `Schema.NullishOr(...).optionalWith({ default: () => undefined })`; the
  generator produces `S.optional(S.String)`. Close, but the null-handling /
  default semantics are a hand-tuning point, driven by how the spec models the
  field (`required` vs `type: [..., "null"]`).
- **`additionalProperties: true`** became `S.Record({ key: S.String, value: S.Unknown })`
  (see `generated/JsonWebKey.ts`) — reasonable, but worth a look for opaque
  blobs like JWKs.

---

## Bottom line

- **axum → OpenAPI:** feasible and mechanical with `utoipa`/`utoipa-axum`
  (the cost is annotating handlers + `ToSchema` on DTOs; not done here).
- **OpenAPI → Effect schemas:** works well *today* with `openapi-to-effect` on
  the repo's Effect 3, modulo a house-style/lint pass.
- **OpenAPI → Effect *client*:** still manual — `openapi-to-effect` stops at
  schemas; the endpoint/transport/client layer is hand-written (the official
  `@effect/openapi-generator` that would close this gap is Effect-v4-beta only).
- **Highest-value near-term use:** generate the spec from axum and **diff** it
  against the spec the existing Effect `HttpApi` already emits for free
  (`OpenApi.fromApi`) as a CI contract test — it catches drift findings 1–3
  above without committing to full client codegen.
