### Framework-minted per-run ids beat per-factory minting: sealing the id with the plan makes "one build = one run" structural

**Discovered during**: claude/issue-439-collector-provenance — reworking PR #453's provenance seams after review
**Learning**: The first cut had each collector's plan factory mint its own run/session uuid, which made three factories impure, forced three test files onto identity-projection comparisons, and rested "one plan build is one run" on an unenforced calling convention. Moving the mint to the single dispatch point (`resourcePersistenceRuntimeIfMatches`) and widening the factory to `(config, runId)` inverted all of that: the factories are deterministic given inputs, the invariant is enforced by construction (the runtime seals the plan and its id together), and tests deep-equal plans against a fixed id. The general shape: when several components each mint a "fresh per X" identity, look for the one seam where X is created and mint there — the impurity concentrates into one place and everything downstream becomes a pure function of the id. Two supporting facts made the test reverts work: `toEqual` compares functions by reference, so any function-valued plan field (entities, hooks) must be a **module-level singleton**, never built inside the factory; and a per-build entity **closure** (the recorder's) still defeats deep equality even with a fixed id, so the projection legitimately survives exactly there.
**Suggested destination**: Strategies.md, or the plan-determinism trap in `slices/collector/AGENTS.md` (already updated on this branch)

### A plan factory that is legitimately impure breaks a registry test that deep-equals plans

**Discovered during**: claude/issue-436-draft-pr-2nu428 — `web-trace-collector` minting a session id per plan build
**Learning**: `collector-registry`'s dispatch property test asserted `planFor(config)` deep-equals the descriptor's own `makeScrapingPlan(config)`, with the comment "the plan factory is per-config so structural equality stands in for identity". That premise held only while every collector's plan was a pure function of config. A recording collector must mint a fresh session id per _run_ (a config-derived id would make the second recording of a remote silently upsert over the first), and `makeScrapingPlan` is called exactly once per sync run — so the mint belongs there, and two builds from one config are unequal by construction. Two separate things break the equality, not one: the session id itself, and the fact that a per-build entity factory produces a fresh `parse` **closure** each time (`toEqual` compares functions by reference), so even a deterministic id would not have saved it. The fix is to compare an identity _projection_ — name, `firstPage`, step names, entity names — which still fails loudly on a mis-dispatch (a plan from the wrong descriptor differs in all four) without asserting a purity the interface never promised. Worth knowing before adding any collector whose plan carries per-run state.
**Suggested destination**: Strategies.md (test-premise drift), or the `collector-registry` notes in `slices/collector/AGENTS.md`

## Workspace-wide `vp test` needs `vp run pack` first in a fresh container — unbuilt `dist/` fails hundreds of tests

**Discovered during**: claude/fhir-r4-openapi-spec-ibzynx — a full `vp test` showed 438 failures that had nothing to do with the change
**Learning**: Workspace packages' `exports` map `default` to `./dist/...`; only the `source` condition points at `src/`. Vitest resolves `source` for files _inside_ the project under test, but cross-package imports in some projects resolve to `dist/`, so on a fresh container (post `vp install`, nothing built) a workspace-wide `vp test` fails en masse with `Cannot find module .../dist/...` while any single package's suite (run from its directory) passes. Run `vp run pack` once first; after that the full suite is green. Corollary: a plain `node script.ts` importing a workspace package fails the same way — run one-off scripts as a temp test file through `vp test` instead.
**Suggested destination**: CLAUDE.md commands section, or docs/Testing/Testing Reference.md

## Re-driving `hfs_router` in-process: strip `Accept-Encoding` or the delegated sub-response comes back compressed and won't parse

**Discovered during**: claude/fhir-patient-everything-op-95ig70 — debugging a `$everything` 500 (`failed to parse sub-response JSON: expected value at line 1 column 1`)
**Learning**: `emr-rust`'s `$everything` handler (`patient_everything.rs`) delegates data-fetching by re-driving a clone of HFS's own router in-process (`router.clone().oneshot(sub_request)`), forwarding the caller's headers so auth/tenant resolution matches a direct request. But `helios-rest`'s `create_app_with_auth` wraps the router in a `CompressionLayer` (`compress_when(SizeAbove::new(32) & NotForContentType(parquet/zip))`) — so forwarding the real client's `Accept-Encoding: gzip, deflate, br` makes HFS gzip the sub-response body. The sub-request still returns **200**; the body is just compressed, so `serde_json::from_slice` fails at the first byte (`expected value at line 1 column 1` — column **1**, not 0, is the tell: non-empty body, invalid first byte = the `0x1f` gzip magic). Tests passed because their request helper never set `Accept-Encoding`. Fix: skip `header::ACCEPT_ENCODING` when copying headers into the sub-request — we consume the body in-process, not over the wire, so we always want it identity-encoded; the real client's `Accept-Encoding` is honored by the outer HTTP stack against our own response. General rule: any in-process `oneshot` re-drive of a router that carries a compression/content-negotiation layer must drop hop-by-hop / transfer-encoding-negotiation headers (`Accept-Encoding` first) from the forwarded set.
**Suggested destination**: unsure — a note near the `patient_everything.rs` module docs, or an emr-rust delegation how-to if one emerges

## `.local-notes` design-handoff HTML is a self-extracting bundle — the real markup lives in `__bundler/template` + `__dc_inline` JSON

**Discovered during**: claude/issue-256-implementation-ohs995 — matching the OAuth consent screen to the Scope Picker reference design
**Learning**: The standalone design files (e.g. `.local-notes/Scope Picker (standalone).html`, ~1.1MB) are not readable HTML — they're a JS bundler shell whose page is JSON-encoded in a `<script type="__bundler/template">` tag. Extract with a small node script (regex the tag, `JSON.parse`), then split again: the decoded page holds a `<script type="application/json" id="__dc_inline">` map of named sub-component templates (`PermissionStatement`, `FlagToggleRow`, …) plus the main page after the `</helmet>` (the helmet is a full inlined Tundra CSS copy — skip it). Each component is a mustache-ish `<x-dc>` template + a `DCLogic` class carrying the interaction model (state machine, serialization rules) — the class is worth reading, it specifies behavior, not just looks. The templates use the repo's real CSS custom properties (`--color-raised`, `--space-*`), so styles translate almost 1:1 to token-driven CSS modules.
**Suggested destination**: unsure (design-handoff how-to, if one emerges)

## Vite+ 0.2 upgrade: peer deps dodge `pnpm.overrides`; every plugin-hosting package must declare `vite: catalog:`; the vitest alias line is dead

**Discovered during**: vite-plus 0.1.21 → 0.2.2 / @vitejs/plugin-react 5 → 6 upgrade
**Learning**: Three coupled traps. (1) `pnpm.overrides` rewrites regular/dev/transitive deps but **not peer resolution** — a `vite` peer (`@vitejs/plugin-react`, `@tanstack/router-plugin`, `vite-plugin-singlefile`) binds to whatever `vite` the host package's own tree provides, and with `autoInstallPeers` an unprovided peer pulls **real** `vite@8` from the registry. With `nodeLinker: hoisted` that real vite wins the root `node_modules/vite` slot and every `defineConfig`/plugin call typechecks against mismatched `Plugin`/`UserConfig` types ("Excessive stack depth", "No overload matches"). Fix: every package that hosts a vite plugin declares `"vite": "catalog:"` (the catalog aliases it to `@voidzero-dev/vite-plus-core`), same as `wildflower-tauri` always did; the `pnpm.overrides` pin still matters for regular deps like vitest's own `vite` dependency. Verify with `vp why -r vite` — real `vite@x.y.z` should have zero dependents. (2) vite-plus 0.2.x depends on **real `vitest`** — the `@voidzero-dev/vite-plus-test` alias line ended at 0.1.24, so bumping the old catalog alias to `^0.2.2` is unsatisfiable (`ERR_PNPM_NO_MATCHING_VERSION`); pin `vitest` to the version `vp --version` reports instead. (3) The core alias ships **no `vite` bin** — `"dev": "vite"` scripts only ever worked via the accidentally-installed real vite (a stale `node_modules/.bin/vite` symlink); scripts must use `vp dev` / `vp build` / `vp preview`.
**Suggested destination**: docs/Dependencies/Version Override Explanation.md (partially applied this session) / Strategies.md

## rathole's `"Unable to listen for shutdown signal: channel closed"` is a teardown symptom, not a cause

**Discovered during**: claude/pr-202-tunnel-seam — debugging tunnel launch flap
**Learning**: We build `rathole` with `default-features = false` (no `notify`/`hot-reload`), so rathole's config watcher is the stub variant that does nothing but `await` the `broadcast::Receiver<bool>` shutdown we hand `rathole::run(cli, shutdown_rx)`. rathole's `run()` therefore ends — tearing down the control channel and logging `"Unable to listen for shutdown signal: channel closed"` from `client.run` — the instant **our** `shutdown_tx` drops, which happens when the supervisor's `run_once` future is dropped on cancel. So that error means "the supervisor got cancelled," i.e. a reconcile cancelled it — chase _what issued the reconcile_, not the rathole error. Confirmed by logging which `select!` branch `run_once` takes (`cancel.cancelled()` fired). The verify-deadline-too-tight theory was a red herring: the tunnel verifies in ~1s; it's the flap (cancel → re-dial) that breaks launches.
**Suggested destination**: unsure (tunnel-rust relay_clients/rathole.rs context)

## `reconcile` must not re-dial a live tunnel on a no-op settings revision bump

**Discovered during**: claude/pr-202-tunnel-seam — tunnel flap fix
**Learning**: Any newer settings revision made the tunnel daemon's `reconcile` cancel the live supervisor and re-dial from scratch — even when the _dialable_ config (relay + public_host) was unchanged. That tears rathole down (drops in-flight requests, flaps the public origin) on every redundant write (a settings re-save, a `requestedRunning` re-assert). Fix: `SupervisorHandle` carries the `relay_settings`/`public_host` it's driving; `reconcile` returns early (keeps the live tunnel) when the incoming revision is still `requested_running` with the same relay + host. The persisted/wire revision still advances (the `/tunnel` response reads it from the DB settings, not the watch), so leaving the watch's `settings_revision` at the supervisor's value is correct and keeps its `set_state` supersession check intact.
**Suggested destination**: unsure (tunnel-rust domain/tunnel_daemon.rs context)

## Cross-language (TS/Rust) semantics contract via a shared JSON fixture at the slice root

**Discovered during**: claude/core-ui-events-4crpo0 — review follow-ups pinning the scopes-core ↔ scopes-rust grammar mirror
**Learning**: When the same domain grammar is implemented twice (TS `scopes-core` + Rust `scopes-rust`), prose "mirrors scopes-rust" doc comments don't stop drift — a shared vector file does. Pattern: put the fixture at the slice root (`slices/scopes/scope-test-vectors.json`), consume it from Rust with `include_str!(concat!(env!("CARGO_MANIFEST_DIR"), "/../scope-test-vectors.json"))` in a `tests/*.rs` integration test (parse with `serde_json::Value` — no derive needed, so no serde `derive` feature question), and from TS with a plain `import vectors from '../../scope-test-vectors.json'` (works fine outside the tsconfig `include` seed; `resolveJsonModule` is already on repo-wide). Encode both parse cases (`scope → kind + canonical rendering`) and semantics cases (`allowed/requested → covers`). Where the two sides partition differently (TS splits fhirV1/fhirV2, Rust has one FhirResource variant), keep the finer-grained kind in the fixture and coarsen in the Rust consumer's match. Gotcha: root `vp check` formats JSON files too — run `vp check --fix` after authoring the fixture or the root check fails on formatting.
**Suggested destination**: docs/Testing/Testing Reference.md (cross-language contract tests)

## oxfmt parses `.hbs` files as markup — exclude served template trees from `fmt` or `vp check` fails before analysis

**Discovered during**: claude/handlebars-static-app-templates-2ia3yl — adding the handlebars template tree to self-hosted-apps-rust
**Learning**: oxfmt (the `vp check`/pre-commit formatter) treats `*.hbs` as an HTML-ish template language and hard-fails on non-markup content before any analysis starts — e.g. a json5 comment containing `<public_host>` reads as an "Unclosed element" SyntaxError, killing the whole `vp check` run (and with it `vp staged` in the pre-commit hook). Even when it parses, reformatting would mangle `{{…}}` expressions and the json5 payload they render into. Fix: add the template tree (`slices/apps/self-hosted-apps-rust/templates/**`) to `fmt.ignorePatterns` in the root `vite.config.ts` — these are served runtime assets, not source. Same reasoning as the existing `**/openapi/*.openapi.json` and `**/*.toml` exclusions.
**Suggested destination**: unsure (vite.config.ts fmt commentary already carries it)

## Pre-commit "Task killed: vp check --fix" usually means a SIBLING staged task failed (e.g. cargo fmt --check)

**Discovered during**: claude/self-hosted-apps-rust-design-t4teg2 — apps-rust domain refactor
**Learning**: `vp staged` (the pre-commit hook) runs its per-glob tasks concurrently and, when one fails, kills the others — the summary line then reads `✖ Task killed: vp check --fix`, which points at the _victim_, not the culprit. When Rust files are staged, the real failure is usually `rust.sh pre-commit`'s `cargo fmt --check` printing "Diff in …" blocks further up the output (hand-written Rust that isn't rustfmt-clean). Standalone `node_modules/.bin/vp check --fix` passing while the hook keeps failing is the tell. Fix: run `cargo fmt`, restage, and commit; scroll up past the kill line for the actual diffs. Two side gotchas from the same session: (1) `vp check --fix` run standalone can reformat files _after_ you staged them, so restage before retrying; (2) don't run a background `cargo check` concurrently with a commit — the hook's rust.sh contends on the cargo target lock.
**Suggested destination**: CONTRIBUTING.md git-hooks section (or the Vite+ block in AGENTS.md)

## `Equal.equals` silently degrades to reference equality on classes that don't implement `Equal` — check before adopting it

**Discovered during**: claude/issue-256-implementation-ohs995 — consent-screen refactor moving scope editing onto domain objects
**Learning**: Effect's `Equal.equals(a, b)` never fails on a class that doesn't implement `Equal.Equal` — it falls back to reference equality and returns `false` for two structurally identical instances. In `scopes-core` the domain classes implement `[Equal.symbol]`/`[Hash.symbol]` selectively: `KnownScope`, the contexts (via the `Context` base), and the resource types did, but `UnknownScope` did not — so a draft-membership check like `draft.unknown.some(Equal.equals(scope))` type-checked, looked idiomatic, and always returned `false` (parsed instances are never reference-equal), turning a toggle into an append-duplicates bug. Before writing `Equal.equals` against a domain class, verify the class (or its base) implements `Equal.Equal`; when adding a new sibling variant to a family where the others are value-comparable, implement `Equal`/`Hash` at the same time (compare `kind` + payload, mirror the sibling's shape). The fix belongs in the domain class, not at the call site — serialize-and-compare call sites are the workaround smell.
**Suggested destination**: docs/Effect/Patterns Reference.md (value equality on domain classes)

## `Schema.declare` combinators need `arbitrary` AND `equivalence` annotations before tests can generate/compare through them

**Discovered during**: claude/emr-fhir-r4-migration-5lh030 — deleting emr-core and porting fhir-r4 schema tests to generate from the wire schemas
**Learning**: A `Schema.declare(...)`-based combinator (kitchen-sink's `OrNullAsOptional`/`OrNullAsUndefined`, fhir-r4's choice-slot null stub) derives nothing: `Arbitrary.make` throws `MissingAnnotation` and `Schema.equivalence` silently falls back to reference equality, so `toSchemaEqual` reports "Values are not schema-equivalent … no visual difference" for structurally identical values. This stayed hidden for as long as tests generated/compared via the plain-Struct emr-core row schemas; the moment the wire schemas became the only schema tree, every property test failed at once. Fix at the combinator, not per call-site: `.annotations({ arbitrary: (inner) => (fc) => fc.oneof(fc.constant(null), inner(fc)), equivalence: (inner) => (a, b) => a === null || b === null ? a === b : inner(a, b) })` — declaration annotations receive the type-parameters' derived arbitraries/equivalences as arguments. Rule of thumb: any new `Schema.declare` that will appear inside property-tested schemas ships with `arbitrary` + `equivalence` annotations from day one.
**Suggested destination**: docs/Effect/Patterns Reference.md (Schema.declare checklist) or docs/Testing/Property Testing Reference.md

## Building schemas from another package's reused datatypes breaks `vp pack`'s dts (TS2883) — the producer must export the named interfaces at top level

**Discovered during**: claude/github-issue-335-2lac0i — the new `fhir-stu3-as-r4` slice (and `rexall-be-well-collector`) reuse `fhir-r4/data-types` schemas
**Learning**: When a package builds new Effect `Schema.Struct`s that spread/reference another package's datatype schemas (e.g. `...DomainResource.fields`, `Extension.Schema`), the struct's _inferred_ decoded type embeds that package's named interfaces (`ExtensionType`, `ReferenceType`, `IdentifierType`). If the producer only exposes them through a namespace re-export (`export * as Extension` + `type ExtensionType as Type` → `Extension.Type`), `tsgo`'s declaration emit can't map the raw interface back to that path and `vp pack` fails with TS2883 ("cannot be named without a reference to 'ExtensionType'") — even though `vp check` (typecheck only) stays green, because the leak only bites at `.d.ts` generation. The clean fix is on the _producer_ side: add a direct top-level re-export of each named interface (`export type { Type as ExtensionType } from './…/extension.ts'`, `export type { ReferenceType, IdentifierType } from './…/identifier-and-reference.ts'` in `data-types/index.ts`). With a top-level name to reference, the consumer's plain `typeof Struct.Type` / `typeof Struct.Encoded` annotations pack cleanly — no hand-written wire interfaces needed. (Hand-rolling explicit `Type`/`Encoded` interfaces in the consumer also works but is far more code, and forces you to also _export_ every `Encoded` interface or a Bundle/wrapper referencing them fails with TS4023.) The same bite recurs for _wrapper/factory_ return types: `rexall-be-well-collector` calling `Bundle.searchsetBundle(...)` embeds `BundleValue` from `fhir-r4`'s `resources/bundle.ts`, so that too now has a top-level re-export (`export type { BundleValue } from './resources/bundle.ts'` in `data-types/index.ts`) — whenever a consumer's inferred type names an internal interface, re-export it flat from the producer. `vp check` won't catch any of this; run `vp pack` on the consuming package.
**Suggested destination**: docs/Testing or a slices/emr dts how-to; relevant to any slice reusing `fhir-r4` schemas

## `EntityDefinition.parse` only ever saw what a _decoding_ entity needs — a _recording_ one needed three additions to `RemoteResponse`

**Discovered during**: claude/issue-436-draft-pr-2nu428 — `web-trace-collector`, the first collector that records exchanges instead of decoding payloads out of them
**Learning**: `RemoteResponse` was shaped entirely around entities that recognize a URL and decode a known payload: `url`, `status`, `statusText`, `headers`, `text()`. Every field a _recorder_ needs was either dropped on the floor or unreachable. (1) **The sniffer's correlation `id` was discarded.** `handleResponseStart` has `event.id` in hand — it uses it as the tracker's `MutableHashMap` key — but never passed it to the `RemoteResponse`, so `parse` could not know which request it was looking at. Any storage scheme keyed on request identity (here `{sessionId}-{requestId}`, which is what makes a retried write an idempotent upsert instead of a duplicate) is impossible without it; the alternative, a counter threaded through `parse`, re-derives an id the sniffer already assigned and loses idempotency. (2) **There was no timestamp at all.** `parse` runs at _settle_, so a clock read inside it labels the end of the response as its beginning — the tracker is the only place that knows when `ResponseStart` was observed. (3) **`text()` is lossy and there was no alternative.** `#chunks` is private and the only accessor UTF-8-decodes, so a body that is not valid UTF-8 (an image, a protobuf, an undecoded gzip) comes back peppered with U+FFFD, and a re-encode of that string is not the body that arrived — you cannot base64 it, you cannot hash it, and `byteLength` is the only truthful thing left. A `bytes()` accessor is the fix, and its return type wants pinning to `Uint8Array<ArrayBuffer>` rather than the default `Uint8Array<ArrayBufferLike>`: every platform `BufferSource` parameter (`crypto.subtle.digest`, `Blob`, `fetch`) rejects the latter, so leaving it loose pushes a cast onto every caller. Note `TextEncoder.encode()` and `fc.uint8Array()` both produce the loose form, so tests that build bytes by hand copy through `new Uint8Array(...)` while the production path stays copy-free. The general shape: a seam designed around one consumer silently encodes that consumer's assumptions, and the second consumer's requirements read as "the ticket forgot something" when they are really "the seam was never asked this question".
**Suggested destination**: alongside the `EntityDefinition` / handler docs in `slices/collector/collector-fundamentals`

## jsdom enforces HTML5 constraint validation, so `type="url"` swallows the case your schema test meant to exercise

**Discovered during**: claude/issue-436-draft-pr-2nu428 — the `WebTraceConfigForm` start-URL field
**Learning**: A form test that types a malformed value into an `<input type="url">` and expects the component's own `Schema.decodeUnknownEither` `ParseError` to render inline will fail confusingly: jsdom blocks the submit on the input's constraint validation, so the `onSubmit` handler never runs, no error state is set, and nothing renders. The `expect(onSubmit).not.toHaveBeenCalled()` half of such a test still **passes — for the wrong reason** — which is what makes it confusing; only the "and shows the error" half fails. To exercise the schema rather than the platform, pick a value the input's type accepts but the schema rejects — here `ftp://files.example.com` (a well-formed URL with a scheme the schema forbids) instead of `not-a-url`. Same trap applies to `type="email"`, `type="number"` (`min`/`step`), and anything with `pattern` or `required`.
**Suggested destination**: docs/Testing/React Testing Reference.md — form-validation testing

## A `vite-plus` bump that leaves the exact `vite` override behind reintroduces the two-`UserConfig` type split

**Discovered during**: claude/consolidate-dependabot-prs-1xuhvi — combining Dependabot PRs #457 (js-minor-patch group) and #459 (jsdom 30)
**Learning**: The catalog's `vite-plus` and the root `pnpm.overrides` entry `vite: npm:@voidzero-dev/vite-plus-core@<exact>` are one pin in two places, and only the second one is load-bearing. Bumping the catalog alone (`vite-plus: ^0.2.5` → `^0.2.6`) leaves the override pinning core `0.2.5` while `vite-plus@0.2.6` brings its own core `0.2.6`, so the lockfile carries two `@voidzero-dev/vite-plus-core` entries — exactly the split [Version Override Explanation](../Dependencies/Version%20Override%20Explanation.md) warns about — and every `defineConfig` call fails to typecheck with `TS2321: Excessive stack depth comparing types … and 'UserConfig'` plus a companion `TS2769: No overload matches this call`. Bumping the _catalog range_ to `^0.2.6` does **not** fix it: an exact override outranks the catalog, so `vp install` reports "Lockfile is up to date, resolution step is skipped" and nothing moves. The only fix is editing the override itself. Two things make this expensive to diagnose from the error text alone: the errors name only `vite.config.ts` files (nothing points at a dependency), and they are drowned out if you run `vp lint` before `vp run pack` — an unbuilt workspace adds a pile of `TS2307: Cannot find module '<workspace-pkg>'` noise, because typecheck reads `dist/*.d.ts` via the packages' export maps. Always `vp run pack` first, then treat whatever survives as real. Quickest confirmation of the split, no build needed: `grep -oE "@voidzero-dev/vite-plus-core@[0-9.]+" pnpm-lock.yaml | sort -u` should print exactly one line. The same "re-pin on every bump" duty already applies to the `vitest` override, and by the same reasoning to `react-dom` on a React bump.
**Suggested destination**: already folded into [Version Override Explanation](../Dependencies/Version%20Override%20Explanation.md) as a "Re-pinning on a vite-plus bump" section; the pack-before-lint half of the diagnosis may belong in Strategies.md

## fhir-r4 decodes a `uri` primitive to a `URL` on the fully-typed top level, so naive string-schema re-decode of `medicationCodeableConcept.coding.system` silently fails

**Discovered during**: claude/shoppers-drugmart-collector — adding Shoppers Drug Mart fallbacks (DIN/name/sig) to `medication-sponsorship-react`'s `MedicationRequest → MedicationView` adapter
**Learning**: `medication.ts` re-decodes loosely-typed slots (`medicationCodeableConcept`, `contained`, …) through narrow local `Schema.Struct`s "tolerant of both the wire and decoded shapes." That tolerance was a half-truth: a FHIR `uri` primitive stays a plain string on the wire and on loosely-typed `contained` resources, but the **fully-typed top-level** `MedicationRequest.medicationCodeableConcept.coding[].system` decodes to a `URL` instance (`sys instanceof URL === true`; `JSON.stringify` renders it unquoted). So a `Coding` struct with `system: Schema.String` returns `Option.none()` for the whole concept whenever a top-level coding carries a system — which silently disabled the existing `displayNameOf` coding-`display` fallback and blocked a new DIN-from-`coding[].code` fallback. The asymmetry is the tell: `dinOf` reads the **contained** Medication's `coding.system` and compares it `=== DIN_CODING_SYSTEM` fine (contained stays a string), while the same field on the top-level concept is a `URL`. Fix that keeps types clean and honours the module's stated intent: a `nullableUri` schema = `Schema.transform(Schema.Union(Schema.String, Schema.instanceOf(URL)), Schema.String, { decode: v => typeof v === 'string' ? v : v.href })`, used for `Coding.system`, so both shapes normalize to the string form and every `=== <system-uri>` comparison keeps working. General rule: when re-decoding an **already-decoded** fhir-r4 resource (not raw wire) through a permissive local schema, `uri`/`url`-typed fields are `URL`s, not strings — either coerce or read them as `Schema.Unknown`. `vp check` (typecheck) won't catch it; only a runtime decode of a resource carrying that field does.
**Suggested destination**: a slices/emr fhir-r4 "re-decoding decoded resources" gotcha doc, alongside the TS2883 dts entry
