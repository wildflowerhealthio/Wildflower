## The collector sniffer must run on a real `http(s)` origin — `about:blank` has a null origin that Tauri IPC rejects, so build the sniffer directly on the target via a one-shot `Start` input, never a blank pre-mount

**Discovered during**: claude/shoppers-drugmart-collector-o2lbac — FHIR collector hung; the sniffer webview's own devtools console showed `native_webview_data_plane_emit` → 500 and `plugin:event|listen` → 500
**Learning**: Two independent facts kill the "mount `about:blank`, let its near-instant settle prime the drain" design on macOS/wry. **(1) Null origin.** `about:blank`'s origin is the string `null`, which Tauri's IPC can't parse — so **every** command invoked from an `about:blank` page is rejected: `native_webview_data_plane_emit` (the sniffer's Web→Host emit seam) and `plugin:event|listen` (its Host→Web receive seam) both 500 with "Origin header is not a valid URL", and the sniffer logs `bridge emit dropped (bridge): Origin header is not a valid URL`. On `about:blank` the sniffer is deaf and mute — it can neither post the `PageLoaded` the drain waits on nor receive host messages. A `data:`/`WebviewBuilder::with_html` first page has the same null origin, so "just use a real HTML first page" only helps if that page is **served from a real `http(s)` origin**. **(2) Content-process crash.** `about:blank` also terminates the WKWebView content process (two `web content process terminated` lines, both child webviews) with no recovery. **Working shape:** build the sniffer webview **directly on the target URL** (a real origin → IPC works — proven: a sniffer on the https patient page delivered `PageLoaded` and the FSM advanced patient→observations). With no `about:blank` settle to prime the drain, the runner (`collector-react/src/runtime/sync-run.ts`) dispatches a one-shot `Start` input right after registering handlers; `onStart` drains the plan's leading `Open` with **no page in hand** (sound — the leading step is always an `Open`, which needs none) instead of waiting for a first `PageLoaded`. The native-webview `open_url` must still accept `about:blank` for the internal cookie-seed transit — a `WebviewTarget { Http, Blank }` enum + `parse_target` in `plugins/tauri-plugin-native-webview/src/url_scheme.rs` recognises the sentinel in one place rather than an inline `if url == "about:blank"`. **Open issue — a host→SPA delivery race:** on a fast first load the target's single `PageLoaded` can be lost before the SPA is ready to route it (a crash-delayed load delivers it; a clean fast one drops it — the sniffer emit reaches the host log but the FSM's input trace never shows it). The FSM is correct and the coordinator's inbound-dispatch fiber is app-lifetime (gated on the boot `signalReady`, so it's live before any run), which makes the loss subtler than "subscription not up" — still being pinned down.
**Suggested destination**: the `AwaitingPageLoaded` / start-up notes in the Handler Explanation + `slices/collector/AGENTS.md` + a native-webview note that the sniffer can only run on a real `http(s)` origin (null-origin IPC constraint)

## The sniffer's settle (`PageLoaded`) is strictly once-per-document, so a settle-wait can't be a rolling grace — but that's exactly what makes a pattern-less "wait for next settle" safe after an `Open`

**Discovered during**: claude/shoppers-drugmart-collector-o2lbac — replacing the collector `idleTimeout` with a pattern-less `AwaitPageSettled` and an `about:blank` mount
**Learning**: The instinct "replace the rolling `idleTimeout` idle guard with a settle-based wait" is wrong the moment you check the sniffer: `PageLoaded` fires **at most once per document**, guarded by a burned `pageSnapshotEmitted` latch (`browser-sniffer-tauri/src/install-sniffer.ts` ~L761-773, pinned by "should emit a single PageLoaded even if load fires twice"). Late XHR fan-out that starts _after_ a page settled never produces a second settle — settle also already requires network-idle (`activeRequests.size === 0`) + a 1s quiet window, ceiling 10s. So a settle-wait can NOT replace a trailing fixed `Delay` grace (there's no second settle to wait for); the `Delay`s stay. What settle-once _does_ enable: a **pattern-less** `AwaitPageSettled` ("wait for the next settle, ignore the page in hand") is unambiguous right after an `Open`, because the only settle still coming is the freshly-opened page's. Two more load-bearing facts fell out: (1) the FSM start-up state `AwaitingPageLoaded` arms **no timer**, so a dead first page hung forever under the old model — mounting the sniffer on `about:blank` (its near-instant settle primes the drain) and making the old `firstPage` a leading `Open` step converts that unbounded hang into a bounded step-hold, which is what lets `idleTimeout` be removed _entirely_; (2) the residual risk you're accepting is a **stalled tracked request** (sniffer saw `ResponseStart`, no terminal) — the completion gate (queue drained ∧ all requests settled) never trips and, with no idle guard, the run parks until cancel. `abandonAllRequestSniffing` still exists on the handler as the force-close seam a positional backstop would reuse; nothing drives it today.
**Suggested destination**: the `AwaitPageSettled` / completion-gate notes in `slices/collector/AGENTS.md` + the browser-sniffer settle docs (both updated on this branch)

## `about:blank` isn't a mountable `WebViewSource`, so "mount blank, navigate via steps" is a TS⇄Rust wire change, not a config tweak

**Discovered during**: claude/shoppers-drugmart-collector-o2lbac — same task
**Learning**: `WebViewSource.Uri` is schema-restricted to `http(s)://` on **both** sides (TS `HttpUriString` and Rust `resolve_source`, which rejects `NonHttpUri`), and the `Html` variant is a decode-and-drop placeholder that returns `HtmlNotSupported`. So there is no existing way to hand the host a blank starting page. Cleanest realization of "always mount `about:blank`, let the plan's leading `Open` do the first real navigation": **drop the `source` field from `RequestSniffableWebView` entirely** and have the Rust handler mount `WebviewUrl::External(Url::parse("about:blank"))` unconditionally (`url::Url::parse("about:blank")` succeeds; the plugin navigates fine). `Open`'s own `resolve_source` path stays http(s)-only and untouched. It's a bridge wire change — update `collector-fundamentals/bridge.ts`, the Rust payload struct + handler, and the `lib.rs` tag-literal drift assert (the tag _name_ is unchanged, so `events.rs` needs no edit) — but it needed no OpenAPI snapshot regen (the collector bridge isn't the `/collector` HTTP surface). Side effect worth checking: the parallel `useRequestSniffableWebView` hook (mount at an arbitrary source) had **zero callers** and its whole purpose evaporates with the sourceless wire, so it was deleted.
**Suggested destination**: the Wire Pinning How-To, or the browser-sniffer Tauri Host Explanation (mount row updated on this branch)

## Framework-minted per-run ids beat per-factory minting: sealing the id with the plan makes "one build = one run" structural

**Discovered during**: claude/issue-439-collector-provenance — reworking PR #453's provenance seams after review
**Learning**: The first cut had each collector's plan factory mint its own run/session uuid, which made three factories impure, forced three test files onto identity-projection comparisons, and rested "one plan build is one run" on an unenforced calling convention. Moving the mint to the single dispatch point (`resourcePersistenceRuntimeIfMatches`) and widening the factory to `(config, runId)` inverted all of that: the factories are deterministic given inputs, the invariant is enforced by construction (the runtime seals the plan and its id together), and tests deep-equal plans against a fixed id. The general shape: when several components each mint a "fresh per X" identity, look for the one seam where X is created and mint there — the impurity concentrates into one place and everything downstream becomes a pure function of the id. Two supporting facts made the test reverts work: `toEqual` compares functions by reference, so any function-valued plan field (entities, hooks) must be a **module-level singleton**, never built inside the factory; and a per-build entity **closure** (the recorder's) still defeats deep equality even with a fixed id, so the projection legitimately survives exactly there.
**Suggested destination**: Strategies.md, or the plan-determinism trap in `slices/collector/AGENTS.md` (already updated on this branch)

## Collapsing per-interaction bridge tags into one `PageAction` message: the step becomes `{ action; advanceWhen? }`, so plan-only fields can't leak by construction

**Discovered during**: claude/issue-386 — replacing the `Click`/`Fill` bridge tags with a single `PageAction` message family and recomposing `Link`
**Learning**: The earlier "strip `advanceWhen` before verbatim-forwarding a `Link` variant" trick (see the entry below) went away entirely. Two moves did it: (1) `browser-sniffer-core` now declares ONE host→web `PageAction` tag whose payload is `{ action: Schema.Union(ClickAction, FillAction) }`, the actions discriminated by an inner `kind` literal — a new interaction (Scroll/WaitFor/Submit) is a union variant, not a whole new tag + demux + Rust drift-guard + bootstrap-regen rollout. (2) `Link` stopped being `Open | Click | Fill` variants that doubled as wire messages; a step is now `{ readonly action: StepAction; readonly advanceWhen?: Advance }` where `StepAction = typeof OpenMessage.Type | typeof PageActionMessage.Type` (typed against the bridge bodies themselves). The step machine forwards `step.action` untouched, so the plan-only `advanceWhen` lives on the wrapper and _cannot_ reach the wire — no destructure, no "excess prop silently stripped on encode" hazard, and the "does the dispatched payload carry advanceWhen?" test is now a structural guarantee rather than a regression risk. Load-bearing details: the injected sniffer's IIFE can't run runtime schemas, so it hand-demuxes `PageAction` by `action.kind` with `typeof` guards (mirror the existing style); the Rust host still only _forwards_ `PageAction` by `_tag` (no serde mirror — it never decodes the payload), so the drift guard stays the tag-literal `assert_eq!` in `lib.rs` + the TS bridge round-trip property, and `PageAction` is a control tag so it stays OUT of `NATIVE_WEBVIEW_DATA_PLANE_TAGS`. Telemetry `LinkKind` keeps cardinality low by emitting the action tag plus a `PageAction`'s inner kind (`Open` / `PageAction:Click` / `PageAction:Fill`). One subtlety: `model/link.ts` type-imports `OpenMessage` from the sibling `../bridge.ts` — fine because it's `import type` (erased, no runtime cycle) and `bridge.ts` imports only `./model/web-view-source.ts`, never `link.ts`.
**Suggested destination**: a collector/bridge how-to, or alongside the Wire Pinning How-To (supersedes the `Link`-variant strip entry below)

## Re-driving `hfs_router` in-process: strip `Accept-Encoding` or the delegated sub-response comes back compressed and won't parse

**Discovered during**: claude/fhir-patient-everything-op-95ig70 — debugging a `$everything` 500 (`failed to parse sub-response JSON: expected value at line 1 column 1`)
**Learning**: `emr-rust`'s `$everything` handler (`patient_everything.rs`) delegates data-fetching by re-driving a clone of HFS's own router in-process (`router.clone().oneshot(sub_request)`), forwarding the caller's headers so auth/tenant resolution matches a direct request. But `helios-rest`'s `create_app_with_auth` wraps the router in a `CompressionLayer` (`compress_when(SizeAbove::new(32) & NotForContentType(parquet/zip))`) — so forwarding the real client's `Accept-Encoding: gzip, deflate, br` makes HFS gzip the sub-response body. The sub-request still returns **200**; the body is just compressed, so `serde_json::from_slice` fails at the first byte (`expected value at line 1 column 1` — column **1**, not 0, is the tell: non-empty body, invalid first byte = the `0x1f` gzip magic). Tests passed because their request helper never set `Accept-Encoding`. Fix: skip `header::ACCEPT_ENCODING` when copying headers into the sub-request — we consume the body in-process, not over the wire, so we always want it identity-encoded; the real client's `Accept-Encoding` is honored by the outer HTTP stack against our own response. General rule: any in-process `oneshot` re-drive of a router that carries a compression/content-negotiation layer must drop hop-by-hop / transfer-encoding-negotiation headers (`Accept-Encoding` first) from the forwarded set.
**Suggested destination**: unsure — a note near the `patient_everything.rs` module docs, or an emr-rust delegation how-to if one emerges

## `.local-notes` design-handoff HTML is a self-extracting bundle — the real markup lives in `__bundler/template` + `__dc_inline` JSON

**Discovered during**: claude/issue-256-implementation-ohs995 — matching the OAuth consent screen to the Scope Picker reference design
**Learning**: The standalone design files (e.g. `.local-notes/Scope Picker (standalone).html`, ~1.1MB) are not readable HTML — they're a JS bundler shell whose page is JSON-encoded in a `<script type="__bundler/template">` tag. Extract with a small node script (regex the tag, `JSON.parse`), then split again: the decoded page holds a `<script type="application/json" id="__dc_inline">` map of named sub-component templates (`PermissionStatement`, `FlagToggleRow`, …) plus the main page after the `</helmet>` (the helmet is a full inlined Tundra CSS copy — skip it). Each component is a mustache-ish `<x-dc>` template + a `DCLogic` class carrying the interaction model (state machine, serialization rules) — the class is worth reading, it specifies behavior, not just looks. The templates use the repo's real CSS custom properties (`--color-raised`, `--space-*`), so styles translate almost 1:1 to token-driven CSS modules.
**Suggested destination**: unsure (design-handoff how-to, if one emerges)

## Tauri `Webview::set_cookie` must not be called from a main-thread event handler; queue it from off-main and let FIFO order the navigate

**Discovered during**: claude/issue-256-implementation — seeding the owner `wf_auth` cookie into the native-webview popup
**Learning**: wry's macOS `set_cookie`/`cookies_for_url` block by re-entrantly pumping the main `NSRunLoop` (`wait_for_blocking_operation`) until the `WKHTTPCookieStore` completion fires. Tauri's `Webview::set_cookie` sends a `WebviewMessage::SetCookie` to the main loop — but `send_user_message` executes **inline** when already on the main thread, so calling it from inside a `run_on_main_thread` callback (or any event handler) nests the run-loop pump inside tao's event handler: observed as both child webviews' "web content process terminated" and a hard app deadlock. From a NON-main thread the message queues normally and the main loop handles it on a clean iteration. `SetCookie` has no reply channel (fire-and-forget), but the loop is FIFO — `set_cookie`, `set_cookie`, `navigate` queued in order guarantees every cookie commits before the navigation's first request. So: build the webview at `about:blank` on the main thread, then seed + navigate from the caller thread.
**Suggested destination**: plugins/tauri-plugin-native-webview/docs/Explanation.md (applied this session) / Strategies.md

## NSHTTPCookie boolean properties are presence-keyed: `cookie::Cookie::set_http_only(false)` makes the cookie HttpOnly on macOS

**Discovered during**: claude/issue-256-implementation — the JS-readable `wf_auth_exp` companion landed HttpOnly in the popup
**Learning**: The `cookie` crate records `set_http_only(false)` / `set_secure(false)` as `Some(false)`, and wry's macOS conversion (`cookie_into_wkwebview`) inserts the NSHTTPCookie `"HttpOnly"`/`Secure` property for **any** `Some`, with string value "TRUE"/"FALSE" — but Foundation keys off the property's _presence_, so a `Some(false)` cookie comes out HttpOnly. (The crate's `to_string()` renders `Some(false)` as no attribute, so `Set-Cookie`-based paths are immune; only the typed-Cookie → NSHTTPCookie path hits this.) When building a `cookie::Cookie` destined for `Webview::set_cookie`, set boolean attributes only when true and leave them `None` otherwise, and pin `cookie.http_only() == None` (not `Some(false)`) in tests.
**Suggested destination**: unsure (native-webview plugin docs; wry upstream issue candidate)

## Vite+ 0.2 upgrade: peer deps dodge `pnpm.overrides`; every plugin-hosting package must declare `vite: catalog:`; the vitest alias line is dead

**Discovered during**: vite-plus 0.1.21 → 0.2.2 / @vitejs/plugin-react 5 → 6 upgrade
**Learning**: Three coupled traps. (1) `pnpm.overrides` rewrites regular/dev/transitive deps but **not peer resolution** — a `vite` peer (`@vitejs/plugin-react`, `@tanstack/router-plugin`, `vite-plugin-singlefile`) binds to whatever `vite` the host package's own tree provides, and with `autoInstallPeers` an unprovided peer pulls **real** `vite@8` from the registry. With `nodeLinker: hoisted` that real vite wins the root `node_modules/vite` slot and every `defineConfig`/plugin call typechecks against mismatched `Plugin`/`UserConfig` types ("Excessive stack depth", "No overload matches"). Fix: every package that hosts a vite plugin declares `"vite": "catalog:"` (the catalog aliases it to `@voidzero-dev/vite-plus-core`), same as `wildflower-tauri` always did; the `pnpm.overrides` pin still matters for regular deps like vitest's own `vite` dependency. Verify with `vp why -r vite` — real `vite@x.y.z` should have zero dependents. (2) vite-plus 0.2.x depends on **real `vitest`** — the `@voidzero-dev/vite-plus-test` alias line ended at 0.1.24, so bumping the old catalog alias to `^0.2.2` is unsatisfiable (`ERR_PNPM_NO_MATCHING_VERSION`); pin `vitest` to the version `vp --version` reports instead. (3) The core alias ships **no `vite` bin** — `"dev": "vite"` scripts only ever worked via the accidentally-installed real vite (a stale `node_modules/.bin/vite` symlink); scripts must use `vp dev` / `vp build` / `vp preview`.
**Suggested destination**: docs/Dependencies/Version Override Explanation.md (partially applied this session) / Strategies.md

## Cookie-auth: clients are tokenless; the `AuthStateStore` subscribable is only a readiness signal

**Discovered during**: claude/github-issue-218-42hl8q — Part A (cookie-based auth on the web path); later fully tokenless under #218
**Learning**: No HTTP client attaches an `Authorization` header anymore — auth rides the same-origin `HttpOnly` `wf_auth` cookie the browser sends automatically (`FetchHttpClient` defaults to `credentials: 'same-origin'`). There is no client-side token-injection Tag; `defineSliceHttpClient` and every bespoke client build a plain tokenless `HttpApiClient.make(api)` requiring only `HttpClient.HttpClient`. The `AuthStateStore` `subscribable` survives but purely as the auth-readiness _signal_: it feeds `AuthStateProvider`, the `auth-ready` gate, and the token-rotation cache invalidator — never a request header. On web that signal is the non-secret `exp` hint from the readable `wf_auth_exp` companion cookie; on embedded/Tauri it's the host-pushed real JWT. Because nothing reads it as a header, the web `exp`-hint value is harmless (no risk of `Authorization: Bearer <exp-digits>`). `NeedsAuthMessage` stays env-agnostic — its `setToken(access_token)` is interpreted by the web store as "re-derive from the cookie, ignore the arg" (it then full-page-reloads), and the embedded store stores the real JWT. Don't push env branching into the shared component.
**Suggested destination**: Auth Token Storage Explanation.md (updated this session) / unsure

## rathole's `"Unable to listen for shutdown signal: channel closed"` is a teardown symptom, not a cause

**Discovered during**: claude/pr-202-tunnel-seam — debugging tunnel launch flap
**Learning**: We build `rathole` with `default-features = false` (no `notify`/`hot-reload`), so rathole's config watcher is the stub variant that does nothing but `await` the `broadcast::Receiver<bool>` shutdown we hand `rathole::run(cli, shutdown_rx)`. rathole's `run()` therefore ends — tearing down the control channel and logging `"Unable to listen for shutdown signal: channel closed"` from `client.run` — the instant **our** `shutdown_tx` drops, which happens when the supervisor's `run_once` future is dropped on cancel. So that error means "the supervisor got cancelled," i.e. a reconcile cancelled it — chase _what issued the reconcile_, not the rathole error. Confirmed by logging which `select!` branch `run_once` takes (`cancel.cancelled()` fired). The verify-deadline-too-tight theory was a red herring: the tunnel verifies in ~1s; it's the flap (cancel → re-dial) that breaks launches.
**Suggested destination**: unsure (tunnel-rust relay_clients/rathole.rs context)

## `reconcile` must not re-dial a live tunnel on a no-op settings revision bump

**Discovered during**: claude/pr-202-tunnel-seam — tunnel flap fix
**Learning**: Any newer settings revision made the tunnel daemon's `reconcile` cancel the live supervisor and re-dial from scratch — even when the _dialable_ config (relay + public_host) was unchanged. That tears rathole down (drops in-flight requests, flaps the public origin) on every redundant write (a settings re-save, a `requestedRunning` re-assert). Fix: `SupervisorHandle` carries the `relay_settings`/`public_host` it's driving; `reconcile` returns early (keeps the live tunnel) when the incoming revision is still `requested_running` with the same relay + host. The persisted/wire revision still advances (the `/tunnel` response reads it from the DB settings, not the watch), so leaving the watch's `settings_revision` at the supervisor's value is correct and keeps its `set_state` supersession check intact.
**Suggested destination**: unsure (tunnel-rust domain/tunnel_daemon.rs context)

## Tauri host `emit` echoes back to host `listen` on the same event — bridge handlers must filter by tag

**Discovered during**: claude/pr-202-tunnel-seam — wiring the apps RequestTunnel bridge handler for Tauri
**Learning**: The webview↔host bridge multiplexes every tag onto one Tauri event (`shared_structures_rust::bridge::BRIDGE_EVENT`). A host listener registered with `app.listen(BRIDGE_EVENT, …)` also receives the host's own `app.emit(BRIDGE_EVENT, …)` replies, so a web→host handler must decode the envelope `_tag` and act on _only_ its inbound tag (e.g. `RequestTunnel`), dropping host→web echoes and sibling-slice traffic — otherwise it loops on its own replies. Host→web wire types live in the slice's `*-rust::bridge` module (e.g. `AppsHostToWeb`, mirroring `GatekeeperHostToWeb`) and are byte-pinned to the TS `Schema.parseJson(Schema.TaggedStruct(...))` shapes in `*-core/src/bridge.ts` with golden serde tests; Tauri's struct-`emit` matches `parseJson` (verified against the working gatekeeper bridge). The `RequestTunnel` handler must be attached where the `TunnelService` exists (in `run_server`, not the sync `setup()`), so thread an `AppHandle` through.
**Suggested destination**: unsure (apps bridge / Tauri host wiring)

## Slice-standalone route files: `Route.useRouteContext()` widens to `any` without a registered Router; annotate `select`

**Discovered during**: ruthmarks/tanstack-inmemory-foundation — tunnel/apps migration onto router-context `runAuthed`
**Learning**: A `*-react` slice's route file (`createFileRoute(...)`) type-checks BOTH standalone (`vp run --filter <slice> check`) and when mounted under `apps/wildflower-react`. `Route.useParams()` is typed in both (params come from the route's own path). `Route.useRouteContext()` is NOT — in the slice's standalone build there is no `declare module '@tanstack/react-router' { interface Register }` (the slice never calls `createRouter` for a real app), so `RegisteredRouter` falls back to `AnyRouter` and an un-`select`ed `Route.useRouteContext()` returns `any` → `typescript(no-unsafe-assignment)` under oxlint. Fix WITHOUT a cast: give the slice a structural `XRouterContext` (`{ queryClient; runAuthed }`, re-declared per Issue #101, NOT imported from the app), make the slice's `__root.tsx` use `createRootRouteWithContext<XRouterContext>()`, and read context via an ANNOTATED select: `Route.useRouteContext({ select: (c: XRouterContext) => c.runAuthed })`. The annotation makes the result a typed value; the app build (which DOES register the router) sees the structurally-equal shape. The loader's `({ context })` is fine — it's typed from the route's resolved context chain, not the Register.

## Embedded WebView token lands AFTER `transport.flushed`; authed route loaders can 401 because the auth gate is a React component, not `beforeLoad`

**Discovered during**: ruthmarks/tanstack-inmemory-foundation — adding a tunnel route loader
**Learning**: In `wildflower-react` the `_auth` / `/settings` auth gates are React-COMPONENT gates (`AuthorizedAppShell`/`SettingsLayout` → `RequireAuth`, which reads the token reactively and renders `<NeedsAuthMessage>` when absent), NOT `beforeLoad` gates. TanStack `loader`s run during routing, before those components render — and `<TransportProvider>` (which blocks the React tree until the gatekeeper-bridge handshake delivers the token via `AuthTokenIssued`, post-`transport.flushed`) sits BELOW `<RouterProvider>`. So an authed loader on an admin route fires on embedded first paint BEFORE the token exists and 401s. `authTokenRef` reads `localStorage` synchronously at module load, so on standalone web the token is present immediately, but embedded has no localStorage token until the bridge writes it. Mitigations used: (1) eager startup prefetch is gated on `Effect.runSync(authTokenRef.get)` being non-null/non-empty (skips on embedded first paint); (2) the route loader's `ensureQueryData` is wrapped in try/catch so a failed prefetch is non-fatal — navigation proceeds and the in-component `useSuspenseQuery` (rendered only once `RequireAuth` sees the post-flush token) does the first read. `waitForHostTokenRef` (gatekeeper-react) is the readiness flag the gate consults but is not currently consumed by loaders.

## Page headers: one `<PageHeader>` per page (fixed-parent back link); externally-published flows get an inside-`/settings` twin rather than moving

**Discovered during**: festive-hamilton — back buttons + header audit across wildflower-react
**Learning**: The web app's per-page headers are unified by a single generic `PageHeader` (`global/react-tundraish`): a one-line, ellipsis-truncating title, an optional trailing `actions` slot, and an optional `backHref` that renders a TanStack `<Link>` to the page's **fixed logical parent** (NOT `history.back()` — a fixed parent is deterministic on a refreshed/deep-linked/OAuth-redirect landing where there's no in-app history to pop). Rule: every screen renders exactly one `PageHeader` as the first child of its page shell; the three tab surfaces (`/home`, `/collector`, `/settings`) omit `backHref`, everything else sets it. The old double-header came from the `/settings` _layout_ rendering a persistent `<h1>Settings</h1>` on top of each child's own heading — fixed by moving "Settings" into the index page so the layout owns no heading. `react-tundraish` can use `<Link to={stringVar}>` because it compiles without the app's `Register` augmentation, so `to` stays `string` (same reason `ItemList` does it) — no cast, and consumers pass plain path literals.

The device-authorization flow showed the right move when a settings page would otherwise need an externally-published URL: `/gatekeeper/devices` is the RFC 8628 `verification_uri`, built in BOTH `gatekeeper-core/page-paths.ts` AND `gatekeeper-rust/http/page_paths.rs` (drift-tested; `routes.test.tsx` asserts "settings landings are not externally published"). Instead of moving it into `/settings` (which would change the verification*uri shown on other devices and touch Rust), **lift the inner form out of the route** (`screens/device/device-code-entry-form.tsx`, `device-consent-screen.tsx` — header-less, parameterized by `onSubmit`/`onDone`) and render it from TWO routes: the public `/gatekeeper/devices*`(no back link) and an owner-facing twin`/settings/gatekeeper/devices*`(back link to the access page, reached from the "Authorize a Device" row). Same inner content, different chrome; the published URL and Rust stay untouched. Generalizes the existing`requests`/`requests*`sibling-route trick: name the consent twin`devices\_.$userCode.tsx`so it doesn't nest under the headerless`devices.tsx` entry route.
**Suggested destination**: docs/UI/Settings Fragments How-To.md (the outside/inside twin pattern) + a UI headers reference if one emerges

## Cross-language (TS/Rust) semantics contract via a shared JSON fixture at the slice root

**Discovered during**: claude/core-ui-events-4crpo0 — review follow-ups pinning the scopes-core ↔ scopes-rust grammar mirror
**Learning**: When the same domain grammar is implemented twice (TS `scopes-core` + Rust `scopes-rust`), prose "mirrors scopes-rust" doc comments don't stop drift — a shared vector file does. ## `Equal.equals` silently degrades to reference equality on classes that don't implement `Equal` — check before adopting it

**Discovered during**: claude/issue-256-implementation-ohs995 — consent-screen refactor moving scope editing onto domain objects
**Learning**: Effect's `Equal.equals(a, b)` never fails on a class that doesn't implement `Equal.Equal` — it falls back to reference equality and returns `false` for two structurally identical instances. ## `Schema.declare` combinators need `arbitrary` AND `equivalence` annotations before tests can generate/compare through them

**Discovered during**: claude/emr-fhir-r4-migration-5lh030 — deleting emr-core and porting fhir-r4 schema tests to generate from the wire schemas
**Learning**: A `Schema.declare(...)`-based combinator (kitchen-sink's `OrNullAsOptional`/`OrNullAsUndefined`, fhir-r4's choice-slot null stub) derives nothing: `Arbitrary.make` throws `MissingAnnotation` and `Schema.equivalence` silently falls back to reference equality, so `toSchemaEqual` reports "Values are not schema-equivalent … no visual difference" for structurally identical values. This stayed hidden for as long as tests generated/compared via the plain-Struct emr-core row schemas; the moment the wire schemas became the only schema tree, every property test failed at once. Fix at the combinator, not per call-site: `.annotations({ arbitrary: (inner) => (fc) => fc.oneof(fc.constant(null), inner(fc)), equivalence: (inner) => (a, b) => a === null || b === null ? a === b : inner(a, b) })` — declaration annotations receive the type-parameters' derived arbitraries/equivalences as arguments. Rule of thumb: any new `Schema.declare` that will appear inside property-tested schemas ships with `arbitrary` + `equivalence` annotations from day one.

## Opaque cross-boundary JSON columns: `#[schema(value_type = Value)]` is the drift-safe way to spec them

**Discovered during**: claude/pr-343-diesel-rewrite — collector-rust (diesel) storing the TS-owned `CollectorConfig` union verbatim
**Learning**: When a Rust slice stores/serves a JSON payload whose schema is TS-owned (e.g. `collector_remotes.config`, the tagged `CollectorConfig` union), the utoipa annotation on the field must be `#[schema(value_type = Value)]`, which emits an **empty schema `{}`**. The openapi-drift engine normalizes `{}` to `any` (a wildcard that matches whatever the TS side declares — today a single-member union, later a widened one) so adding a TS collector never breaks the drift gate. `value_type = Object` is NOT equivalent: it emits `{"type":"object"}`, which normalizes to an object with zero fields and drifts against the client's concrete union ("field on client, MISSING from server"). This holds regardless of how the column is stored on the Rust side: whether the field is a plain `serde_json::Value` mapped to a diesel TEXT column (config JSON round-tripped through `serde_json::to_string`/`from_str`) or a `#[serde(transparent)]` newtype — the wire shape is the raw inner value, and `value_type = Value` documents exactly that opacity.
**Suggested destination**: docs/Effect/OpenAPI Spec Drift How-To.md (gotchas section)

## Diesel 2.2 `serde_json` feature has no SQLite `Json` support — map JSON columns via a `Text` newtype + `serialize_as`/`deserialize_as`

**Discovered during**: claude/pr-343-diesel-rewrite — making collector-rust's `Remote` the diesel model directly (removing the internal row struct)
**Learning**: Diesel 2.2's `serde_json` feature only wires `serde_json::Value` ⇄ the `Json` sql type on the Postgres and MySQL backends; `FromSql`/`ToSql<Json, Sqlite>` landed in diesel 2.3 (`src/sqlite/types/json.rs` doesn't exist in 2.2.12), which the workspace deliberately pins away from. On the 2.2.x line the pattern is a thin `#[derive(AsExpression, FromSqlRow)] #[diesel(sql_type = Text)]` newtype over `serde_json::Value` with hand-written `ToSql`/`FromSql<Text, Sqlite>` (compact `to_string()` out, `from_str` in — corrupt TEXT surfaces as a diesel deserialization error, not a panic), plugged into the model with `#[diesel(serialize_as = X, deserialize_as = X)]` so the field itself stays a plain `serde_json::Value`. Two follow-on gotchas: (1) `serialize_as` converts via `Into`, which consumes the value, so diesel stops generating the borrowed `Insertable` impl — `.values(&model)` becomes `.values(model.clone())`; (2) the newtype appears in the model's public `Queryable`/`Insertable` impls, so it must be `pub` (E0446 otherwise). ## Pooling a diesel `:memory:` database needs a shared-cache URI + a resident connection — each pooled connection otherwise gets its own empty db

**Discovered during**: claude/pr-343-diesel-rewrite — moving collector-rust off a single `Arc<Mutex<SqliteConnection>>` onto an app-wide diesel r2d2 pool (`persistence_rust::open_pool` / `DieselPool`)
**Learning**: An r2d2 pool over the diesel URL `":memory:"` gives every pooled connection its OWN private in-memory database, so a migration (or any write) on one checkout is invisible to the next — tests that pass with a single connection break the moment the store checks out a second. Fix: a shared-cache URI, `file:<unique-name>?mode=memory&cache=shared` (unique per pool via an `AtomicU64` counter so tests stay isolated). diesel's `SqliteConnection::establish` accepts `file:` URIs verbatim — libsqlite3-sys opens with `SQLITE_OPEN_URI`, no extra flags. Lifetime subtlety: a shared-cache in-memory db exists only while ≥1 connection to it is open, so the pool must hold one resident — r2d2 defaults `min_idle` to `max_size` and establishes them eagerly at `build()`, which keeps the db alive for the pool's lifetime (rely on that rather than tearing down to zero idle). This is the diesel counterpart of `persistence_rust::Connection::open_in_memory`, and it lives in persistence-rust as `open_in_memory_pool()` (public, non-test — same as the rusqlite one — so every diesel-backed slice's tests can reuse it). For the on-disk pool test, prefer a `tempfile::tempdir()` path over `:memory:` so the cross-connection round-trip actually exercises one shared file. Query a pooled connection's pragmas in a test via `diesel::sql_query("SELECT timeout AS value FROM pragma_busy_timeout()")` with a `#[derive(QueryableByName)]` scalar struct (the `pragma_*()` table-valued functions are available in the bundled SQLite).
**Suggested destination**: a diesel/persistence how-to if one emerges, or alongside the other PR-343 diesel entries above

## Moving an already-shipped table from the persistence-rust runner to diesel migrations needs idempotent DDL (`IF NOT EXISTS` / `INSERT OR IGNORE`)

**Discovered during**: claude/rust-slices-standardization-odf5e2-tunnel — migrating tunnel-rust's `TunnelStore` off rusqlite + the namespaced `run_migrations` runner onto the app-wide diesel pool + embedded diesel migrations
**Learning**: When a slice's table was created by the retired `persistence_rust::run_migrations` runner (bookkept in `schema_migrations`) and you re-express it as a diesel embedded migration (bookkept in the disjoint `__diesel_schema_migrations`), diesel sees version `0001` as un-applied on every pre-existing database and runs its `up.sql`. A verbatim `CREATE TABLE` (what a brand-new slice like collector uses) then fails against the already-present table. The transition-safe form is idempotent DDL — `CREATE TABLE IF NOT EXISTS …` + `INSERT OR IGNORE INTO … (id) VALUES (…)` for a seeded singleton — so `0001` is a no-op on an upgraded database while still creating the table + seed on a fresh one (byte-for-byte the schema the old runner produced). This only matters for tables that predate the diesel move; a genuinely new table keeps the plain `CREATE TABLE`. Worth a regression test that runs the embedded migrations against a hand-created legacy table and asserts the existing singleton row is neither duplicated nor overwritten.
**Suggested destination**: a diesel/persistence how-to if one emerges, or alongside the other diesel-migration entries above

## Diesel's stock migration harness shares one un-namespaced `__diesel_schema_migrations` — a second diesel slice's `0001` silently masks the first

**Discovered during**: claude/rust-slices-standardization-odf5e2-tunnel — reviewing/fixing PR #354, which made tunnel-rust the _second_ diesel-backed slice to run its embedded migrations against the app-wide shared pool (collector was the first)
**Learning**: `MigrationHarness::run_pending_migrations` records applied versions in a single, **un-namespaced** `__diesel_schema_migrations` table keyed by the migration _version_ (the directory-name prefix before the first `_`). Every slice here starts its history at `0001_initial_schema`, so when a second diesel slice runs migrations against the _same_ shared database, diesel sees version `0001` already applied and **skips the second slice's migration entirely** — its table is never created and the app fails to boot on a fresh install (idempotent `IF NOT EXISTS` DDL does NOT rescue this: the migration is skipped, never run). It's order-independent (whichever `setup_*` runs first wins `0001`; the loser's later migrations then fail against a missing table) and invisible to per-slice unit tests, which each use an isolated in-memory pool where only that slice's migrations run — only the shared-pool host wiring (which can't build without GTK in the dev env) exercises the clash. This is the diesel counterpart of the collision the rusqlite `persistence_rust::run_migrations` runner has always prevented with a per-`namespace` `schema_migrations` table. The false-comfort tell is a "the two bookkeepers coexist with no collision" doc comment that only reasons about the rusqlite `schema_migrations`, never about a _second diesel slice_. Fix: `persistence_rust::run_diesel_migrations(conn, namespace, source)` — a namespaced diesel runner enumerating a `MigrationSource<Sqlite>` and tracking applied versions per `(namespace, version)` in `diesel_slice_migrations` (each pending migration + its bookkeeping row applied in one transaction). Every diesel slice calls it with its own namespace; nothing uses stock `run_pending_migrations`. Regression test lives in persistence-rust: two fixture trees both named `0001_initial_schema` run under different namespaces and both apply.
**Suggested destination**: a diesel/persistence how-to if one emerges, or alongside the other diesel-migration entries above

## Orphan rule blocks diesel `serialize_as`/`deserialize_as` on `Option<foreign>` fields — mirror that one table with a private db row struct

**Discovered during**: claude/rust-slices-standardization — gatekeeper-rust's rusqlite→diesel store migration
**Learning**: The PR-343 `Text`-newtype pattern (`#[diesel(serialize_as = X, deserialize_as = X)]` on a plain domain field) extends fine to typed inners (`Vec<String>`, `Url`, enums) — but ONLY for non-`Option` fields. A nullable column whose field is `Option<Url>` would need `impl From<Option<UrlText>> for Option<Url>` (and the reverse), and `Option` is neither local nor `#[fundamental]`, so coherence rejects the impl. Don't fight it per-field: give that one table a private `#[derive(Queryable, Selectable, Insertable)]` row struct in `db/` whose fields ARE the wrapper types (`Option<UrlText>`, `Option<JsonStrings>` — the blanket `Option<T: ToSql/FromSql>` impls cover Nullable), plus `From` conversions to/from the domain type at the query boundary. In gatekeeper only `authorization_requests` needed this; every other table maps its domain struct directly. **Suggested destination**: alongside the PR-343 diesel entries / a diesel persistence how-to if one emerges

## A `GatekeeperStore` transaction seam (GAT `type Tx` + `with_connection`/`transaction`/`immediate_transaction`) lets multi-statement logic live in the pure domain

**Discovered during**: claude/gatekeeper-store-transactions — splitting gatekeeper-rust's persistence port so composed operations move out of the store
**Learning**: A CRUD-only store port (collector/tunnel) needs no transaction seam, but gatekeeper accreted seven "specialized" store methods (`upsert_*_grant`, `revoke_grant_and_expire_client_families`, `consume_refresh_token`, the three `expire_*`) purely because a multi-statement operation had to be atomic and the store was the only place a transaction could live — so their business logic (scope-union read-merge-write, delete-both-then-expire, the three-state consume) was reachable only through SQLite and duplicated in the in-memory fake. The fix is to split the port into `GatekeeperTx` (single-statement primitives, `&mut self`) plus a seam trait `GatekeeperStore { type Tx<'a>: GatekeeperTx; fn with_connection/transaction/immediate_transaction(f: impl FnOnce(&mut Self::Tx<'_>) -> Result<T, E>) }`, and compose the compound operations in `domain/actions` inside those closures. Load-bearing details: (1) the elided `&mut Self::Tx<'_>` in the closure bound is **higher-ranked** (`for<'a>`), so pass closures `|tx| tx.foo()` — a bare fn-item path `GatekeeperTx::foo` fails to unify; (2) diesel's `Connection::transaction`/`SqliteConnection::immediate_transaction` require `E: From<diesel::result::Error>` even when the closure body maps its own query errors (BEGIN/COMMIT can still fail raw), so add `impl From<diesel::result::Error> for GatekeeperError` in the `db` layer to keep `domain::error` diesel-free; (3) `SqliteConnection::immediate_transaction` is inherent on `SqliteConnection` and hands the closure `&mut SqliteConnection`, while `Connection::transaction` on a `PooledConnection` hands back `&mut PooledConnection` — deref the pooled conn to `&mut SqliteConnection` up front so both runners and every `db/*` free fn share one connection type; (4) keep the `GatekeeperStore` default methods (each `self.with_connection(|tx| tx.op())`) so existing standalone call sites are untouched and lone reads stay autocommit (no write lock); (5) `type Tx<'a>` on a `pub` trait makes the concrete `SqliteGatekeeperTx` public interface — it must be `pub` (E0446); (6) the self-contained `expire_*` bodies keep their own `conn.transaction` wrapper and nest safely as **savepoints** when composed inside an outer domain transaction, so they need no decomposition; (7) the `BEGIN IMMEDIATE` lock-at-read property that prevents lost scope-unions must ride the seam explicitly (`immediate_transaction`) — it silently regresses if a composed upsert uses the deferred `transaction`. The fake models rollback by snapshotting all maps before `transaction`/`immediate_transaction` and restoring on `Err`; it cannot model real lock contention, so the concurrency-safety tests (guarded-update, lost-update) stay SQLite-backed in `crate::db` while the orchestration/merge logic gains fast fake-based coverage in `domain::actions`.
**Suggested destination**: an Effect/persistence "store transaction seam" how-to if one emerges, or alongside the diesel persistence entries above

## Parallel subagents in one checkout: `git mv` auto-stages, so an unrelated commit sweeps the renames in

**Discovered during**: claude/rust-packages-audit-nmbqs7 — three subagents editing disjoint crates in the same checkout
**Learning**: `git mv` stages the rename immediately (unlike content edits, which stay unstaged). When one workstream commits with `git add <its-paths> && git commit`, a _concurrent_ workstream's already-staged renames ride along even though no path under them was added — the commit picks up everything in the index, and `git commit -- <paths>` is the only form that restricts it. The committed tree then holds renamed files whose `mod` declarations (unstaged content edits) are missing, i.e. HEAD doesn't compile. Recovery before pushing: `git reset --soft <base>`, `git restore --staged <other-workstream-paths>`, then re-commit with explicit `git commit -- <paths>` pathspecs. Prevention: parallel agents belong in worktrees (`.devcontainer/wf-worktree.sh`); if they do share a checkout, every commit during concurrent work should use `git commit -- <paths>`, and treat "renames from a crate I didn't touch appear in my commit stat" as the tell.
**Suggested destination**: Strategies.md (parallel-agent hygiene), or CONTRIBUTING.md git workflow

## Building schemas from another package's reused datatypes breaks `vp pack`'s dts (TS2883) — the producer must export the named interfaces at top level

**Discovered during**: claude/github-issue-335-2lac0i — the new `fhir-stu3-as-r4` slice (and `rexall-be-well-collector`) reuse `fhir-r4/data-types` schemas
**Learning**: When a package builds new Effect `Schema.Struct`s that spread/reference another package's datatype schemas (e.g. `...DomainResource.fields`, `Extension.Schema`), the struct's _inferred_ decoded type embeds that package's named interfaces (`ExtensionType`, `ReferenceType`, `IdentifierType`). If the producer only exposes them through a namespace re-export (`export * as Extension` + `type ExtensionType as Type` → `Extension.Type`), `tsgo`'s declaration emit can't map the raw interface back to that path and `vp pack` fails with TS2883 ("cannot be named without a reference to 'ExtensionType'") — even though `vp check` (typecheck only) stays green, because the leak only bites at `.d.ts` generation. The clean fix is on the _producer_ side: add a direct top-level re-export of each named interface (`export type { Type as ExtensionType } from './…/extension.ts'`, `export type { ReferenceType, IdentifierType } from './…/identifier-and-reference.ts'` in `data-types/index.ts`). With a top-level name to reference, the consumer's plain `typeof Struct.Type` / `typeof Struct.Encoded` annotations pack cleanly — no hand-written wire interfaces needed. (Hand-rolling explicit `Type`/`Encoded` interfaces in the consumer also works but is far more code, and forces you to also _export_ every `Encoded` interface or a Bundle/wrapper referencing them fails with TS4023.) The same bite recurs for _wrapper/factory_ return types: `rexall-be-well-collector` calling `Bundle.searchsetBundle(...)` embeds `BundleValue` from `fhir-r4`'s `resources/bundle.ts`, so that too now has a top-level re-export (`export type { BundleValue } from './resources/bundle.ts'` in `data-types/index.ts`) — whenever a consumer's inferred type names an internal interface, re-export it flat from the producer. `vp check` won't catch any of this; run `vp pack` on the consuming package.
**Suggested destination**: docs/Testing or a slices/emr dts how-to; relevant to any slice reusing `fhir-r4` schemas

## Scope-gating `/access` "default-safe": facades + a source-guard test, because Rust visibility can't seal a field from one sibling module only

**Discovered during**: claude/resource-types-permissions-gsmi0x — issue #261, scope-gated service extractors over gatekeeper's `/access` surface
**Learning**: The goal was "a forgotten permission check can't ship" — make the store reachable _only_ through a `Scoped<F>` extractor that runs `Grant::covers(required)` first. Three non-obvious walls shaped the final shape. (1) **You cannot restrict a field/method's visibility to a sibling module.** `pub(in path)` accepts only _ancestor_ modules of the item, so from `http::state` you can't say "visible to `http::routes::oauth` but not `http::routes::grants`" — both are siblings. Since the OAuth surface legitimately needs the raw `GatekeeperState.store` and the admin surface must not, pure visibility can't express it; the store stays `pub(crate)`. The enforceable substitute: migrate every admin handler to take _only_ facade extractors (never `State<Arc<GatekeeperState>>`), so forgetting the facade means the handler has no way to reach data (a compile-time dead end), and back it with a unit test that `include_str!`s each admin route file and asserts it contains no `State<` / `.store` / `.revocation_store` — the teeth that make omission fail CI rather than merely being discouraged. (2) **`pub use` can't promote a `pub(crate)` item to public (E0364)** — the re-exported item itself must be `pub`. The `grantable_admin_scopes` registry had to be `pub fn` (not `pub(crate)`), which also killed its dead-code warning under clippy `-D warnings` since `pub` lib items aren't "dead". (3) **The approver "can't delegate more than you hold" clamp must bridge the SMART v1-word / v2-letter permission grammars.** `Grant::covers`/`Permission::contains` are deliberately grammar-strict (a client registered in one grammar authorizes only that grammar), so an owner holding `system/*.cruds` does NOT `covers` a client's requested `patient/Observation.read` — the owner would be blocked from approving any v1-word client, and an integration test caught exactly this. Fix: widen _both_ the approver's grant and each granted scope with `with_alternate_canonical_forms` (the same twinning the token minter applies) before the coverage check, and clamp only FHIR/Wildflower _resource_ scopes — non-resource markers (`openid`, `offline_access`, `launch`) aren't in the owner grant and must pass through unclamped or you'd block legitimate owner approvals. Also worth noting: authN (a `require_valid_session` layer that verifies once and stashes `VerifiedClaims` in request extensions → 401) and authZ (the `Scoped<F>` extractor reads those claims, checks coverage → 403) split cleanly, and logout stays self-service (reads the stashed claims, takes no scope) rather than being force-fit into a resource facade.
**Suggested destination**: a gatekeeper auth/authorization how-to (scope-gated extractors + the `Scoped<F>`/facade pattern), or alongside the Jargon Explanation

## Lifting the scope-gate to a shared layer: generalize over State+Claims, and carry scopes cross-slice via a framework-neutral `ScopeClaims` in request extensions

**Discovered during**: claude/resource-types-permissions-gsmi0x (follow-up) — lifting gatekeeper's `Scoped<F>`/`GatedService` into `shared-structures-rust` so every HTTP slice can copy the pattern, and converting `databases-rust` as the first consumer
**Learning**: The generic machinery moved to `shared_structures_rust::scope_gating` (behind a `scope-gating` feature gating `axum` + `scopes-rust`), **not** `scopes-rust` — that crate is a deliberately pure value library (serde + tracing only, mirroring the pure TS `scopes-core`); `shared-structures-rust` already houses feature-gated axum machinery (`http-errors`, `health-check`, `served-origin`) and is every HTTP slice's shared dep. Load-bearing details: (1) **Generalize `GatedService` with two associated types** — `type State: Clone + Send + Sync` and `type Claims: GrantedScopes` — and implement `impl<F: GatedService> FromRequestParts<F::State> for Scoped<F>` (the projection `F::State` as the extractor's state parameter compiles fine and matches the router state). `build(state, granted: &Grant)` gains the caller's `Grant` so a facade needing per-resource gating can hold it; fixed-capability facades ignore it. (2) **The claims-portability trick is what makes the pattern reusable without a dependency inversion.** A downstream slice (databases) can't name gatekeeper's domain `VerifiedClaims`, so the shared layer defines a framework-neutral `ScopeClaims { scope: Option<String> }` implementing `GrantedScopes`, and gatekeeper's **`BearerGate` (`require_valid_bearer_token`) inserts one into request extensions after verifying** — it previously verified and _discarded_ the claims. Every host-composed slice router behind `layer_router_with_gatekeeper_auth_gating` now gets scopes for free; a slice with a richer claims type implements `GrantedScopes` on it instead (gatekeeper keeps `VerifiedClaims` for its own `/access` surface). (3) **Data-dependent gating** (databases' scope depends on _which_ database): return `required_scopes() -> vec![]` (coarse gate = "authenticated only", satisfied by the `ScopeClaims` presence) and check `granted.covers(&descriptor.read_scope)` _inside_ the facade method, **before** the existence check, so an under-scoped caller gets `403` whether or not the resource exists (no existence leak — mirrors gatekeeper's gate-before-handler). Keep read vs delete as _separate_ facades so a read handler structurally can't delete. (4) **Splitting a source-guarded file into a directory shifts the `include_str!` paths** (`../routes/…` → `../../routes/…`), and the forbidden-token list must target the store's _method-call shapes_ (`.existing(`, `.databases(`, `State<`) not the bare type name — a doc-comment or `expect("…DatabasesState::new")` mention of the type is a false positive. (5) **Typed scope builders belong in `scopes-rust`, not hand-spelled at call sites.** Added `Scope::wildflower(res, perm)` / `wildflower_all(perm)` / `fhir_system_all(perm)` + `Permission::READ_SEARCH` (the `rs` letter bag) so the host and gatekeeper name scopes typed (a typo is a compile error, never a silent `Scope::Unknown` no token covers); gatekeeper's old local `wildflower_scope` helper collapsed into `Scope::wildflower`. Because coverage never crosses the SMART v1-word / v2-letter grammars, a required scope like `system/*.rs` must stay a **letter bag** for an owner's `system/*.cruds` (also a letter bag) to cover it — don't reach for the `read` word. Host still owns the which-scope-per-database policy (declared on each `DatabaseDescriptor`); the slice enforces whatever scope it's handed.

## Splitting a big Rust file into a folder: source-guard `include_str!`, the `oauth/` route-guard exemption, and one-binary integration tests

**Discovered during**: claude/pr-397-file-audit-dwg5j3 — breaking up the largest files under PR #397 (gatekeeper scope-gating) into folders
**Learning**: Pure file-reorg refactors still trip several non-obvious walls. (1) **Source-guard tests that `include_str!` a sibling break on the rename.** `domain/capabilities/mod.rs` counts `_scopes() -> Vec<Scope>` occurrences via `include_str!("consents.rs")`; splitting `consents.rs` → `consents/{mod,oauth,device,delegation}.rs` needs the include repointed to `consents/mod.rs` (where both `*_scopes()` fns stayed). Grep for `include_str!` before moving any guarded file. (2) **The `access_handlers_reach_the_store_only_through_capabilities` guard exempts by path prefix `oauth/`**, so splitting `oauth/token_exchange.rs` → `oauth/token_exchange/*.rs` (whose submodules legitimately hold `State<`/`.store`) stays green — but a split of a _non-exempt_ admin handler into a subdir would newly trip it — and databases' sibling guard skips only `mod.rs`, so extracting `routes/mod.rs`'s inline test module to `routes/tests.rs` tripped it (the router tests hold `State<`/`DatabaseFiles`) until I exempted `tests.rs` too; a `read_dir`-based source guard scans _any_ new `.rs` you drop under it. (3) **A Rust trait is one item — you can't split it across files.** `gatekeeper_store.rs` (877L, two traits) splits cleanly by _trait_ into `gatekeeper_store/{mod,tx,store.rs}`; decomposing `GatekeeperTx` further into per-resource _sub-traits_ was rejected because supertrait methods require the _defining_ trait in scope at every call site (so `capabilities/*` would each need N new `use` lines) **and** every `impl GatekeeperTx` block (Sqlite adapter + fake) would have to split into N blocks — large churn/regression risk for a size cleanup. Same one-impl-per-trait rule means `test_fake.rs`'s ~400-line `impl GatekeeperTx` block is irreducible; the honest split is structs+`GatekeeperStore` impl in `mod.rs`, that atomic impl in `tx.rs`, fixtures in `fixtures.rs` (a child module can read the parent struct's private fields, so the impl moves without widening visibility). (4) **A 3480-line `tests/integration.rs` splits into ONE test binary, not N.** `tests/integration/main.rs` + `mod common; mod <section>;` is auto-discovered as a single `integration` target (cargo picks up `tests/<name>/main.rs`); put every helper/`TestDb`/shared `const` in `common.rs` as `pub` + `pub use` the whole import union, and each section does `use crate::common::*;`. Because it's one binary, every helper is "used" by some section (no `dead_code`), and the glob import never warns unused — so no `#![allow(dead_code)]` (which the separate-`tests/common/mod.rs`-per-binary layout would force). Split-point detection that survives braces-in-string-literals: top-level items end at the first col-0 `}` (fn/struct) or first line ending `;` (const), never naive brace-counting. Update the one doc that pins a moved test path (`…/integration.rs::test` → `…/integration/smoke.rs::test`).
**Suggested destination**: Strategies.md (large-refactor / file-splitting hygiene), or a Rust module-layout how-to

## Freezing a plan freezes Effect's `Duration` singletons — and a frozen `Duration` makes `Hash.hash` throw process-wide

**Discovered during**: claude/pr-429-rebase-review-xfcfgh — PR #429 review, `ScrapingPlan.make`'s `deepFreeze` meeting an `AwaitUserDismiss` step whose plan set `idleTimeout: Duration.infinity`
**Learning**: `kitchen-sink`'s `deepFreeze` walks own enumerable keys, so it doesn't stop at a value that merely _looks_ opaque — an Effect `Duration` has an own enumerable `value`, so `deepFreeze` freezes the `Duration` instance and recurses into it. That is harmless for a `Duration.seconds(30)` built at the call site, but `Duration.infinity` and `Duration.zero` are **module-level singletons Effect hands out by reference**: freezing one inside a single identity factory mutates a value every other holder in the process shares. The consequence is delayed and looks unrelated to freezing — `DurationProto`'s `Hash` implementation memoises onto the instance with `Object.defineProperty`, which throws `TypeError` on a frozen object, so some later, entirely unrelated `Hash.hash(Duration.infinity)` (or any `Equal`/`HashMap` use) blows up. Verified directly: `Hash.hash(Object.freeze(Duration.seconds(1)))` throws. Generalises past `Duration` — any branded/prototype-bearing library value (Effect `Option`/`Either` instances, `RegExp`, class instances) is a candidate, and freezing a `RegExp` has its own bite (`lastIndex` becomes unwritable, so a `/g` regex's `exec` throws). The fix taken here was at the _boundary_ (`ScrapingPlan.make` skips `Duration.isDuration` values while still freezing the step objects holding them) rather than narrowing `deepFreeze` for every caller — but the general rule is worth knowing before reaching for `deepFreeze` on anything holding library values. The tell: nothing fails at freeze time, and `vp check` is perfectly green.
**Suggested destination**: a `deepFreeze` caveat in `global/kitchen-sink`'s README, or Strategies.md (identity-factory hygiene)

## `EntityDefinition.parse` only ever saw what a _decoding_ entity needs — a _recording_ one needed three additions to `RemoteResponse`

**Discovered during**: claude/issue-436-draft-pr-2nu428 — `web-trace-collector`, the first collector that records exchanges instead of decoding payloads out of them
**Learning**: `RemoteResponse` was shaped entirely around entities that recognize a URL and decode a known payload: `url`, `status`, `statusText`, `headers`, `text()`. Every field a _recorder_ needs was either dropped on the floor or unreachable. (1) **The sniffer's correlation `id` was discarded.** `handleResponseStart` has `event.id` in hand — it uses it as the tracker's `MutableHashMap` key — but never passed it to the `RemoteResponse`, so `parse` could not know which request it was looking at. Any storage scheme keyed on request identity (here `{sessionId}-{requestId}`, which is what makes a retried write an idempotent upsert instead of a duplicate) is impossible without it; the alternative, a counter threaded through `parse`, re-derives an id the sniffer already assigned and loses idempotency. (2) **There was no timestamp at all.** `parse` runs at _settle_, so a clock read inside it labels the end of the response as its beginning — the tracker is the only place that knows when `ResponseStart` was observed. (3) **`text()` is lossy and there was no alternative.** `#chunks` is private and the only accessor UTF-8-decodes, so a body that is not valid UTF-8 (an image, a protobuf, an undecoded gzip) comes back peppered with U+FFFD, and a re-encode of that string is not the body that arrived — you cannot base64 it, you cannot hash it, and `byteLength` is the only truthful thing left. A `bytes()` accessor is the fix, and its return type wants pinning to `Uint8Array<ArrayBuffer>` rather than the default `Uint8Array<ArrayBufferLike>`: every platform `BufferSource` parameter (`crypto.subtle.digest`, `Blob`, `fetch`) rejects the latter, so leaving it loose pushes a cast onto every caller. Note `TextEncoder.encode()` and `fc.uint8Array()` both produce the loose form, so tests that build bytes by hand copy through `new Uint8Array(...)` while the production path stays copy-free. The general shape: a seam designed around one consumer silently encodes that consumer's assumptions, and the second consumer's requirements read as "the ticket forgot something" when they are really "the seam was never asked this question".
**Suggested destination**: alongside the `EntityDefinition` / handler docs in `slices/collector/collector-fundamentals`

## A plan factory that is legitimately impure breaks a registry test that deep-equals plans

**Discovered during**: claude/issue-436-draft-pr-2nu428 — `web-trace-collector` minting a session id per plan build
**Learning**: `collector-registry`'s dispatch property test asserted `planFor(config)` deep-equals the descriptor's own `makeScrapingPlan(config)`, with the comment "the plan factory is per-config so structural equality stands in for identity". That premise held only while every collector's plan was a pure function of config. A recording collector must mint a fresh session id per _run_ (a config-derived id would make the second recording of a remote silently upsert over the first), and `makeScrapingPlan` is called exactly once per sync run — so the mint belongs there, and two builds from one config are unequal by construction. Two separate things break the equality, not one: the session id itself, and the fact that a per-build entity factory produces a fresh `parse` **closure** each time (`toEqual` compares functions by reference), so even a deterministic id would not have saved it. The fix is to compare an identity _projection_ — name, `firstPage`, step names, entity names — which still fails loudly on a mis-dispatch (a plan from the wrong descriptor differs in all four) without asserting a purity the interface never promised. Worth knowing before adding any collector whose plan carries per-run state.
**Suggested destination**: Strategies.md (test-premise drift), or the `collector-registry` notes in `slices/collector/AGENTS.md`

## jsdom enforces HTML5 constraint validation, so `type="url"` swallows the case your schema test meant to exercise

**Discovered during**: claude/issue-436-draft-pr-2nu428 — the `WebTraceConfigForm` start-URL field
**Learning**: A form test that types a malformed value into an `<input type="url">` and expects the component's own `Schema.decodeUnknownEither` `ParseError` to render inline will fail confusingly: jsdom blocks the submit on the input's constraint validation, so the `onSubmit` handler never runs, no error state is set, and nothing renders. ## Off-main-thread `set_cookie` never fixed the macOS deadlock — wry's nested run-loop pump is the hazard, so write `WKHTTPCookieStore` async instead

**Discovered during**: claude/github-issue-442 — cold-launch cloud-app launches hard-hanging the Tauri desktop app
**Learning**: Supersedes the "queue it from off-main and let FIFO order the navigate" entry above, whose "fire-and-forget FIFO message" model was unsound. wry's macOS `set_cookie` calls `wait_for_blocking_operation`, which **spins the main run loop** (`-[NSRunLoop acceptInputForMode:beforeDate:]`) waiting on WebKit's completion. tauri always delivers `WebviewMessage::SetCookie` on the main thread from inside tao's event handler, which holds `Handler.callback: Mutex` (non-reentrant). Whether the caller was on-main (inline) or off-main (queued) changes only _how_ the message arrives — it still executes under that lock, and the nested pump can flush a pending Core-Animation transaction → layer display → tao `draw_rect` → `handle_nonuser_event` → re-lock → `__psynch_mutexwait` forever. That's why it presented as cold-launch-only and intermittent: the deadlock needs a dirty CA layer pending at pump time, which webview construction reliably queues and a warm rewire usually doesn't. A `sample` of the hung process (not a crash log — it's not a crash) shows the whole re-entrant stack and is the fastest way to identify this class of hang. Fix shape: bypass wry, fire `WKHTTPCookieStore.setCookie(_:completionHandler:)` on the main thread but asynchronously, count completions, and do the follow-up work (navigate, read-back) from the last one — the completion lands on a normal, non-nested run-loop iteration, so the mutex is never re-entered. The same applies to reads: `cookies_for_url` pumps identically, so a "did the cookie land?" read-back must use async `getAllCookies`. General rule for this codebase: **any wry API named like a synchronous getter/setter on macOS may be a run-loop pump in disguise — grep for `wait_for_blocking_operation` before calling one from anywhere the main thread can reach.**
**Suggested destination**: Strategies.md; the mechanics are applied in `plugins/tauri-plugin-native-webview/docs/Lifecycle and Races Explanation.md` § "Cookie seeding must not pump the main run loop"

## fhir-r4 decodes a `uri` primitive to a `URL` on the fully-typed top level, so naive string-schema re-decode of `medicationCodeableConcept.coding.system` silently fails

**Discovered during**: claude/shoppers-drugmart-collector — adding Shoppers Drug Mart fallbacks (DIN/name/sig) to `medication-sponsorship-react`'s `MedicationRequest → MedicationView` adapter
**Learning**: `medication.ts` re-decodes loosely-typed slots (`medicationCodeableConcept`, `contained`, …) through narrow local `Schema.Struct`s "tolerant of both the wire and decoded shapes." That tolerance was a half-truth: a FHIR `uri` primitive stays a plain string on the wire and on loosely-typed `contained` resources, but the **fully-typed top-level** `MedicationRequest.medicationCodeableConcept.coding[].system` decodes to a `URL` instance (`sys instanceof URL === true`; `JSON.stringify` renders it unquoted). So a `Coding` struct with `system: Schema.String` returns `Option.none()` for the whole concept whenever a top-level coding carries a system — which silently disabled the existing `displayNameOf` coding-`display` fallback and blocked a new DIN-from-`coding[].code` fallback. The asymmetry is the tell: `dinOf` reads the **contained** Medication's `coding.system` and compares it `=== DIN_CODING_SYSTEM` fine (contained stays a string), while the same field on the top-level concept is a `URL`. Fix that keeps types clean and honours the module's stated intent: a `nullableUri` schema = `Schema.transform(Schema.Union(Schema.String, Schema.instanceOf(URL)), Schema.String, { decode: v => typeof v === 'string' ? v : v.href })`, used for `Coding.system`, so both shapes normalize to the string form and every `=== <system-uri>` comparison keeps working. General rule: when re-decoding an **already-decoded** fhir-r4 resource (not raw wire) through a permissive local schema, `uri`/`url`-typed fields are `URL`s, not strings — either coerce or read them as `Schema.Unknown`. `vp check` (typecheck) won't catch it; only a runtime decode of a resource carrying that field does.
**Suggested destination**: a slices/emr fhir-r4 "re-decoding decoded resources" gotcha doc, alongside the TS2883 dts entry

## `PageLoaded` never fires at all if `window.load` never fires — the settle ceiling only arms on `load`

**Discovered during**: claude/shoppers-drugmart-collector — debugging the 2FA `AwaitPageSettled` hold parking on a visibly-loaded health dashboard
**Learning**: The sniffer's settle watch (quiet window + `SETTLE_MAX_WAIT_MS` ceiling) is armed by the `load` listener, so the ceiling is a bound on _settling after `load`_, not on the page ever emitting. A page with one hanging resource (a stalled beacon, an image that never resolves) can sit interactive for minutes with `load` never firing — and then emits **no `PageLoaded` whatsoever**, so an `AwaitPageSettled` hold on it can only end via its own `timeout` (a 5-minute 2FA hold reads as a silent hang). Two structural consequences worth knowing: (1) the machine's `AwaitingPageLoaded` start-up state is _unbounded_ — no timer exists until the first settled `PageLoaded` starts the drain, so a first page that never settles parks the run with zero timeouts armed; (2) "the page is visibly up" and "the sniffer saw a settled load" are independent facts. The `PageRequested` bridge message (fired once per document at `DOMContentLoaded`) + the `AwaitPageRequested` hold exist for exactly this: gate on arrival when settlement may never come.
**Suggested destination**: browser-sniffer [Architecture Explanation](../../slices/browser-sniffer/docs/Architecture%20Explanation.md) § settlement already documents the emission; the hold-selection guidance is in the collector slice AGENTS Traps
