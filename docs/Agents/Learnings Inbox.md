## Workspace-wide `vp test` needs `vp run pack` first in a fresh container — unbuilt `dist/` fails hundreds of tests

**Discovered during**: claude/fhir-r4-openapi-spec-ibzynx — a full `vp test` showed 438 failures that had nothing to do with the change
**Learning**: Workspace packages' `exports` map `default` to `./dist/...`; only the `source` condition points at `src/`. Vitest resolves `source` for files _inside_ the project under test, but cross-package imports in some projects resolve to `dist/`, so on a fresh container (post `vp install`, nothing built) a workspace-wide `vp test` fails en masse with `Cannot find module .../dist/...` while any single package's suite (run from its directory) passes. Run `vp run pack` once first; after that the full suite is green. Corollary: a plain `node script.ts` importing a workspace package fails the same way — run one-off scripts as a temp test file through `vp test` instead.
**Suggested destination**: CLAUDE.md commands section, or docs/Testing/Testing Reference.md

## Re-driving `hfs_router` in-process: strip `Accept-Encoding` or the delegated sub-response comes back compressed and won't parse

**Discovered during**: claude/fhir-patient-everything-op-95ig70 — debugging a `$everything` 500 (`failed to parse sub-response JSON: expected value at line 1 column 1`)
**Learning**: `emr-rust`'s `$everything` handler (`patient_everything.rs`) delegates data-fetching by re-driving a clone of HFS's own router in-process (`router.clone().oneshot(sub_request)`), forwarding the caller's headers so auth/tenant resolution matches a direct request. But `helios-rest`'s `create_app_with_auth` wraps the router in a `CompressionLayer` (`compress_when(SizeAbove::new(32) & NotForContentType(parquet/zip))`) — so forwarding the real client's `Accept-Encoding: gzip, deflate, br` makes HFS gzip the sub-response body. The sub-request still returns **200**; the body is just compressed, so `serde_json::from_slice` fails at the first byte (`expected value at line 1 column 1` — column **1**, not 0, is the tell: non-empty body, invalid first byte = the `0x1f` gzip magic). Tests passed because their request helper never set `Accept-Encoding`. Fix: skip `header::ACCEPT_ENCODING` when copying headers into the sub-request — we consume the body in-process, not over the wire, so we always want it identity-encoded; the real client's `Accept-Encoding` is honored by the outer HTTP stack against our own response. General rule: any in-process `oneshot` re-drive of a router that carries a compression/content-negotiation layer must drop hop-by-hop / transfer-encoding-negotiation headers (`Accept-Encoding` first) from the forwarded set.
**Suggested destination**: unsure — a note near the `patient_everything.rs` module docs, or an emr-rust delegation how-to if one emerges

## `.local-notes` design-handoff HTML is a self-extracting bundle — the real markup lives in `__bundler/template` + `__dc_inline` JSON

**Discovered during**: claude/issue-256-implementation-ohs995 — matching the OAuth consent screen to the Scope Picker reference design
**Learning**: The standalone design files (e.g. `.local-notes/Scope Picker (standalone).html`, ~1.1MB) are not readable HTML — they're a JS bundler shell whose page is JSON-encoded in a `<script type="__bundler/template">` tag. Extract with a small node script (regex the tag, `JSON.parse`), then split again: the decoded page holds a `<script type="application/json" id="__dc_inline">` map of named sub-component templates (`PermissionStatement`, `FlagToggleRow`, …) plus the main page after the `</helmet>` (the helmet is a full inlined Tundra CSS copy — skip it). Each component is a mustache-ish `<x-dc>` template + a `DCLogic` class carrying the interaction model (state machine, serialization rules) — the class is worth reading, it specifies behavior, not just looks. The templates use the repo's real CSS custom properties (`--color-raised`, `--space-*`), so styles translate almost 1:1 to token-driven CSS modules.
**Suggested destination**: unsure (design-handoff how-to, if one emerges)

## Tauri `Webview::set_cookie` must not be called from a main-thread event handler; queue it from off-main and let FIFO order the navigate

**Discovered during**: claude/issue-256-implementation — seeding the owner `wf_auth` cookie into the native-webview popup
**Learning**: wry's macOS `set_cookie`/`cookies_for_url` block by re-entrantly pumping the main `NSRunLoop` (`wait_for_blocking_operation`) until the `WKHTTPCookieStore` completion fires. Tauri's `Webview::set_cookie` sends a `WebviewMessage::SetCookie` to the main loop — but `send_user_message` executes **inline** when already on the main thread, so calling it from inside a `run_on_main_thread` callback (or any event handler) nests the run-loop pump inside tao's event handler: observed as both child webviews' "web content process terminated" and a hard app deadlock. From a NON-main thread the message queues normally and the main loop handles it on a clean iteration. `SetCookie` has no reply channel (fire-and-forget), but the loop is FIFO — `set_cookie`, `set_cookie`, `navigate` queued in order guarantees every cookie commits before the navigation's first request. So: build the webview at `about:blank` on the main thread, then seed + navigate from the caller thread.
**Suggested destination**: plugins/tauri-plugin-native-webview/docs/Explanation.md (applied this session) / Strategies.md

## NSHTTPCookie boolean properties are presence-keyed: `cookie::Cookie::set_http_only(false)` makes the cookie HttpOnly on macOS

**Discovered during**: claude/issue-256-implementation — the JS-readable `wf_auth_exp` companion landed HttpOnly in the popup
**Learning**: The `cookie` crate records `set_http_only(false)` / `set_secure(false)` as `Some(false)`, and wry's macOS conversion (`cookie_into_wkwebview`) inserts the NSHTTPCookie `"HttpOnly"`/`Secure` property for **any** `Some`, with string value "TRUE"/"FALSE" — but Foundation keys off the property's _presence_, so a `Some(false)` cookie comes out HttpOnly. (The crate's `to_string()` renders `Some(false)` as no attribute, so `Set-Cookie`-based paths are immune; only the typed-Cookie → NSHTTPCookie path hits this.) When building a `cookie::Cookie` destined for `Webview::set_cookie`, set boolean attributes only when true and leave them `None` otherwise, and pin `cookie.http_only() == None` (not `Some(false)`) in tests.
**Suggested destination**: unsure (native-webview plugin docs; wry upstream issue candidate)

## Vite+ 0.2 upgrade: peer deps dodge `pnpm.overrides`; every plugin-hosting package must declare `vite: catalog:`; the vitest alias line is dead

**Discovered during**: vite-plus 0.1.21 → 0.2.2 / @vitejs/plugin-react 5 → 6 upgrade
**Learning**: Three coupled traps. (1) `pnpm.overrides` rewrites regular/dev/transitive deps but **not peer resolution** — a `vite` peer (`@vitejs/plugin-react`, `@tanstack/router-plugin`, `vite-plugin-singlefile`) binds to whatever `vite` the host package's own tree provides, and with `autoInstallPeers` an unprovided peer pulls **real** `vite@8` from the registry. With `nodeLinker: hoisted` that real vite wins the root `node_modules/vite` slot and every `defineConfig`/plugin call typechecks against mismatched `Plugin`/`UserConfig` types ("Excessive stack depth", "No overload matches"). Fix: every package that hosts a vite plugin declares `"vite": "catalog:"` (the catalog aliases it to `@voidzero-dev/vite-plus-core`), same as `wildflower-tauri` always did; the `pnpm.overrides` pin still matters for regular deps like vitest's own `vite` dependency. Verify with `vp why -r vite` — real `vite@x.y.z` should have zero dependents. (2) vite-plus 0.2.x depends on **real `vitest`** — the `@voidzero-dev/vite-plus-test` alias line ended at 0.1.24, so bumping the old catalog alias to `^0.2.2` is unsatisfiable (`ERR_PNPM_NO_MATCHING_VERSION`); pin `vitest` to the version `vp --version` reports instead. (3) The core alias ships **no `vite` bin** — `"dev": "vite"` scripts only ever worked via the accidentally-installed real vite (a stale `node_modules/.bin/vite` symlink); scripts must use `vp dev` / `vp build` / `vp preview`.
**Suggested destination**: docs/Dependencies/Version Override Explanation.md (partially applied this session) / Strategies.md

## Cookie-auth: clients are tokenless; the `AuthStateStore` subscribable is only a readiness signal

**Discovered during**: claude/github-issue-218-42hl8q — Part A (cookie-based auth on the web path); later fully tokenless under #218
**Learning**: No HTTP client attaches an `Authorization` header anymore — auth rides the same-origin `HttpOnly` `wf_auth` cookie the browser sends automatically (`FetchHttpClient` defaults to `credentials: 'same-origin'`). There is no client-side token-injection Tag; `defineSliceHttpClient` and every bespoke client build a plain tokenless `HttpApiClient.make(api)` requiring only `HttpClient.HttpClient`. The `AuthStateStore` `subscribable` survives but purely as the auth-readiness _signal_: it feeds `AuthStateProvider`, the `auth-ready` gate, and the token-rotation cache invalidator — never a request header. On web that signal is the non-secret `exp` hint from the readable `wf_auth_exp` companion cookie; on embedded/Tauri it's the host-pushed real JWT. Because nothing reads it as a header, the web `exp`-hint value is harmless (no risk of `Authorization: Bearer <exp-digits>`). `NeedsAuthMessage` stays env-agnostic — its `setToken(access_token)` is interpreted by the web store as "re-derive from the cookie, ignore the arg" (it then full-page-reloads), and the embedded store stores the real JWT. Don't push env branching into the shared component.
**Suggested destination**: Auth Token Storage Explanation.md (updated this session) / unsure

## rathole's `"Unable to listen for shutdown signal: channel closed"` is a teardown symptom, not a cause

**Discovered during**: claude/pr-202-tunnel-seam — debugging tunnel launch flap
**Learning**: We build `rathole` with `default-features = false` (no `notify`/`hot-reload`), so rathole's config watcher is the stub variant that does nothing but `await` the `broadcast::Receiver<bool>` shutdown we hand `rathole::run(cli, shutdown_rx)`. rathole's `run()` therefore ends — tearing down the control channel and logging `"Unable to listen for shutdown signal: channel closed"` from `client.run` — the instant **our** `shutdown_tx` drops, which happens when the supervisor's `run_once` future is dropped on cancel. So that error means "the supervisor got cancelled," i.e. a reconcile cancelled it — chase _what issued the reconcile_, not the rathole error. Confirmed by logging which `select!` branch `run_once` takes (`cancel.cancelled()` fired). The verify-deadline-too-tight theory was a red herring: the tunnel verifies in ~1s; it's the flap (cancel → re-dial) that breaks launches.
**Suggested destination**: unsure (tunnel-rust relay_clients/rathole.rs context)

## `reconcile` must not re-dial a live tunnel on a no-op settings revision bump

**Discovered during**: claude/pr-202-tunnel-seam — tunnel flap fix
**Learning**: Any newer settings revision made the tunnel daemon's `reconcile` cancel the live supervisor and re-dial from scratch — even when the _dialable_ config (relay + public_host) was unchanged. That tears rathole down (drops in-flight requests, flaps the public origin) on every redundant write (a settings re-save, a `requestedRunning` re-assert). Fix: `SupervisorHandle` carries the `relay_settings`/`public_host` it's driving; `reconcile` returns early (keeps the live tunnel) when the incoming revision is still `requested_running` with the same relay + host. The persisted/wire revision still advances (the `/tunnel` response reads it from the DB settings, not the watch), so leaving the watch's `settings_revision` at the supervisor's value is correct and keeps its `set_state` supersession check intact.
**Suggested destination**: unsure (tunnel-rust domain/tunnel_daemon.rs context)

## Tauri host `emit` echoes back to host `listen` on the same event — bridge handlers must filter by tag

**Discovered during**: claude/pr-202-tunnel-seam — wiring the apps RequestTunnel bridge handler for Tauri
**Learning**: The webview↔host bridge multiplexes every tag onto one Tauri event (`shared_structures_rust::bridge::BRIDGE_EVENT`). A host listener registered with `app.listen(BRIDGE_EVENT, …)` also receives the host's own `app.emit(BRIDGE_EVENT, …)` replies, so a web→host handler must decode the envelope `_tag` and act on _only_ its inbound tag (e.g. `RequestTunnel`), dropping host→web echoes and sibling-slice traffic — otherwise it loops on its own replies. Host→web wire types live in the slice's `*-rust::bridge` module (e.g. `AppsHostToWeb`, mirroring `GatekeeperHostToWeb`) and are byte-pinned to the TS `Schema.parseJson(Schema.TaggedStruct(...))` shapes in `*-core/src/bridge.ts` with golden serde tests; Tauri's struct-`emit` matches `parseJson` (verified against the working gatekeeper bridge). The `RequestTunnel` handler must be attached where the `TunnelService` exists (in `run_server`, not the sync `setup()`), so thread an `AppHandle` through.
**Suggested destination**: unsure (apps bridge / Tauri host wiring)

## Slice-standalone route files: `Route.useRouteContext()` widens to `any` without a registered Router; annotate `select`

**Discovered during**: ruthmarks/tanstack-inmemory-foundation — tunnel/apps migration onto router-context `runAuthed`
**Learning**: A `*-react` slice's route file (`createFileRoute(...)`) type-checks BOTH standalone (`vp run --filter <slice> check`) and when mounted under `apps/wildflower-react`. `Route.useParams()` is typed in both (params come from the route's own path). `Route.useRouteContext()` is NOT — in the slice's standalone build there is no `declare module '@tanstack/react-router' { interface Register }` (the slice never calls `createRouter` for a real app), so `RegisteredRouter` falls back to `AnyRouter` and an un-`select`ed `Route.useRouteContext()` returns `any` → `typescript(no-unsafe-assignment)` under oxlint. Fix WITHOUT a cast: give the slice a structural `XRouterContext` (`{ queryClient; runAuthed }`, re-declared per Issue #101, NOT imported from the app), make the slice's `__root.tsx` use `createRootRouteWithContext<XRouterContext>()`, and read context via an ANNOTATED select: `Route.useRouteContext({ select: (c: XRouterContext) => c.runAuthed })`. The annotation makes the result a typed value; the app build (which DOES register the router) sees the structurally-equal shape. The loader's `({ context })` is fine — it's typed from the route's resolved context chain, not the Register.

## Embedded WebView token lands AFTER `transport.flushed`; authed route loaders can 401 because the auth gate is a React component, not `beforeLoad`

**Discovered during**: ruthmarks/tanstack-inmemory-foundation — adding a tunnel route loader
**Learning**: In `wildflower-react` the `_auth` / `/settings` auth gates are React-COMPONENT gates (`AuthorizedAppShell`/`SettingsLayout` → `RequireAuth`, which reads the token reactively and renders `<NeedsAuthMessage>` when absent), NOT `beforeLoad` gates. TanStack `loader`s run during routing, before those components render — and `<TransportProvider>` (which blocks the React tree until the gatekeeper-bridge handshake delivers the token via `AuthTokenIssued`, post-`transport.flushed`) sits BELOW `<RouterProvider>`. So an authed loader on an admin route fires on embedded first paint BEFORE the token exists and 401s. `authTokenRef` reads `localStorage` synchronously at module load, so on standalone web the token is present immediately, but embedded has no localStorage token until the bridge writes it. Mitigations used: (1) eager startup prefetch is gated on `Effect.runSync(authTokenRef.get)` being non-null/non-empty (skips on embedded first paint); (2) the route loader's `ensureQueryData` is wrapped in try/catch so a failed prefetch is non-fatal — navigation proceeds and the in-component `useSuspenseQuery` (rendered only once `RequireAuth` sees the post-flush token) does the first read. `waitForHostTokenRef` (gatekeeper-react) is the readiness flag the gate consults but is not currently consumed by loaders.

## Page headers: one `<PageHeader>` per page (fixed-parent back link); externally-published flows get an inside-`/settings` twin rather than moving

**Discovered during**: festive-hamilton — back buttons + header audit across wildflower-react
**Learning**: The web app's per-page headers are unified by a single generic `PageHeader` (`global/react-tundraish`): a one-line, ellipsis-truncating title, an optional trailing `actions` slot, and an optional `backHref` that renders a TanStack `<Link>` to the page's **fixed logical parent** (NOT `history.back()` — a fixed parent is deterministic on a refreshed/deep-linked/OAuth-redirect landing where there's no in-app history to pop). Rule: every screen renders exactly one `PageHeader` as the first child of its page shell; the three tab surfaces (`/home`, `/collector`, `/settings`) omit `backHref`, everything else sets it. The old double-header came from the `/settings` _layout_ rendering a persistent `<h1>Settings</h1>` on top of each child's own heading — fixed by moving "Settings" into the index page so the layout owns no heading. `react-tundraish` can use `<Link to={stringVar}>` because it compiles without the app's `Register` augmentation, so `to` stays `string` (same reason `ItemList` does it) — no cast, and consumers pass plain path literals.

The device-authorization flow showed the right move when a settings page would otherwise need an externally-published URL: `/gatekeeper/devices` is the RFC 8628 `verification_uri`, built in BOTH `gatekeeper-core/page-paths.ts` AND `gatekeeper-rust/http/page_paths.rs` (drift-tested; `routes.test.tsx` asserts "settings landings are not externally published"). Instead of moving it into `/settings` (which would change the verification*uri shown on other devices and touch Rust), **lift the inner form out of the route** (`screens/device/device-code-entry-form.tsx`, `device-consent-screen.tsx` — header-less, parameterized by `onSubmit`/`onDone`) and render it from TWO routes: the public `/gatekeeper/devices*`(no back link) and an owner-facing twin`/settings/gatekeeper/devices*`(back link to the access page, reached from the "Authorize a Device" row). Same inner content, different chrome; the published URL and Rust stay untouched. Generalizes the existing`requests`/`requests*`sibling-route trick: name the consent twin`devices\_.$userCode.tsx`so it doesn't nest under the headerless`devices.tsx` entry route.
**Suggested destination**: docs/UI/Settings Fragments How-To.md (the outside/inside twin pattern) + a UI headers reference if one emerges

## Cross-language (TS/Rust) semantics contract via a shared JSON fixture at the slice root

**Discovered during**: claude/core-ui-events-4crpo0 — review follow-ups pinning the scopes-core ↔ scopes-rust grammar mirror
**Learning**: When the same domain grammar is implemented twice (TS `scopes-core` + Rust `scopes-rust`), prose "mirrors scopes-rust" doc comments don't stop drift — a shared vector file does. Pattern: put the fixture at the slice root (`slices/scopes/scope-test-vectors.json`), consume it from Rust with `include_str!(concat!(env!("CARGO_MANIFEST_DIR"), "/../scope-test-vectors.json"))` in a `tests/*.rs` integration test (parse with `serde_json::Value` — no derive needed, so no serde `derive` feature question), and from TS with a plain `import vectors from '../../scope-test-vectors.json'` (works fine outside the tsconfig `include` seed; `resolveJsonModule` is already on repo-wide). Encode both parse cases (`scope → kind + canonical rendering`) and semantics cases (`allowed/requested → covers`). Where the two sides partition differently (TS splits fhirV1/fhirV2, Rust has one FhirResource variant), keep the finer-grained kind in the fixture and coarsen in the Rust consumer's match. Gotcha: root `vp check` formats JSON files too — run `vp check --fix` after authoring the fixture or the root check fails on formatting.
**Suggested destination**: docs/Testing/Testing Reference.md (cross-language contract tests)

## oxfmt parses `.hbs` files as markup — exclude served template trees from `fmt` or `vp check` fails before analysis

**Discovered during**: claude/handlebars-static-app-templates-2ia3yl — adding the handlebars template tree to self-hosted-apps-rust
**Learning**: oxfmt (the `vp check`/pre-commit formatter) treats `*.hbs` as an HTML-ish template language and hard-fails on non-markup content before any analysis starts — e.g. a json5 comment containing `<public_host>` reads as an "Unclosed element" SyntaxError, killing the whole `vp check` run (and with it `vp staged` in the pre-commit hook). Even when it parses, reformatting would mangle `{{…}}` expressions and the json5 payload they render into. Fix: add the template tree (`slices/apps/self-hosted-apps-rust/templates/**`) to `fmt.ignorePatterns` in the root `vite.config.ts` — these are served runtime assets, not source. Same reasoning as the existing `**/openapi/*.openapi.json` and `**/*.toml` exclusions.
**Suggested destination**: unsure (vite.config.ts fmt commentary already carries it)

## Pre-commit "Task killed: vp check --fix" usually means a SIBLING staged task failed (e.g. cargo fmt --check)

**Discovered during**: claude/self-hosted-apps-rust-design-t4teg2 — apps-rust domain refactor
**Learning**: `vp staged` (the pre-commit hook) runs its per-glob tasks concurrently and, when one fails, kills the others — the summary line then reads `✖ Task killed: vp check --fix`, which points at the _victim_, not the culprit. When Rust files are staged, the real failure is usually `rust.sh pre-commit`'s `cargo fmt --check` printing "Diff in …" blocks further up the output (hand-written Rust that isn't rustfmt-clean). Standalone `node_modules/.bin/vp check --fix` passing while the hook keeps failing is the tell. Fix: run `cargo fmt`, restage, and commit; scroll up past the kill line for the actual diffs. Two side gotchas from the same session: (1) `vp check --fix` run standalone can reformat files _after_ you staged them, so restage before retrying; (2) don't run a background `cargo check` concurrently with a commit — the hook's rust.sh contends on the cargo target lock.
**Suggested destination**: CONTRIBUTING.md git-hooks section (or the Vite+ block in AGENTS.md)

## `Equal.equals` silently degrades to reference equality on classes that don't implement `Equal` — check before adopting it

**Discovered during**: claude/issue-256-implementation-ohs995 — consent-screen refactor moving scope editing onto domain objects
**Learning**: Effect's `Equal.equals(a, b)` never fails on a class that doesn't implement `Equal.Equal` — it falls back to reference equality and returns `false` for two structurally identical instances. In `scopes-core` the domain classes implement `[Equal.symbol]`/`[Hash.symbol]` selectively: `KnownScope`, the contexts (via the `Context` base), and the resource types did, but `UnknownScope` did not — so a draft-membership check like `draft.unknown.some(Equal.equals(scope))` type-checked, looked idiomatic, and always returned `false` (parsed instances are never reference-equal), turning a toggle into an append-duplicates bug. Before writing `Equal.equals` against a domain class, verify the class (or its base) implements `Equal.Equal`; when adding a new sibling variant to a family where the others are value-comparable, implement `Equal`/`Hash` at the same time (compare `kind` + payload, mirror the sibling's shape). The fix belongs in the domain class, not at the call site — serialize-and-compare call sites are the workaround smell.
**Suggested destination**: docs/Effect/Patterns Reference.md (value equality on domain classes)

## `Schema.declare` combinators need `arbitrary` AND `equivalence` annotations before tests can generate/compare through them

**Discovered during**: claude/emr-fhir-r4-migration-5lh030 — deleting emr-core and porting fhir-r4 schema tests to generate from the wire schemas
**Learning**: A `Schema.declare(...)`-based combinator (kitchen-sink's `OrNullAsOptional`/`OrNullAsUndefined`, fhir-r4's choice-slot null stub) derives nothing: `Arbitrary.make` throws `MissingAnnotation` and `Schema.equivalence` silently falls back to reference equality, so `toSchemaEqual` reports "Values are not schema-equivalent … no visual difference" for structurally identical values. This stayed hidden for as long as tests generated/compared via the plain-Struct emr-core row schemas; the moment the wire schemas became the only schema tree, every property test failed at once. Fix at the combinator, not per call-site: `.annotations({ arbitrary: (inner) => (fc) => fc.oneof(fc.constant(null), inner(fc)), equivalence: (inner) => (a, b) => a === null || b === null ? a === b : inner(a, b) })` — declaration annotations receive the type-parameters' derived arbitraries/equivalences as arguments. Rule of thumb: any new `Schema.declare` that will appear inside property-tested schemas ships with `arbitrary` + `equivalence` annotations from day one.
**Suggested destination**: docs/Effect/Patterns Reference.md (Schema.declare checklist) or docs/Testing/Property Testing Reference.md

## Opaque cross-boundary JSON columns: `#[schema(value_type = Value)]` is the drift-safe way to spec them

**Discovered during**: claude/pr-343-diesel-rewrite — collector-rust (diesel) storing the TS-owned `CollectorConfig` union verbatim
**Learning**: When a Rust slice stores/serves a JSON payload whose schema is TS-owned (e.g. `collector_remotes.config`, the tagged `CollectorConfig` union), the utoipa annotation on the field must be `#[schema(value_type = Value)]`, which emits an **empty schema `{}`**. The openapi-drift engine normalizes `{}` to `any` (a wildcard that matches whatever the TS side declares — today a single-member union, later a widened one) so adding a TS collector never breaks the drift gate. `value_type = Object` is NOT equivalent: it emits `{"type":"object"}`, which normalizes to an object with zero fields and drifts against the client's concrete union ("field on client, MISSING from server"). This holds regardless of how the column is stored on the Rust side: whether the field is a plain `serde_json::Value` mapped to a diesel TEXT column (config JSON round-tripped through `serde_json::to_string`/`from_str`) or a `#[serde(transparent)]` newtype — the wire shape is the raw inner value, and `value_type = Value` documents exactly that opacity.
**Suggested destination**: docs/Effect/OpenAPI Spec Drift How-To.md (gotchas section)

## Diesel 2.2 `serde_json` feature has no SQLite `Json` support — map JSON columns via a `Text` newtype + `serialize_as`/`deserialize_as`

**Discovered during**: claude/pr-343-diesel-rewrite — making collector-rust's `Remote` the diesel model directly (removing the internal row struct)
**Learning**: Diesel 2.2's `serde_json` feature only wires `serde_json::Value` ⇄ the `Json` sql type on the Postgres and MySQL backends; `FromSql`/`ToSql<Json, Sqlite>` landed in diesel 2.3 (`src/sqlite/types/json.rs` doesn't exist in 2.2.12), which the workspace deliberately pins away from. On the 2.2.x line the pattern is a thin `#[derive(AsExpression, FromSqlRow)] #[diesel(sql_type = Text)]` newtype over `serde_json::Value` with hand-written `ToSql`/`FromSql<Text, Sqlite>` (compact `to_string()` out, `from_str` in — corrupt TEXT surfaces as a diesel deserialization error, not a panic), plugged into the model with `#[diesel(serialize_as = X, deserialize_as = X)]` so the field itself stays a plain `serde_json::Value`. Two follow-on gotchas: (1) `serialize_as` converts via `Into`, which consumes the value, so diesel stops generating the borrowed `Insertable` impl — `.values(&model)` becomes `.values(model.clone())`; (2) the newtype appears in the model's public `Queryable`/`Insertable` impls, so it must be `pub` (E0446 otherwise). Binding as TEXT keeps a STRICT `TEXT` column happy, and utoipa doc comments feed OpenAPI `description` strings — editing a spec'd type's rustdoc means regenerating the snapshot even when the schema shape is untouched.
**Suggested destination**: a diesel/persistence how-to if one emerges, or promote alongside the `value_type = Value` entry above

## Pooling a diesel `:memory:` database needs a shared-cache URI + a resident connection — each pooled connection otherwise gets its own empty db

**Discovered during**: claude/pr-343-diesel-rewrite — moving collector-rust off a single `Arc<Mutex<SqliteConnection>>` onto an app-wide diesel r2d2 pool (`persistence_rust::open_pool` / `DieselPool`)
**Learning**: An r2d2 pool over the diesel URL `":memory:"` gives every pooled connection its OWN private in-memory database, so a migration (or any write) on one checkout is invisible to the next — tests that pass with a single connection break the moment the store checks out a second. Fix: a shared-cache URI, `file:<unique-name>?mode=memory&cache=shared` (unique per pool via an `AtomicU64` counter so tests stay isolated). diesel's `SqliteConnection::establish` accepts `file:` URIs verbatim — libsqlite3-sys opens with `SQLITE_OPEN_URI`, no extra flags. Lifetime subtlety: a shared-cache in-memory db exists only while ≥1 connection to it is open, so the pool must hold one resident — r2d2 defaults `min_idle` to `max_size` and establishes them eagerly at `build()`, which keeps the db alive for the pool's lifetime (rely on that rather than tearing down to zero idle). This is the diesel counterpart of `persistence_rust::Connection::open_in_memory`, and it lives in persistence-rust as `open_in_memory_pool()` (public, non-test — same as the rusqlite one — so every diesel-backed slice's tests can reuse it). For the on-disk pool test, prefer a `tempfile::tempdir()` path over `:memory:` so the cross-connection round-trip actually exercises one shared file. Query a pooled connection's pragmas in a test via `diesel::sql_query("SELECT timeout AS value FROM pragma_busy_timeout()")` with a `#[derive(QueryableByName)]` scalar struct (the `pragma_*()` table-valued functions are available in the bundled SQLite).
**Suggested destination**: a diesel/persistence how-to if one emerges, or alongside the other PR-343 diesel entries above

## Moving an already-shipped table from the persistence-rust runner to diesel migrations needs idempotent DDL (`IF NOT EXISTS` / `INSERT OR IGNORE`)

**Discovered during**: claude/rust-slices-standardization-odf5e2-tunnel — migrating tunnel-rust's `TunnelStore` off rusqlite + the namespaced `run_migrations` runner onto the app-wide diesel pool + embedded diesel migrations
**Learning**: When a slice's table was created by the retired `persistence_rust::run_migrations` runner (bookkept in `schema_migrations`) and you re-express it as a diesel embedded migration (bookkept in the disjoint `__diesel_schema_migrations`), diesel sees version `0001` as un-applied on every pre-existing database and runs its `up.sql`. A verbatim `CREATE TABLE` (what a brand-new slice like collector uses) then fails against the already-present table. The transition-safe form is idempotent DDL — `CREATE TABLE IF NOT EXISTS …` + `INSERT OR IGNORE INTO … (id) VALUES (…)` for a seeded singleton — so `0001` is a no-op on an upgraded database while still creating the table + seed on a fresh one (byte-for-byte the schema the old runner produced). This only matters for tables that predate the diesel move; a genuinely new table keeps the plain `CREATE TABLE`. Worth a regression test that runs the embedded migrations against a hand-created legacy table and asserts the existing singleton row is neither duplicated nor overwritten.
**Suggested destination**: a diesel/persistence how-to if one emerges, or alongside the other diesel-migration entries above

## Diesel's stock migration harness shares one un-namespaced `__diesel_schema_migrations` — a second diesel slice's `0001` silently masks the first

**Discovered during**: claude/rust-slices-standardization-odf5e2-tunnel — reviewing/fixing PR #354, which made tunnel-rust the _second_ diesel-backed slice to run its embedded migrations against the app-wide shared pool (collector was the first)
**Learning**: `MigrationHarness::run_pending_migrations` records applied versions in a single, **un-namespaced** `__diesel_schema_migrations` table keyed by the migration _version_ (the directory-name prefix before the first `_`). Every slice here starts its history at `0001_initial_schema`, so when a second diesel slice runs migrations against the _same_ shared database, diesel sees version `0001` already applied and **skips the second slice's migration entirely** — its table is never created and the app fails to boot on a fresh install (idempotent `IF NOT EXISTS` DDL does NOT rescue this: the migration is skipped, never run). It's order-independent (whichever `setup_*` runs first wins `0001`; the loser's later migrations then fail against a missing table) and invisible to per-slice unit tests, which each use an isolated in-memory pool where only that slice's migrations run — only the shared-pool host wiring (which can't build without GTK in the dev env) exercises the clash. This is the diesel counterpart of the collision the rusqlite `persistence_rust::run_migrations` runner has always prevented with a per-`namespace` `schema_migrations` table. The false-comfort tell is a "the two bookkeepers coexist with no collision" doc comment that only reasons about the rusqlite `schema_migrations`, never about a _second diesel slice_. Fix: `persistence_rust::run_diesel_migrations(conn, namespace, source)` — a namespaced diesel runner enumerating a `MigrationSource<Sqlite>` and tracking applied versions per `(namespace, version)` in `diesel_slice_migrations` (each pending migration + its bookkeeping row applied in one transaction). Every diesel slice calls it with its own namespace; nothing uses stock `run_pending_migrations`. Regression test lives in persistence-rust: two fixture trees both named `0001_initial_schema` run under different namespaces and both apply.
**Suggested destination**: a diesel/persistence how-to if one emerges, or alongside the other diesel-migration entries above

## Orphan rule blocks diesel `serialize_as`/`deserialize_as` on `Option<foreign>` fields — mirror that one table with a private db row struct

**Discovered during**: claude/rust-slices-standardization — gatekeeper-rust's rusqlite→diesel store migration
**Learning**: The PR-343 `Text`-newtype pattern (`#[diesel(serialize_as = X, deserialize_as = X)]` on a plain domain field) extends fine to typed inners (`Vec<String>`, `Url`, enums) — but ONLY for non-`Option` fields. A nullable column whose field is `Option<Url>` would need `impl From<Option<UrlText>> for Option<Url>` (and the reverse), and `Option` is neither local nor `#[fundamental]`, so coherence rejects the impl. Don't fight it per-field: give that one table a private `#[derive(Queryable, Selectable, Insertable)]` row struct in `db/` whose fields ARE the wrapper types (`Option<UrlText>`, `Option<JsonStrings>` — the blanket `Option<T: ToSql/FromSql>` impls cover Nullable), plus `From` conversions to/from the domain type at the query boundary. In gatekeeper only `authorization_requests` needed this; every other table maps its domain struct directly. Two adjacent findings: diesel 2.2's `chrono` feature maps `DateTime<Utc>`/`Option<DateTime<Utc>>` natively on SQLite (`TimestamptzSqlite`, text `%F %T%.f%:z` — lexicographic order stays chronological, and `%F %T%:z` literals in SQL seeds parse fine), removing any need for timestamp wrappers; and `thiserror` treats an enum field literally named `source` as the structured error source (must impl `Error`), so a collector-style `Backend { context, source: String }` variant needs hand-written `Display`/`Error` impls instead of `#[derive(thiserror::Error)]`.
**Suggested destination**: alongside the PR-343 diesel entries / a diesel persistence how-to if one emerges

## A `GatekeeperStore` transaction seam (GAT `type Tx` + `with_connection`/`transaction`/`immediate_transaction`) lets multi-statement logic live in the pure domain

**Discovered during**: claude/gatekeeper-store-transactions — splitting gatekeeper-rust's persistence port so composed operations move out of the store
**Learning**: A CRUD-only store port (collector/tunnel) needs no transaction seam, but gatekeeper accreted seven "specialized" store methods (`upsert_*_grant`, `revoke_grant_and_expire_client_families`, `consume_refresh_token`, the three `expire_*`) purely because a multi-statement operation had to be atomic and the store was the only place a transaction could live — so their business logic (scope-union read-merge-write, delete-both-then-expire, the three-state consume) was reachable only through SQLite and duplicated in the in-memory fake. The fix is to split the port into `GatekeeperTx` (single-statement primitives, `&mut self`) plus a seam trait `GatekeeperStore { type Tx<'a>: GatekeeperTx; fn with_connection/transaction/immediate_transaction(f: impl FnOnce(&mut Self::Tx<'_>) -> Result<T, E>) }`, and compose the compound operations in `domain/actions` inside those closures. Load-bearing details: (1) the elided `&mut Self::Tx<'_>` in the closure bound is **higher-ranked** (`for<'a>`), so pass closures `|tx| tx.foo()` — a bare fn-item path `GatekeeperTx::foo` fails to unify; (2) diesel's `Connection::transaction`/`SqliteConnection::immediate_transaction` require `E: From<diesel::result::Error>` even when the closure body maps its own query errors (BEGIN/COMMIT can still fail raw), so add `impl From<diesel::result::Error> for GatekeeperError` in the `db` layer to keep `domain::error` diesel-free; (3) `SqliteConnection::immediate_transaction` is inherent on `SqliteConnection` and hands the closure `&mut SqliteConnection`, while `Connection::transaction` on a `PooledConnection` hands back `&mut PooledConnection` — deref the pooled conn to `&mut SqliteConnection` up front so both runners and every `db/*` free fn share one connection type; (4) keep the `GatekeeperStore` default methods (each `self.with_connection(|tx| tx.op())`) so existing standalone call sites are untouched and lone reads stay autocommit (no write lock); (5) `type Tx<'a>` on a `pub` trait makes the concrete `SqliteGatekeeperTx` public interface — it must be `pub` (E0446); (6) the self-contained `expire_*` bodies keep their own `conn.transaction` wrapper and nest safely as **savepoints** when composed inside an outer domain transaction, so they need no decomposition; (7) the `BEGIN IMMEDIATE` lock-at-read property that prevents lost scope-unions must ride the seam explicitly (`immediate_transaction`) — it silently regresses if a composed upsert uses the deferred `transaction`. The fake models rollback by snapshotting all maps before `transaction`/`immediate_transaction` and restoring on `Err`; it cannot model real lock contention, so the concurrency-safety tests (guarded-update, lost-update) stay SQLite-backed in `crate::db` while the orchestration/merge logic gains fast fake-based coverage in `domain::actions`.
**Suggested destination**: an Effect/persistence "store transaction seam" how-to if one emerges, or alongside the diesel persistence entries above

## Parallel subagents in one checkout: `git mv` auto-stages, so an unrelated commit sweeps the renames in

**Discovered during**: claude/rust-packages-audit-nmbqs7 — three subagents editing disjoint crates in the same checkout
**Learning**: `git mv` stages the rename immediately (unlike content edits, which stay unstaged). When one workstream commits with `git add <its-paths> && git commit`, a _concurrent_ workstream's already-staged renames ride along even though no path under them was added — the commit picks up everything in the index, and `git commit -- <paths>` is the only form that restricts it. The committed tree then holds renamed files whose `mod` declarations (unstaged content edits) are missing, i.e. HEAD doesn't compile. Recovery before pushing: `git reset --soft <base>`, `git restore --staged <other-workstream-paths>`, then re-commit with explicit `git commit -- <paths>` pathspecs. Prevention: parallel agents belong in worktrees (`.devcontainer/wf-worktree.sh`); if they do share a checkout, every commit during concurrent work should use `git commit -- <paths>`, and treat "renames from a crate I didn't touch appear in my commit stat" as the tell.
**Suggested destination**: Strategies.md (parallel-agent hygiene), or CONTRIBUTING.md git workflow

## Building schemas from another package's reused datatypes breaks `vp pack`'s dts (TS2883) — the producer must export the named interfaces at top level

**Discovered during**: claude/github-issue-335-2lac0i — the new `fhir-stu3-as-r4` slice (and `rexall-be-well-collector`) reuse `fhir-r4/data-types` schemas
**Learning**: When a package builds new Effect `Schema.Struct`s that spread/reference another package's datatype schemas (e.g. `...DomainResource.fields`, `Extension.Schema`), the struct's _inferred_ decoded type embeds that package's named interfaces (`ExtensionType`, `ReferenceType`, `IdentifierType`). If the producer only exposes them through a namespace re-export (`export * as Extension` + `type ExtensionType as Type` → `Extension.Type`), `tsgo`'s declaration emit can't map the raw interface back to that path and `vp pack` fails with TS2883 ("cannot be named without a reference to 'ExtensionType'") — even though `vp check` (typecheck only) stays green, because the leak only bites at `.d.ts` generation. The clean fix is on the _producer_ side: add a direct top-level re-export of each named interface (`export type { Type as ExtensionType } from './…/extension.ts'`, `export type { ReferenceType, IdentifierType } from './…/identifier-and-reference.ts'` in `data-types/index.ts`). With a top-level name to reference, the consumer's plain `typeof Struct.Type` / `typeof Struct.Encoded` annotations pack cleanly — no hand-written wire interfaces needed. (Hand-rolling explicit `Type`/`Encoded` interfaces in the consumer also works but is far more code, and forces you to also _export_ every `Encoded` interface or a Bundle/wrapper referencing them fails with TS4023.) The same bite recurs for _wrapper/factory_ return types: `rexall-be-well-collector` calling `Bundle.searchsetBundle(...)` embeds `BundleValue` from `fhir-r4`'s `resources/bundle.ts`, so that too now has a top-level re-export (`export type { BundleValue } from './resources/bundle.ts'` in `data-types/index.ts`) — whenever a consumer's inferred type names an internal interface, re-export it flat from the producer. `vp check` won't catch any of this; run `vp pack` on the consuming package.
**Suggested destination**: docs/Testing or a slices/emr dts how-to; relevant to any slice reusing `fhir-r4` schemas
