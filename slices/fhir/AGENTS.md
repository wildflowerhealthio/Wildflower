# AGENTS.md — slices/fhir

FHIR R4 slice: pure wire schemas (Patient / Practitioner / Observation / DiagnosticReport / MedicationRequest / MedicationDispense / DocumentReference / Binary / ServiceRequest / ImagingStudy / CarePlan / Goal / PlanDefinition / Procedure), the `HttpApi` description, and the HTTP client for the off-the-shelf HFS FHIR server embedded by `fhir-r4-rust`; and `fhir-ca-infoway`, Canada Health Infoway's provincial health card naming systems and how a printed health card number becomes an `Identifier` ([its AGENTS.md](./fhir-ca-infoway/AGENTS.md)). Read the [Packages Explanation](./docs/Packages%20Explanation.md) before restructuring anything here.

## Guardrails

- **The server is HFS, not TypeScript.** `fhir-r4-rust` embeds the HeliosSoftware/hfs crates and is served at the server's root, on FHIR paths, by `wildflower-server-rust`. There is no TS server implementation; `fhir-r4` is a description + schemas + client only. Don't add server handlers back to the TS side.
- **`fhir-r4` deliberately breaks the `-core` naming convention.** It is a wire-protocol package that never grows platform adapters, so it takes no suffix. It depends on no other fhir package.
- **`fhir-r4/clients` owns writing to the store: one resource (`upsertResource`), one batch of PUTs (`persistResources`), one batch or transaction Bundle (`persistBatchBundle`, `persistTransactionBundle`), and one server-diff probe (`classifyAgainstServer`) — all reporting outcomes as data.** The batch sinks live here rather than in the importer slice because they need `upsertResource` and the typed client, while `importer-fundamentals` is deliberately FHIR-agnostic. **They take no options.** The writes are this package's, so the spans they emit (`fhir.persist.write` / `fhir.persist.bundle` / `fhir.persist.classify`) and the attributes they tag (`fhir.resource.type`, `fhir.persist.resource_count`) are named in this package's own telemetry catalog — a caller cannot make one write report itself as two different operations. `ResourceWriteFailure` (from `persistResources`) is likewise declared here rather than imported, because this slice sits below its consumers and cannot name them; a consumer checks the two against each other at its own call site.
- **`persistResources` vs `persistBatchBundle` vs `persistTransactionBundle` — pick by transport shape, not by convenience.** `persistResources` fans one PUT out per resource with bounded retries + concurrency (a real-time sync loop — dozens of small writes over the lifetime of a session, each with its own attempt count on the trace), reporting only the failures as `ResourceWriteFailure[]`. `persistBatchBundle` submits one `POST /` `batch` Bundle carrying N PUT entries in a single round trip, each entry landing on its own, and reports the **whole** per-entry result as `BatchEntryOutcome[]` — one per resource handed in, at its position, one entry per `Type/id` on the wire — each one's echoed status, whether it succeeded, and any OperationOutcome diagnostics (parsed from `Bundle.entry.response.outcome`) — so a results view can show what wrote alongside what did not, grouped by response code. `persistTransactionBundle` submits the same entries as a `transaction` Bundle, which the server applies as one unit or refuses whole (HFS on SQLite runs it atomically; `fhir-r4-rust`'s `batch_bundle_at_base` tests pin that), reporting the same per-entry outcomes, every one failed under the refusal's own status and its OperationOutcome's issues when it did not land: the importer's confirmed one-shot, whose resources reference each other across formats and whose linked records must land with the rows that point at them. All three channels are `never`. A long-running sync loop should not switch to a bundle: the failure model (per-entry or whole, one shot) does not fit an infinite drive loop with per-resource retries.
- **`fhir-r4/identity` owns the derivation every stored resource id comes from, and nothing else.** `localResourceId` is persisted wire format — changing it orphans every stored resource. It lives here rather than beside adoption (`slices/http-extraction/fhir-r4-adoption`) because `web-trace-core`, the importer and the synthetic-data generators mint ids with it too. The hash _lane_ is not owned here: it is `kitchen-sink`'s `fnv1a64`, the standard algorithm pinned against the published FNV vectors. What this package owns is what is not standard FNV — the second lane's displaced basis, the 128-bit concatenation, the `wf-` rendering, and the length-prefixed component encoding (`joinIdComponents`, exported because a caller folding several values into one `originalId` must fold them the same way rather than inventing a separator). The design is written up in the [Source Identity Explanation](../http-extraction/fhir-r4-adoption/docs/Source%20Identity%20Explanation.md). `fhir-sync-pebble-core` carries a `bigint`-free port of `localResourceId` and `joinIdComponents` for the Pebble watchapp's ES5 phone bundle, held to these by a parity test, so a change here fails there too.
- **`fhir-r4/resources`' `ResourceType` is the whole R4 resource-type value set, not the modelled `FhirResource` union.** A reference may name any R4 type (`Encounter/1`), so the value set is what tells a reference to an R4 resource from a source's own pseudo-type (carebook's `PrescriptionOrder`); `fhir-r4-adoption` reads it to decide which literal references it detaches. `resource-type.test.ts` checks that it holds every type of the union and of `@types/fhir`'s R4 union (which leaves out `AdverseEvent`).
- **`fhir-r4/patient-minimal` is a narrowed `Patient` (`PatientMinimal.Schema`: `id`, `name`, `birthDate`, `gender`) and `HumanName.displayName`, without the datatype registry.** Importing `fhir-r4/data-types` or `/resources` (or anything that reaches them) runs every datatype's `registerDatatypeSchema` and brings the schemas' `fast-check` arbitraries along, too much for a page with a size budget (the authorization server's consent card). The subpath loads only `effect`, which `patient-minimal.test.ts` checks by walking its imports; `HumanName.displayName` re-exports the same `displayName`, so the two can't differ. The schema is lenient where `Patient.Schema` is strict, for a picker listing any server: each name decodes on its own, `given`'s `null`s are dropped, and `birthDate` is the string the server wrote.
- **`fhir-r4-react/smart` owns the wiring a first-party SMART app needs, and it is auth-critical.** A completed sign-in is a `SmartConnection` (`smart-connection.ts`): the `FhirBaseUrl` it is for (a branded schema that trims trailing slashes once, on decode), the bearer token (`None` for an open server) and the launch's patient. `smart-client.ts`'s `SmartClient` is a `Context.Tag` holding that connection and the one read the readers make; `SmartClient.layer(connection)` builds it over the page's `HttpClient`. `smart-runtime.ts`'s `smartRuntimeFor(connection, transport?)` is the one runtime an app runs on: `SmartClient.layer` and the typed `FhirR4ResourcesHttpApiClient` over the same transport, with its `runSmart`, which runs everything over one `ManagedRuntime` built on the first run, until `release` closes it (a later run builds it afresh). `smart-app-react`'s `SmartHandshakeGate` builds it, provides it (`useRunSmart`), and hands it to the app, whose router context carries the same runtime (`buildSmartRouterContext(runtime, queryClient)`). An app served from its **own** origin (the published site, or a dev server on `localhost`) authenticates with its own SMART bearer token through it, since the server trusts no caller as local. Copying it is copying auth-critical code. Three properties are the reason it exists and must survive any edit — each is pinned by a test in `smart-client.test.ts` and `smart-runtime.test.ts`:
  - **The typed client emits base-relative FHIR paths; the connection names the base.** `FhirResourcesApi` emits base-relative paths (`/Patient`), so the client can address any FHIR server. Naming the base is the provider's job: the launcher sends them through its API transport, since a Wildflower server serves FHIR at its root (`apps/launcher/launcher-web`'s `runtime-layer.ts`), while a SMART app addresses them under its connection's `fhirBaseUrl` — the `iss`, or the server a standalone launch was pointed at — **verbatim**. There is no `iss` parsing: whatever server the sign-in named is the base. `smart-runtime.test.ts` pins the verbatim address as a property over arbitrary bases.
  - **One rule decides every request's address and credential.** `addressedUnderFhirBase` resolves a request's URL against the FHIR base with the WHATWG URL parser (a relative one first loses its leading slashes, so `/Patient` and `Patient` are both `{fhirBaseUrl}/Patient`) and returns an `Either`: `Right` when the resolved URL is the base or a path under it, on its origin, such as a search bundle's `next` link, and `Left` anywhere else. The request goes to the resolved URL either way, with the token only on the right, since the token was granted for the FHIR server the sign-in named and must never leave it. The check runs after dot segments are resolved, so `../r4-admin/Patient` or `%2e%2e/r4-admin/Patient` against `https://fhir.example/r4` goes bare. `SmartClient.layer` and `smartHttpClientLayer` (the same rule for a client that is not a `SmartClient`, which `apps/authorization/authorization-web` uses for its API) both apply it, so the typed client and the readers cannot disagree about where a token goes. A connection with no token sets no header at all, never a `Bearer` with nothing after it.
  - **The transport stays a parameter.** That is what lets a consumer drive its whole tree over a stub and assert what actually went on the wire. `smartRuntimeFor` takes it (default `FetchHttpClient.layer`, which the gate uses); the sign-in itself names no transport, since it resolves to a `SmartConnection`. The stub is `./smart/test-helpers`' `stubFhirServer`: a transport answering by longest URL prefix (a relative key is a path under its `STUB_FHIR_BASE`, resolved by `addressedUnderFhirBase`) and recording each request as sent, which `stubSmartRuntime` builds a runtime over. Every suite that reads through a `SmartClient` uses it rather than a stub of its own.
- **`fhir-r4-react/smart`'s sign-in steps are Effects, split by which side of the redirect they run on, and only the page's edges run them.** `sign-in-redirect.ts` leaves for the sign-in: `redirectToSignInAt(discovered, config, launch)` starts at endpoints already discovered, and `redirectToSelfAddressedSignInReturn` signs in to an open server (one with no authorization endpoint) by addressing the redirect to the page itself, retaining the server and an `expectedState` first. `retained-sign-in-requests.ts` holds what crosses the redirect: `authorization-core`'s retained sign-in request under `RETAINED_SIGN_IN_REQUEST_KEY` (`fhir-r4-react.retained-sign-in-request`) and the `RetainedSelfAddressedSignInRequest` under `RETAINED_SELF_ADDRESSED_SIGN_IN_REQUEST_KEY` (`fhir-r4-react.retained-self-addressed-sign-in-request`), both package-wide since `sessionStorage` is per tab and each app has its own origin. `sign-in-after-redirect.ts` finishes on the way back: `completeSignInAfterRedirectHere(landing)` redeems a `SignInReturn`'s code, or accepts a `SelfAddressedSignInReturn` whose `state` matches (`CallbackStateMismatch` when it does not, `NoSignInInProgress` when nothing was retained, or when `completeSignIn` finds no return to complete), and resolves to a `SmartConnection`; `discardRefusedSignInAfterRedirectHere` drops everything for a `SignInRefused`. **Every sign-in arrival takes every retained request and scrubs the callback from the URL** (`takeRetainedSignInRequests`) before it decides anything. Each request has its store service: `authorization-core`'s `RetainedSignInRequestStore`, and `RetainedSelfAddressedSignInRequestStore` here, both built from `authorization-core`'s store implementation over `kitchen-sink`'s storage-item helpers. A refused storage call is `RetainedRequestUnusable` (a take fails only on a refused read: a record already read is not lost to a refused removal, and a `SignInReturn` is not failed by the self-addressed key, which is not its to complete), and a record that does not decode is `retainedRequestUnrecognisedFromAnotherVersion`'s `RetainedRequestUnrecognised`, so both wordings have one home. The redemption names the redirect URI the outbound leg did (`appRootRedirectUri`, `app-root-redirect-uri.ts`). Each step requires `authorization-core`'s sign-in services (the `HttpClient`, `SignInCrypto`, `RetainedSignInRequestStore` and `PageSecurity`) and the `RetainedSelfAddressedSignInRequestStore` from its context (`SmartSignInServices`) rather than taking a `fetch` or a storage. No step here runs itself: `useSmartHandshake`'s query, `smart-app-react`'s launch page, root and `ConnectMenu` are the four edges that do, and each provides `smartSignInLayer(window)` (`BrowserSignIn.layerFromWindow` with the store at `RETAINED_SIGN_IN_REQUEST_KEY`, and the self-addressed store at `RETAINED_SELF_ADDRESSED_SIGN_IN_REQUEST_KEY`).
- **`fhir-r4-react/smart`'s sign-in probes before it redirects, `Unreachable` ≠ `Open`, and the authorize navigation is guarded.** `smart-support.ts`'s `detectSmartSupport(fhirBaseUrl)` reads `{fhirBaseUrl}/.well-known/smart-configuration` through `authorization-core`'s `fetchSmartConfiguration`, the fetch discovery makes too, and resolves one of four `SmartSupport` tags — `Smart` (the config names an `authorization_endpoint` and `authorization-core`'s `discoveredSmartServerFrom` accepts its endpoints for this page, carrying what it `discovered`), **`Unusable`** (`discoveredSmartServerFrom` refuses them — an endpoint that is not https or loopback, no `token_endpoint`, no S256 — with its `reason`), `Open` (a real HTTP answer with no such config, a 404 or non-JSON included) or **`Unreachable`** (the probe got _no response_, with its `reason`). `Unreachable` is deliberate and load-bearing: a CORS-blocked probe gets no response, as a down server's does, so it is surfaced to the user with a retry, **never** silently degraded to `Open` — treating it as open would fire unauthenticated reads at a server that may require auth. `redirectToSignIn(config, launch)` probes a server a reader picked and an EHR launch's `iss` alike, and `Match`es on the outcome: `Smart` → `redirectToSignInAt`, so the configuration is fetched once; `Open` → `redirectToSelfAddressedSignInReturn`, so an `?iss=` launch to an open server connects as a pick of it does; the other two redirect nowhere. The fetch goes through the context's `HttpClient`, with trace propagation off so it stays a CORS-simple request, and the probe reads whether the page is secure from its `PageSecurity`: a test answers over `./smart/test-helpers`' `stubFhirServer`, the same transport-from-the-context philosophy as the runtime above. **The authorize navigation is only ever to endpoints `discoveredSmartServerFrom` accepted for this page** in the probe; otherwise the outcome is `Unusable`, with its reason, and the page stays put. `normalizeServerUrl` and `insecureTargetReason` are not defined here: `smart-support.ts` re-exports `authorization-core/smart-client`'s, and `smart-support.test.ts` asserts each re-export is the same function, so a second copy cannot quietly grow; `ConnectMenu` refuses an insecure pick with the latter before connecting. `root-arrival.ts` re-exports `arrivingSmartLaunchFrom` the same way, with the same identity test, so the launcher and the docs console, which sign in with `authorization-core`, read a launch as the SMART apps do without bundling this package. `local-network-hint.ts` owns `withLocalNetworkAccessHint`, which follows a loopback server's connection failure on an https page with a sentence naming Chrome's Local Network Access prompt; the connect menus and the launcher's landing share it. The UI over these steps is `smart-app-react`'s `ConnectMenu` — see [slices/smart-app-react/AGENTS.md](../smart-app-react/AGENTS.md).
- **The app root reads its query string once, into a `RootArrival`.** `root-arrival.ts`'s `rootArrivalFrom(search)` is the one parse: `SignInRefused` (`?error=`, read first, since a refusal carries `state` too), `SignInReturn` (`?code=`, with its `state`), `SelfAddressedSignInReturn` (`?state=` alone), `LaunchRequest` (`?iss=`, via `arrivingSmartLaunchFrom`) or `Visit` (bare, or our own `?launchError=`, which it carries). `smart-app-react`'s `SmartAppRoot` `Match`es on it.
- **`fhir-r4-react/smart`'s `appLaunchUrl` builds the link that launches a hosted SMART app against a server, from the app's launch page (its root, which starts the launch its URL carries: `arrivingSmartLaunchFrom`).** For a FHIR base on SMART Health IT's launcher (`launch.smarthealthit.org`, `/v/<version>/fhir` or `/v/<version>/sim/<code>/fhir`) it is the EHR launch the launcher page builds: `iss` the launcher's unsimulated FHIR base, `launch` a `patient-portal` launch code carrying the session's patient, encoded as smart-launcher-v2's `src/isomorphic/codec.ts` encodes it (`app-launch-url.test.ts` decodes it the way that codec does, and checks it byte for byte against a code the launcher minted). For any other server it is `?iss=<FHIR base>` alone, which the app root runs as a standalone launch. The launcher's Home on a plain SMART server links every hosted app through it.
- **Every `fhir-r4-react/smart` paged read goes through `fetchResourcePage`, and the read descriptor is the only resource-specific part.** `resource-page.ts` owns the whole algorithm — the permissive `Bundle` page decode (a response that is not a bundle is an empty last page), the `next`-link cursor, and the per-entry decode-or-drop that keeps one malformed row from failing a page. Every reader requires `SmartClient` from its context rather than taking a client. A resource adds a `PagedResourceRead` naming three things and nothing else: its `resourceType`, the `fhir-r4` schema its entries decode through, and a `firstPageQuery` building the first page's search parameters. `fetchMedicationRequestPage` (`MedicationRequest?patient=…&_sort=-authoredon`, keeping its own `{ patientId } | { pageUrl }` cursor so `apps/medications/medications-web` is untouched, and decoding through `withMandatoryId(MedicationRequest.Schema)` so an entry without an `id` is dropped rather than keyed by position), `fetchObservationPage` (`Observation?patient=…&_sort=date`), `fetchObservationBasedOnOrPartOfPage` (the same, narrowed by `based-on` and/or `part-of`), `fetchPatientPage` (`Patient?_sort=family`, the read behind `smart-app-react`'s `PatientPicker`), `fetchPlanDefinitionPage` (`PlanDefinition?topic=…`), `fetchActiveServiceRequestPage` (`ServiceRequest?category=…&instantiates-canonical=…&status=active`), `fetchServiceRequestPage` (the same in every status) and `fetchProcedurePage` (`Procedure?category=…&instantiates-canonical=…`) are all thin wrappers over it — the next read is a descriptor, not another copy of the paging. Those readers stay generic: a search value a feature owns (a `topic` or `category` token, a definition's canonical url) is the caller's first-page input, never baked into the descriptor. `fetchAllResourcePages(fetchPage, first)` follows `next` links from one of those readers to the last page for a caller that needs the whole result, failing with `ResourcePageCycleError` on a `next` link it already read and on any failed page rather than returning a partial history. A page request the network dropped — the client's `FhirRequestDropped`, because no HTTP response arrived, as when a browser's CORS or Local Network Access check fails it — is reissued with exponential backoff (3 retries, 250 ms → 1 s) before it fails the read; an HTTP error (`FhirHttpError`, any status, whose message names the status, the URL and any OperationOutcome text the server sent) and a body that is not JSON fail at once. Only the request is retried, never the bundle decode. Every read pins `_count` to the shared `RESOURCE_PAGE_SIZE` (200): a server's default page is commonly 10–50, which turns a year of observations into dozens of round trips. **The patient id is always a parameter, never read off the connection's `launchPatientId` inside the reader** — the caller decides what "no patient in context" means for its launch, and both patient-scoped reads drop the `patient=` filter entirely when it is `null`. `fetchPatient(id)` is the single-resource counterpart and resolves an `Option<Patient>`: `None` when the server answers 404 or 410, the one answer a caller acts on (a routed app's patient route turns it into its no-patient card); an answer that does not decode as a `Patient` fails with `BundleDecodeError`, as an undecodable page entry does, and any other transport or HTTP failure with `ResourcePageRequestError`.
- **A failed SMART launch is never silent — it lands on the app root and renders there.** `launch-error.ts` owns the contract for the three ways a launch fails: `redirectToSignIn` failing or finding the `iss` `Unreachable` or `Unusable` on the launch page and a failed sign-in after the redirect each encode a `LaunchErrorBody` (`launchErrorBodyFor`, from the failure's typed `reason`) and redirect to the app root (`launchErrorRedirect`); the authorization server's own OAuth `?error=` return lands on the app root as it is. `rootArrivalFrom` reads either back (`Visit`'s `launchError`, `SignInRefused`'s `refusal`), and `launchError` makes the `Error` the app root hands to tundraish's `ErrorBanner`. Three properties are load-bearing:
  - **The wire is the Tauri arm's wire.** URL-safe-base64 JSON, byte-identical to `apps/launcher/apps-react/src/routes/_auth/home/-launch-error.ts`, so both arms' `?launchError` decode the same way. Changing one without the other forks the contract.
  - **`launchErrorRedirect` strips `code`/`state`/`error`/`error_description`/`error_uri` from the target.** This is what makes the redirect safe to fire from a failed sign-in: `rootArrivalFrom` reads `code`/`state`, so carrying either to the app root would re-enter the app, fail the same single-use code, and redirect again — forever. Pinned by a property test.
  - **The reported value is an `Error`, not a string.** Tundraish's `formatErrorDetails` returns `null` for a non-`Error`, which silently drops the "Show details" disclosure — the one place `iss` and the OAuth `error_uri` are visible. The diagnostics are attached as own enumerable properties precisely because that is what its own-fields pass surfaces.

- **The redirect-target token exchange runs through `useSmartHandshake`, once — never a bare `useEffect`.** The authorization code in the redirect URL is single-use, so the exchange (`completeSignInAfterRedirectHere` → `authorization-core`'s `completeSignIn`, the POST to the token endpoint) may fire once, ever. `useSmartHandshake(landing)` (`use-smart-handshake.ts`) wraps it in a keyed TanStack Query with `retry: false` and `staleTime`/`gcTime: Infinity`, which is what makes that hold under `React.StrictMode`'s dev double-mount — a raw `useEffect` runs the exchange twice, and the second run finds the single-use retained requests already taken and fails the handshake. The query's data is the outcome as an `Either`, so the `SmartHandshake` it reports (`Connecting`, `Failed` with its typed error, `Ready` with the connection) keeps the failure's type; a defect throws to the error boundary. The app builds its one `QueryClient` with `buildSmartQueryClient()` and provides it at the tree root (where the hook runs, before any router context exists); the router context carries that same instance, so the exchange and every app read share one cache. `smart-app-react`'s `SmartAppRoot` builds and provides that client, so an app mounted in it gets this wiring for free, and a new SMART app must mount it too rather than copying the root. `smart-app-react`'s `SmartHandshakeGate` is the hook's one caller.
- **Deviations from the FHIR R4 spec must be recorded, in the catalogue for the side you touched, in the same change.** Client-side (TS schemas / `HttpApi`) go in [fhir-r4/docs/Client Capabilities Reference.md](./fhir-r4/docs/Client%20Capabilities%20Reference.md); server-side (`fhir-r4-rust`'s overrides on top of HFS) go in [fhir-r4-rust/docs/Capability Statement.md](../../apps/host/wildflower-server/fhir-r4-rust/docs/Capability%20Statement.md).

## Traps

- **No drift guard exists between `fhir-r4`'s `HttpApi` and HFS's actual surface.** A snapshot pair does exist (`fhir-r4/openapi/fhir-r4.openapi.json`, generated from the TS `fhir-r4` `HttpApi`, kept fresh by a TS-side test, and rendered by the published server-docs console) — but it only guards the snapshot against the `HttpApi`, not against what HFS actually serves. If you change the `HttpApi` definition, verify HFS actually serves that shape (see the Client Capabilities Reference).
- **Consuming `fhir-r4` from another package has two non-obvious traps** — building schemas from its datatype schemas can break `vp pack`'s `.d.ts` emit (TS2883) while `vp check` stays green, and `uri`/`url` fields on an already-decoded resource are `URL`s, not strings. Both are catalogued in the [Consumer Gotchas Reference](./fhir-r4/docs/Consumer%20Gotchas%20Reference.md); keep the top-level interface re-exports in `data-types/index.ts` when editing `fhir-r4`.
- Complex datatypes self-register into the registry at module load (`registerDatatypeSchema` at the bottom of each datatype file). A `value[x]` slot whose datatype module hasn't been imported fails encode with `UnregisteredDatatype`. Import the registration barrel `fhir-r4/src/data-types/register-all.ts` (one side-effect import that loads every registrable module) instead of hand-listing modules per resource. `register-all.test.ts` asserts the barrel populates every registry slot, so a dropped or forgotten registration is a CI failure rather than a latent runtime one — but the barrel's imports are still bare side effects, so add the matching line whenever a new complex datatype module lands.
