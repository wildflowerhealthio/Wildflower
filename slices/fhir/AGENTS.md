# AGENTS.md — slices/fhir

FHIR R4 slice: pure wire schemas (Patient / Practitioner / Observation / DiagnosticReport / MedicationRequest / MedicationDispense / DocumentReference / Binary / ServiceRequest / ImagingStudy / CarePlan / Goal / PlanDefinition / Procedure), the `HttpApi` description, and the HTTP client for the off-the-shelf HFS FHIR server embedded by `fhir-r4-rust`. Read the [Packages Explanation](./docs/Packages%20Explanation.md) before restructuring anything here.

## Guardrails

- **The server is HFS, not TypeScript.** `fhir-r4-rust` embeds the HeliosSoftware/hfs crates and is served at the server's root, on FHIR paths, by `wildflower-server-rust`. There is no TS server implementation; `fhir-r4` is a description + schemas + client only. Don't add server handlers back to the TS side.
- **`fhir-r4` deliberately breaks the `-core` naming convention.** It is a wire-protocol package that never grows platform adapters, so it takes no suffix. It depends on no other fhir package.
- **`fhir-r4/clients` owns writing to the store: one resource (`upsertResource`), one batch of PUTs (`persistResources`), one batch or transaction Bundle (`persistBatchBundle`, `persistTransactionBundle`), and one server-diff probe (`classifyAgainstServer`) — all reporting outcomes as data.** The batch sinks live here rather than in the importer slice because they need `upsertResource` and the typed client, while `importer-fundamentals` is deliberately FHIR-agnostic. **They take no options.** The writes are this package's, so the spans they emit (`fhir.persist.write` / `fhir.persist.bundle` / `fhir.persist.classify`) and the attributes they tag (`fhir.resource.type`, `fhir.persist.resource_count`) are named in this package's own telemetry catalog — a caller cannot make one write report itself as two different operations. `ResourceWriteFailure` (from `persistResources`) is likewise declared here rather than imported, because this slice sits below its consumers and cannot name them; a consumer checks the two against each other at its own call site.
- **`persistResources` vs `persistBatchBundle` vs `persistTransactionBundle` — pick by transport shape, not by convenience.** `persistResources` fans one PUT out per resource with bounded retries + concurrency (a real-time sync loop — dozens of small writes over the lifetime of a session, each with its own attempt count on the trace), reporting only the failures as `ResourceWriteFailure[]`. `persistBatchBundle` submits one `POST /` `batch` Bundle carrying N PUT entries in a single round trip, each entry landing on its own, and reports the **whole** per-entry result as `BatchEntryOutcome[]` — one per resource handed in, at its position, one entry per `Type/id` on the wire — each one's echoed status, whether it succeeded, and any OperationOutcome diagnostics (parsed from `Bundle.entry.response.outcome`) — so a results view can show what wrote alongside what did not, grouped by response code. `persistTransactionBundle` submits the same entries as a `transaction` Bundle, which the server applies as one unit or refuses whole (HFS on SQLite runs it atomically; `fhir-r4-rust`'s `batch_bundle_at_base` tests pin that), reporting the same per-entry outcomes, every one failed under the refusal's own status and its OperationOutcome's issues when it did not land: the importer's confirmed one-shot, whose resources reference each other across formats and whose linked records must land with the rows that point at them. All three channels are `never`. A long-running sync loop should not switch to a bundle: the failure model (per-entry or whole, one shot) does not fit an infinite drive loop with per-resource retries.
- **`fhir-r4/identity` owns the derivation every stored resource id comes from, and nothing else.** `localResourceId` is persisted wire format — changing it orphans every stored resource. It lives here rather than beside adoption (`slices/http-extraction/fhir-r4-adoption`) because `web-trace-core`, the importer and the synthetic-data generators mint ids with it too. The hash _lane_ is not owned here: it is `kitchen-sink`'s `fnv1a64`, the standard algorithm pinned against the published FNV vectors. What this package owns is what is not standard FNV — the second lane's displaced basis, the 128-bit concatenation, the `wf-` rendering, and the length-prefixed component encoding (`joinIdComponents`, exported because a caller folding several values into one `originalId` must fold them the same way rather than inventing a separator). The design is written up in the [Source Identity Explanation](../http-extraction/fhir-r4-adoption/docs/Source%20Identity%20Explanation.md). `fhir-sync-pebble-core` carries a `bigint`-free port of `localResourceId` and `joinIdComponents` for the Pebble watchapp's ES5 phone bundle, held to these by a parity test, so a change here fails there too.
- **`fhir-r4/patient-minimal` is a narrowed `Patient` (`PatientMinimal.Schema`: `id`, `name`, `birthDate`, `gender`) and `HumanName.displayName`, without the datatype registry.** Importing `fhir-r4/data-types` or `/resources` (or anything that reaches them) runs every datatype's `registerDatatypeSchema` and brings the schemas' `fast-check` arbitraries along, too much for a page with a size budget (the authorization server's consent card). The subpath loads only `effect`, which `patient-minimal.test.ts` checks by walking its imports; `HumanName.displayName` re-exports the same `displayName`, so the two can't differ. The schema is lenient where `Patient.Schema` is strict, for a picker listing any server: each name decodes on its own, `given`'s `null`s are dropped, and `birthDate` is the string the server wrote.
- **`fhir-r4-react/smart` owns the wiring a first-party SMART app needs, and it is auth-critical.** `smart-runtime.ts` is what an app served from its **own** origin (the published site, or a dev server on `localhost`) uses to authenticate with its own SMART bearer token, since the server trusts no caller as local: every caller brings its own bearer. Every first-party SMART app shares it; copying it is copying auth-critical code. Three properties are the reason it exists and must survive any edit — each is pinned by a test in `smart-runtime.test.ts`:
  - **The typed client emits base-relative FHIR paths; the provider names the base URL explicitly.** `FhirResourcesApi` emits base-relative paths (`/Patient`), so the client can address any FHIR server. Naming the base is the provider's job: the launcher sends them through its API transport, since a Wildflower server serves FHIR at its root (`apps/launcher/launcher-web`'s `runtime-layer.ts`), while `smartHttpClientLayer` prepends `session.serverUrl` — the `iss`, or the server a standalone launch was pointed at — **verbatim** (only trailing slashes trimmed, by `fhir-r4/clients`' `trimTrailingSlashes`, the one rule everything joining a path to a FHIR base uses). There is no `iss` parsing and no `Either`/`UnexpectedFhirBase`: whatever server the handshake named is the base, so `smartHttpClientLayer` and `buildSmartRouterContext` return plain values and the app uses them directly. `smart-runtime.test.ts` pins the verbatim-prepend as a property over arbitrary bases.
  - **The bearer token rides only the requests the layer addressed.** An already-absolute URL passes through untouched _and_ uncredentialed: the SMART token was granted for the FHIR server the handshake named, so it must never leave for an origin the session did not name. A session with no token sets no header at all, never a `Bearer` with nothing after it.
  - **The transport stays a parameter — never a baked-in `FetchHttpClient.layer`.** That is what lets a consumer drive its whole tree over a stub and assert what actually went on the wire. The app is the one place the real transport is named.
- **`fhir-r4-react/smart`'s standalone-launch primitives probe before they connect, `unreachable` ≠ `open`, and the authorize navigation is guarded.** `standalone-launch.ts` runs a Standalone SMART App Launch against a user-picked server: `detectSmartSupport(iss, fetchFn?, pageIsSecure?)` GETs `{iss}/.well-known/smart-configuration` and returns one of four outcomes — `smart` (config names an `authorization_endpoint` and `authorization-core`'s `smartIssuerFrom` accepts its endpoints for this page → OAuth+PKCE via `authorizeSmartLaunch`), **`unusable`** (config names an `authorization_endpoint` but `smartIssuerFrom` refuses it — an endpoint that is not https or loopback, no `token_endpoint`, no S256 — carrying the `DiscoveryFailed` reason; no authorize), `open` (a real HTTP answer with no such config, a 404 or non-JSON included → `authorizeOpenServer`, no `Authorization` header), or **`unreachable`** (the fetch _rejected_). `unreachable` is deliberate and load-bearing: a CORS-blocked probe rejects identically to a down server, so it is surfaced to the user with a retry, **never** silently degraded to `open` — treating it as open would fire unauthenticated reads at a server that may require auth. `fetchFn` is a parameter (default `globalThis.fetch`), same transport-is-a-parameter philosophy as the runtime above, and so is `pageIsSecure` (default read from `window.location`). The probe only names the reason early: **`authorizeSmartLaunch` guards the navigation itself**, for this standalone launch and for `smart-app-react`'s EHR launch alike, because it discovers the configuration again. It runs `authorization-core/smart-client`'s `beginSignIn`, whose discovery accepts the advertised endpoints only when `usableEndpointUrl` (`endpointUrlFrom`) does for this page, and `location.assign`s the authorize URL only then; otherwise it rejects with discovery's reason and the page stays put. `authorizeOpenServer` navigates straight to the app's own redirect target, carrying a fresh `state`. Both keep what the redirect target needs (`smart-launch.ts`'s pending connection: the app's registration for a sign-in, or the open server and its `state`) in `sessionStorage`, beside `beginSignIn`'s own pending record, and `readySmartClient` takes it, once, on the way back. `normalizeServerUrl` is **not** defined here any more — `standalone-launch.ts` re-exports the one implementation, which lives in `authorization-core/smart-client`'s `server-target.ts`. It used to be a byte-identical copy, because the original sat in `apps/server-docs-web` and a slice cannot import from an app; moving it into `authorization-core` removed that obstacle and the copy went with it. A test in `standalone-launch.test.ts` asserts the re-export is the same function, so a third copy cannot quietly grow back. `insecureTargetReason` (why an https page cannot reach a plain-http server off loopback) is re-exported the same way, with the same identity test, for `ConnectMenu` to refuse such a pick before connecting. `smart-launch.ts` re-exports `arrivingSmartLaunchFrom` (the launch a page's URL asks it to start) the same way, with the same identity test, so the launcher and the docs console, which sign in with `authorization-core`, read a launch as the SMART apps do without bundling this package. `local-network-hint.ts` owns `withLocalNetworkAccessHint`, which follows a loopback server's connection failure on an https page with a sentence naming Chrome's Local Network Access prompt; the connect menus and the launcher's landing share it. Both sign in through `authorization-core/smart-client`. The UI over these primitives is `smart-app-react`'s `ConnectMenu` — see [slices/smart-app-react/AGENTS.md](../smart-app-react/AGENTS.md).
- **`fhir-r4-react/smart`'s `appLaunchUrl` builds the link that launches a hosted SMART app against a server, from the app's launch page (its root, which starts the launch its URL carries: `arrivingSmartLaunchFrom`).** For a FHIR base on SMART Health IT's launcher (`launch.smarthealthit.org`, `/v/<version>/fhir` or `/v/<version>/sim/<code>/fhir`) it is the EHR launch the launcher page builds: `iss` the launcher's unsimulated FHIR base, `launch` a `patient-portal` launch code carrying the session's patient, encoded as smart-launcher-v2's `src/isomorphic/codec.ts` encodes it (`app-launch-url.test.ts` decodes it the way that codec does, and checks it byte for byte against a code the launcher minted). For any other server it is `?iss=<FHIR base>` alone, which the app root runs as a standalone launch. The launcher's Home on a plain SMART server links every hosted app through it.
- **Every `fhir-r4-react/smart` paged read goes through `fetchResourcePage`, and the read descriptor is the only resource-specific part.** `resource-page.ts` owns the whole algorithm — the permissive `Bundle` page decode (a response that is not a bundle is an empty last page), the `next`-link cursor, and the per-entry decode-or-drop that keeps one malformed row from failing a page. A resource adds a `PagedResourceRead` naming three things and nothing else: its `resourceType`, the `fhir-r4` schema its entries decode through, and a `firstPageQuery` building the first page's search parameters. `fetchMedicationRequestPage` (`MedicationRequest?patient=…&_sort=-authoredon`, keeping its own `{ patientId } | { pageUrl }` cursor so `apps/medications/medications-web` is untouched, and decoding through `withMandatoryId(MedicationRequest.Schema)` so an entry without an `id` is dropped rather than keyed by position), `fetchObservationPage` (`Observation?patient=…&_sort=date`), `fetchObservationBasedOnOrPartOfPage` (the same, narrowed by `based-on` and/or `part-of`), `fetchPatientPage` (`Patient?_sort=family`, the read behind `smart-app-react`'s `PatientPicker`), `fetchPlanDefinitionPage` (`PlanDefinition?topic=…`), `fetchActiveServiceRequestPage` (`ServiceRequest?category=…&instantiates-canonical=…&status=active`), `fetchServiceRequestPage` (the same in every status) and `fetchProcedurePage` (`Procedure?category=…&instantiates-canonical=…`) are all thin wrappers over it — the next read is a descriptor, not another copy of the paging. Those readers stay generic: a search value a feature owns (a `topic` or `category` token, a definition's canonical url) is the caller's first-page input, never baked into the descriptor. `fetchAllResourcePages(fetchPage, first)` follows `next` links from one of those readers to the last page for a caller that needs the whole result, failing with `ResourcePageCycleError` on a `next` link it already read and on any failed page rather than returning a partial history. A page request the network dropped — the client's `FhirRequestDropped`, because no HTTP response arrived, as when a browser's CORS or Local Network Access check fails it — is reissued with exponential backoff (3 retries, 250 ms → 1 s) before it fails the read; an HTTP error (`FhirHttpError`, any status) and a body that is not JSON fail at once. Only the request is retried, never the bundle decode. Every read pins `_count` to the shared `RESOURCE_PAGE_SIZE` (200): a server's default page is commonly 10–50, which turns a year of observations into dozens of round trips. **The patient id is always a parameter, never read off `client.launchPatientId` inside the reader** — the caller decides what "no patient in context" means for its launch, and both patient-scoped reads drop the `patient=` filter entirely when it is `null`. `fetchPatient(client, id)` is the single-resource counterpart and resolves an `Option<Patient>`: `None` when the server answers 404 or 410, the one answer a caller acts on (a routed app's patient route turns it into its no-patient card); an answer that does not decode as a `Patient` fails with `BundleDecodeError`, as an undecodable page entry does, and any other transport or HTTP failure with `ResourcePageRequestError`.
- **A failed SMART launch is never silent — it rides `?launchError` to the app root and renders there.** `launch-error.ts` owns the contract, and it exists because three separate failures used to end with the user on a page that said nothing: `authorizeSmartLaunch` rejecting on the launch page (an unreachable or CORS-blocked `iss`) only wrote bare text into the launch page's body; the authorization server's own OAuth `?error=` return was _deliberately_ excluded from `shouldCompleteSmartLaunch` and so rendered the plain connect menu; and a failed token exchange showed a bare red line in a dead end. All three now encode a `LaunchErrorBody` (`launchErrorBodyFor`), redirect to the app root (`launchErrorRedirect`), and are read back by `launchErrorFrom` into an `Error` the app root hands to tundraish's `ErrorBanner`. Three properties are load-bearing:
  - **The wire is the Tauri arm's wire.** URL-safe-base64 JSON, byte-identical to `apps/launcher/apps-react/src/routes/_auth/home/-launch-error.ts`, so both arms' `?launchError` decode the same way. Changing one without the other forks the contract.
  - **`launchErrorRedirect` strips `code`/`state`/`error`/`error_description`/`error_uri` from the target.** This is what makes the redirect safe to fire from a failed exchange: `shouldCompleteSmartLaunch` reads `code`/`state`, so carrying either to the app root would re-enter the launched branch, fail the same single-use code, and redirect again — forever. Pinned by a property test.
  - **The reported value is an `Error`, not a string.** Tundraish's `formatErrorDetails` returns `null` for a non-`Error`, which silently drops the "Show details" disclosure — the one place `iss` and the OAuth `error_uri` are visible. The diagnostics are attached as own enumerable properties precisely because that is what its own-fields pass surfaces.

- **The redirect-target token exchange runs through `useSmartHandshake`, once — never a bare `useEffect`.** The authorization code in the redirect URL is single-use, so the exchange (`readySmartClient` → `authorization-core`'s `completeSignIn`, the POST to the token endpoint) may fire once, ever. `useSmartHandshake` (`use-smart-handshake.ts`) wraps it in a keyed TanStack Query with `retry: false` and `staleTime`/`gcTime: Infinity`, which is what makes that hold under `React.StrictMode`'s dev double-mount — a raw `useEffect` runs the exchange twice, and the second run finds the single-use pending connection already taken and fails the handshake. The app builds its one `QueryClient` with `buildSmartQueryClient()`, provides it at the tree root (where the hook runs, before any router context exists), and hands that same instance to `buildSmartRouterContext` so the exchange and every app read share one cache. `smart-app-react`'s `SmartAppRoot` builds and provides that client, so an app mounted in it gets this wiring for free; `apps/medications/medications-web`, `apps/importer-web` and `apps/fhir-sync-pebble/fhir-sync-pebble-web` mount it, and a new SMART app must too rather than copying the root.
- **Deviations from the FHIR R4 spec must be recorded, in the catalogue for the side you touched, in the same change.** Client-side (TS schemas / `HttpApi`) go in [fhir-r4/docs/Client Capabilities Reference.md](./fhir-r4/docs/Client%20Capabilities%20Reference.md); server-side (`fhir-r4-rust`'s overrides on top of HFS) go in [fhir-r4-rust/docs/Capability Statement.md](../../apps/host/wildflower-server/fhir-r4-rust/docs/Capability%20Statement.md).

## Traps

- **No drift guard exists between `fhir-r4`'s `HttpApi` and HFS's actual surface.** A snapshot pair does exist (`fhir-r4/openapi/fhir-r4.openapi.json`, generated from the TS `fhir-r4` `HttpApi`, kept fresh by a TS-side test, and rendered by the published server-docs console) — but it only guards the snapshot against the `HttpApi`, not against what HFS actually serves. If you change the `HttpApi` definition, verify HFS actually serves that shape (see the Client Capabilities Reference).
- **Consuming `fhir-r4` from another package has two non-obvious traps** — building schemas from its datatype schemas can break `vp pack`'s `.d.ts` emit (TS2883) while `vp check` stays green, and `uri`/`url` fields on an already-decoded resource are `URL`s, not strings. Both are catalogued in the [Consumer Gotchas Reference](./fhir-r4/docs/Consumer%20Gotchas%20Reference.md); keep the top-level interface re-exports in `data-types/index.ts` when editing `fhir-r4`.
- Complex datatypes self-register into the registry at module load (`registerDatatypeSchema` at the bottom of each datatype file). A `value[x]` slot whose datatype module hasn't been imported fails encode with `UnregisteredDatatype`. Import the registration barrel `fhir-r4/src/data-types/register-all.ts` (one side-effect import that loads every registrable module) instead of hand-listing modules per resource. `register-all.test.ts` asserts the barrel populates every registry slot, so a dropped or forgotten registration is a CI failure rather than a latent runtime one — but the barrel's imports are still bare side effects, so add the matching line whenever a new complex datatype module lands.
