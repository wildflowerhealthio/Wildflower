# Server Runs — Explanation

How the Tauri host runs the install's servers, what it notifies about them,
how the base sees and changes them, and how the host keeps running them in
the background.

## What it is

Every server in `servers.json` is one **unit** on the app's unit runner
(`global/tauri-unit-runner`, over the Tauri-free `global/unit-runner`). Its
words (unit, run, run policy, detail, stop reason, present, background
session, ended by platform) and its rules are in unit-runner's
[Design Explanation](../../../global/unit-runner/docs/Design%20Explanation.md),
and the Tauri side in tauri-unit-runner's
[Design Explanation](../../../global/tauri-unit-runner/docs/Design%20Explanation.md).
This page covers what the servers slice and the host build on them.

**The app pushes, `UnitRunner` starts and stops runs per policy.** The host
never decides when a server runs. It stores each server's run policy in
`servers.json` and pushes it to `TauriUnitRunner`; `UnitRunner` starts and
stops runs to match, restarts a run that ends on its own, and keeps the app
alive in the background while any server should run. It never reads
`servers.json`.

## Packages

| Package                                                            | Role                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `servers-rust`                                                     | `ServerUnit`, a server as a unit, and `ServerDetail`, the detail its runs report. `ServerStatus`, a server's `UnitStatus` with its wire shape, `ServerStatusTracker`, which picks the changed ones, and `ListedServer`. The changes the commands make (`set_run_policy`, `update_server` with `ServerRecord::run_inputs_differ`, `remove_server`). The notification decisions: `RequestNotificationCoalescer` and `StopNotificationTracker`, with `LocalNotification`. No `tauri` dependency: it depends on `unit-runner`, not `tauri-unit-runner`, so a `ServerUnit` runs through `UnitRunnerCore` in its tests. |
| `servers-tauri-rust`                                               | `host_servers`, called from the app's `setup()`; `ServerUnits`, the one place a record becomes a unit, and the way the commands set a policy, remove a unit and read the statuses; the base's commands, which write the registry and then push; the `server-status` event; and posting the notifications through `tauri-plugin-notification`.                                                                                                                                                                                                                                                                     |
| [`wildflower-server-rust`](../../wildflower-server/AGENTS.md)      | The server a run sets up and serves: `set_up(config, host_ports, observers)` composes and binds it, and `WildflowerServer::serve(shutdown)` serves it. `ServerObservers` carries the channels a run's health and forwarded requests come out on.                                                                                                                                                                                                                                                                                                                                                                  |
| [`tauri-unit-runner`](../../../global/tauri-unit-runner/README.md) | The runner, its keep-alive as `tauri-plugin-background-service`'s one service, and whether the app is open, as two plugins.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `servers-core`, `servers-react`                                    | The base: the commands as Effects with their schemas, the server list page, which shows each server's status and sets its run policy, and the keep-alive's recovery, enabled once the base starts.                                                                                                                                                                                                                                                                                                                                                                                                                |
| `apps/wildflower-tauri`                                            | Builds the runner and registers its plugins, builds the host's ports and the server config builder, registers the commands and grants them to the `main` webview, mounts the base, and owns the mobile packaging.                                                                                                                                                                                                                                                                                                                                                                                                 |

## The flow

```text
[Tauri host run()]
  runner = TauriUnitRunner::<ServerDetail>::new(BackgroundServiceStartConfig { label, type })   // from tauri-shared-config.json
  .plugin(tauri_plugin_notification::init())
  .plugin(runner.background_service_plugin())   // the background session
  .plugin(runner.lifecycle_plugin())            // present/absent, iOS return to the foreground, session start/end
  setup():
    host_ports = consent dialog, webview handle, bridge publishers   // shared by every run of every server
    servers_tauri_rust::host_servers(app, data_root, &runner, host_ports, server_config)
      read servers.json ── unreadable ─▶ logged; no server runs
      for each record: ServerUnits::push(record)
        runner.set_unit(domain, record.run_policy, || ServerUnit::new(server_config(&record)?, host_ports, forwarded_request_sender))
      spawn: emit_server_statuses(runner.subscribe())   // the server-status event
      spawn: post_stop_notifications(runner.subscribe())
      spawn: post_request_notifications(forwarded requests)
      manage ServersState { registry, data_root, server_units, registry_writes }

[command] server_add / server_set_credentials
  lock registry_writes ─▶ write servers.json ─▶ ServerUnits::push(record) ─▶ unlock
[command] server_set_run_policy(domain, choice)
  lock ─▶ write the policy (for ─▶ until) ─▶ runner.set_unit_policy(domain, policy) ─▶ unlock
[command] server_update(domain, launcherUrl, stagingCertificates)
  lock ─▶ write the record ─▶ a run input changed? ServerUnits::push(record) ─▶ unlock
[command] server_remove(domain)
  lock ─▶ runner.remove_unit(domain), awaited ─▶ delete the folder, then the record ─▶ unlock
          └─ the deletion fails ─▶ ServerUnits::push(the record as stored)
[command] servers_list
  read servers.json ─▶ join each record with runner.statuses() ─▶ ListedServer[]

[UnitRunner] the policy wants it running ─▶ a run, on its own thread and runtime:
  factory: server_config(&record) ─▶ ServerUnit
  ServerUnit::run(ctx)
    spawn: each published ServerHealth ─▶ ctx.set_detail(ServerDetail { health })
    wildflower_server_rust::set_up(config, host_ports, observers)   // binds the loopback port
    ctx.announce_running()                                         // Starting ─▶ Running
    WildflowerServer::serve(ctx.shutdown_token())
  the run ends ─▶ runtime shut down (every slice task with it) ─▶ Stopped { reason, error }, detail cleared

[servers-tauri-rust] runner.subscribe() ─▶ ServerStatusTracker ─▶ server-status, to the main webview
                     runner.subscribe() ─▶ StopNotificationTracker ─▶ stop notifications
                     forwarded requests ─▶ RequestNotificationCoalescer ─▶ request notifications

[base, once its consent is answered] plugin:background-service|configure_recovery
  { enabled: true, config: the same label and type }
```

## Decisions

| Topic                   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit id                 | A server's unit id is its domain, `ServerRecord::domain()`, the same key `servers.json` uses.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Push                    | `ServerUnits::push` turns a record into `set_unit(domain, run_policy, factory)`. `host_servers` pushes every record at setup, and each command that writes a record pushes it after writing it. One async mutex, `ServersState::registry_writes`, is held from before a command's write until after its push, so the runner always ends up with the record as last written. A command holds it through its relay request too: enrolment is rare, and the write happens inside it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Commands                | `server_set_run_policy` writes the policy the user's `RunPolicyChoice` gives (`for` stored as `until` its deadline) and gives the runner that policy with `set_unit_policy`, which also cancels a pending restart, so choosing a policy again retries a failing server at once. `server_update` writes the launcher and the certificate source, and pushes the record again only when `ServerRecord::run_inputs_differ` says a field a run reads changed: the certificate source is a run's, the launcher only the base's. `server_remove` awaits `remove_unit`, so the run has ended before its folder is deleted, then deletes the folder and the record; a deletion that fails pushes the server back as stored, so it stays registered and on the runner. `servers_list` joins the records with `statuses()`, and answers an unreadable `servers.json` with its error, which the base shows. Errors are `{kind, message}`.                                                                                                                                                                 |
| Status event            | `server-status` carries one server's `UnitStatus<ServerDetail>`, keyed by its domain, camelCase: `{domain, runState, lastStop?: {reason, platformReason?, error?, stoppedAt}, runningSince?, health?}`, `health` being `{kind: "reachable", status}` or `{kind: "unreachable", error}`. A task on `runner.subscribe()` emits it to the `main` webview for each server whose status changed (`ServerStatusTracker`). A removed server gets no event: the base drops a server once `servers_list` no longer lists it, and `server_remove` answers once the server is gone. `servers-wire-golden.json` pins the wire, read by `servers-rust`'s tests and `servers-core`'s decoder tests.                                                                                                                                                                                                                                                                                                                                                                                                          |
| Factory per run         | The factory captures the record it was pushed with, and builds a fresh `ServerUnit` from it at the start of each run: the host's `server_config` turns the record into a `WildflowerServerConfig` (the server's folder, the loopback URL, the owner UI base, the FHIR SearchParameter bundle's directory, the relay settings and the public host). So a run's configuration is fixed from its start to its end, and a config that can't be built is a failed run like any other.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| A run                   | `ServerUnit::run` calls `set_up`, then `announce_running` once the port is bound and every slice is set up, then serves until the runner cancels `ctx.shutdown()`. `set_up` and `serve` both bubble their errors, which become the run's `{:#}` error.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Isolation               | The runner gives each run its own OS thread and tokio runtime, and shuts it down when the run ends. Slices `tokio::spawn` detached tasks that never stop on their own: the tunnel supervisor, the reachability monitor, and gatekeeper's re-mint, revocation purge and retention sweeps. The runtime's shutdown cancels all of them, so a restart can't leave a second tunnel supervisor dialing the relay, and the next run of a server binds the port the last one held. `native_webview_handle`'s `spawn_blocking` stays on Tauri's runtime: it is per-call UI work, not server state.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Health                  | Each run makes its own `watch<Option<ServerHealth>>` and hands its sender to the server as `ServerObservers::server_health_sender`. A task of the run sets each value the reachability monitor publishes as the run's `ServerDetail { health }`. The runner clears the detail when the run ends, so no health outlives its run. `ServerDetail` is a struct so later details, such as the certificate, join it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Host-owned state        | `HostPorts` (the consent dialog, the on-device webview handle, and the owner-token and pending-consent `watch::Sender`s) are built once in `setup()` and shared by every run of every server. Each run's gatekeeper mints a fresh owner token onto the same channel, so the loopback owner trust and the webview keep working across restarts. Several servers running at once would publish onto the same two channels, the latest winning; the fixed loopback port (below) keeps a second one from getting that far.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Fixed loopback port     | Every server binds the one loopback port in `tauri-shared-config.json`. A second server whose policy is active fails to bind it, and the runner retries it every `RESTART_DELAY` (5 s) for as long as its policy stays active. Nothing guards against it: the runner has no cap on running units, and the slice adds none.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Stop notifications      | Keyed by the runner's `StopReason`. A run that ended on its own (`EndedOnItsOwn`) notifies, with its error when it failed, and so does a run the platform stopped by revoking the keep-alive (`KeepAliveRevoked`), with text per `PlatformStopReason`: for example "Wildflower server paused" with "iOS ended the background window.". The runner's own stops (`PolicyInactive`, `Replaced`, `Removed`, `StoppedForRestart`) don't notify. `StopNotificationTracker` reads each change of the runner's statuses and notifies each stop once. The runner retries a failed run every 5 s, so a failure with the same error as the one last notified for that server doesn't notify again until the server has run. Each server's id is `server-stopped:<domain>` and its body starts with the domain, so a burst of one server's stops replaces that server's notification instead of stacking.                                                                                                                                                                                                  |
| Request notifications   | Only **forwarded (tunnel)** requests, using `served_origin::is_forwarded`, the same predicate the owner trust uses. The outermost layer of the served stack reports a `ForwardedRequest` after the response, with `try_send`: a full channel drops the report rather than delay a response. Every run of every server reports on the one channel `host_servers` makes, `FORWARDED_REQUEST_CAPACITY` (256) deep. The record carries when the request arrived, the visitor's address (`for=` of the last `Forwarded` element), the served host, the method, the path reduced to its route (no ids, no query), the status, the response size when known, the duration, the caller and the refusal. `caller` is the `RequestCaller { client_id }` a gatekeeper bearer gate stamped on the response after verifying its token, or `None` when no gate verified one. The types live in `shared-structures-rust` (`request_caller`), where gatekeeper and the server meet. The notifications read only the caller, and a notification names its caller by that id.                                    |
| Coalescing              | Pure, in `servers-rust`, driven by an explicit clock and proptested. There is one notification per caller, with id `server-requests:client:<id>` or `server-requests:unidentified`, replaced in place. The first request after 5 quiet minutes notifies at once ("lifting is using your Wildflower server"). After that the count updates at most every 30 s ("lifting: 42 requests in the last 5 min"). Unidentified callers are never merged with identified ones, so a probe on the tunnel stays visible.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Reachability            | The server's reachability monitor (`wildflower-server-rust`) GETs its own `/health` at `https://<public host>/health`, out to the relay and back down the tunnel, until the first answer, and publishes `ServerHealth`: `Unreachable` with why, then `Reachable` with the draft-06 report. Every app already reaches the server through the same relay, and the next run confirms reach again, so there is no reachability notification; a server that stops has its stop notification.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Resume                  | The runner's lifecycle plugin restarts every running unit on an iOS resume that follows a suspend (`StoppedForRestart`): a suspended app's listening socket can be reclaimed (TN2277), leaving a server that reports running but accepts nothing. That stop doesn't notify. On a phone, the app coming back to the foreground opens it, which starts a `whileOpen` server and lets the runner start the keep-alive again after a revocation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Unreadable registry     | A `servers.json` that can't be read at setup is logged, and no server is pushed, so none runs. The commands still answer, each reading the file again.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Notification permission | The runner asks for it before the keep-alive first starts, if the OS has never asked, so the plugin's own start doesn't ask a second time (see tauri-unit-runner's Design Explanation). The servers never depend on it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Start config            | The label of Android's persistent notification and the foreground-service type live in `tauri-shared-config.json` (`background_service_label`, `background_service_foreground_type`). The host builds the runner's `StartConfig` from them, and the Tauri entry imports the same pair and hands it to the base as `keepAliveStartConfig`, so the plugin's own restarts start the keep-alive the same way. Host tests hold `androidForegroundServiceTypes` and the Android manifest's service type to it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Auto-restart            | The plugin keeps "the service should be running" only once its `configure_recovery` command is called with `{ enabled: true, config }`, which exists only over IPC. So the base calls it once it starts, after its telemetry consent is answered, through `servers-core`'s `enableKeepAliveRecovery`. The `main` webview is granted `background-service:allow-configure-recovery` and nothing else of the plugin's; the app depends on the plugin crate directly so `tauri-build` finds that permission. A failure is logged and costs only the plugin's own restarts. On iOS the persisted intent is what the `BGTask` auto-start reads. On Android the servers need the app (their ports need the `AppHandle`), so after a reboot or an OS kill they run again once the app opens, which the plugin's recovery notification offers.                                                                                                                                                                                                                                                          |
| Persistent notification | Android uses the plugin's foreground-service notification, with the start config's label ("Wildflower server is running"), for every server at once. Its text is fixed at start because the plugin has no update API. iOS and desktop get nothing persistent.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Plugin config           | `plugins.background-service` in `tauri.conf.json`: `androidForegroundServiceTypes: ["specialUse"]` (the plugin checks the start type against it on every platform; a host test reads it through the plugin's own config type) and `iosRequiresNetworkConnectivity: true`. `specialUse`, not `dataSync`: Android 15 caps `dataSync` at 6 h a day, and a server isn't a sync.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Android manifest        | The plugin's manifest asks for `CAMERA`, `RECORD_AUDIO`, `MANAGE_OWN_CALLS`, `USE_FULL_SCREEN_INTENT` and the `phoneCall`, `microphone`, `dataSync` and `remoteMessaging` foreground-service permissions, for its calling and messaging features. The app manifest removes each from the merge (`tools:node="remove"`), and removes the plugin's Telecom `BackgroundCallConnectionService`, which Telecom binds only with `MANAGE_OWN_CALLS`. It narrows the plugin's `LifecycleService` to `specialUse` (`tools:replace`) and replaces the plugin's generic `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` with the server's own reason, which Play reviews. The boot receiver stays, as do the plugin's call- and message-action receivers, which are unexported and fire only from notifications this app never posts. Host tests parse the tracked manifest for each override.                                                                                                                                                                                                                         |
| Plugin fork             | The workspace's `[patch.crates-io]` points the plugin at our fork, pinned to a commit, and `deny.toml` allows that git source. The fork carries two fixes, each sent upstream; the patch goes once upstream releases them. **Android:** the plugin's foreground service starts a native "headless core" through `HeadlessBridge` before it reports itself started, and 1.0.1 fails the start when there is none. The fork accepts a start the plugin itself makes (`manual_start`) as lifecycle-only, since the runner's keep-alive service is in the process. A start Android makes on its own still fails, since the process may hold no app: after a sticky restart the plugin posts its "Tap to resume" recovery notification, which opens the app. **iOS:** going to the background with the service running, the plugin holds a UIKit background task, and 5 seconds before its time runs out stops the service with `PlatformExpiration`, so the runner's revocation ends every run cleanly and their stop notifications ("Wildflower server paused") post before iOS suspends the app. |
| iOS                     | `UIBackgroundModes` gets `fetch` and `processing`, and `BGTaskSchedulerPermittedIdentifiers` gets `$(PRODUCT_BUNDLE_IDENTIFIER).bg-refresh` and `.bg-processing`, which is what the plugin registers (the bundle identifier plus those suffixes). Both go in `Info.ios.plist` and the generated `Info.plist`, which an Xcode-opened build reads alone; a host test checks both.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Desktop                 | In-process mode only. The plugin's `desktop-service` feature (systemd/launchd daemon) stays off: the servers need the `AppHandle`-backed ports. Desktop notifications stack: the notification plugin has no replace-by-id there.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Dependencies            | `tauri-plugin-notification` is locked at 2.4.0, the last release that builds on the workspace's `tauri` 2.11; the manifests ask for `"2"`, so a `tauri` upgrade takes it forward.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

## Verification limits

`servers-tauri-rust` and the app crate link `webkit2gtk`, so they build only
where GTK/webkit is installed (CI, and a container that has it). That is why
the logic lives in `servers-rust` and `wildflower-server-rust`.
`servers-rust`'s `tests/server_unit.rs` runs the real server through
`UnitRunner`: it comes up `Running`, answers `/health`, reports its health
as its detail, stops with the detail cleared when its policy turns off, and
binds the same port again when it turns back on. The manifest and plist tests
check what the files declare, not what the Android manifest merger or iOS make
of them, and the mobile background session can only be verified on a device.

### Device test plan

Android (13 or later, with a server added):

1. First launch: the notification prompt appears once, then the "Wildflower
   server is running" notification with its Stop action. The merged manifest
   (`app/build/intermediates/merged_manifest/`) has none of the removed
   permissions and no `BackgroundCallConnectionService`, and
   `adb shell dumpsys activity services app.tauri.backgroundservice` shows the
   service running as `specialUse`.
2. Set the server's policy to always, lock the phone for ten minutes, then
   call the server through the tunnel from another device: it answers, and a
   request notification names the caller.
3. Tap Stop on the persistent notification: the server stops, and the
   "Wildflower server stopped" notification names it and the reason.
4. Reboot with the server running, then open the app, from the plugin's
   recovery notification if one appears: the server runs.

iOS:

1. First launch: the notification prompt appears once.
2. Background the app, then launch each task from the debugger
   (`e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"<bundle id>.bg-processing"]`,
   then `.bg-refresh`): the server answers through the tunnel inside the
   window.
3. End each window (`_simulateExpirationForTaskWithIdentifier:`): every expiry
   posts "Wildflower server paused", replacing the last one rather than
   stacking.
4. Background the app with no task simulated: shortly before iOS suspends the
   app, "Wildflower server paused" posts, and the server stops.
5. Bring the app back to the foreground: the server runs again, with no stop
   notification for that, and answers.

## Risks

- **Plugin maturity.** First published in April 2026 by one author, about 19k
  lines. It is pinned exactly (`=1.0.1`), patched to our fork's commit. If it
  becomes a liability, the surface `TauriUnitRunner` uses (start, stop, events,
  the Android FGS and the iOS `BGTask`) is small enough to replace.
- **Store review.** Play needs a `specialUse` justification. App Store needs
  justification for `processing`/`fetch` background modes.
- **Helios globals.** No slice holds process-global state. Helios's `OnceLock`s
  are immutable caches or per-instance, and it spawns on the current runtime, so
  a second run in the same process is safe. The `ServerUnit` test runs a
  server twice end to end.

## Deliberately not here

- A cap on running servers, or any guard against two servers on the one
  loopback port.
- iOS Live Activity, a desktop tray icon, or updating the FGS notification text
  (the plugin has no API for it).
- OS-service (daemon) mode on desktop.
- Remote push (APNs/FCM). Every notification is local.
- A native error dialog for a failed run: `UnitRunner` retries it every few
  seconds, and its stop notification says why.
